## URL / Search State（2026-08-25 確定）

Searchの状態はURLが正本。同じ生URLをPC/Mobileへ与えたら**同じ意味**になること。
件数の一致は求めない（モックのfixtureが別なので原理的に不可能）。

### 自由語 `q`

- `q` パラメータ無し / `q=` 空 は **自由語条件なし**（その種別の全件）。空の `q` はURLへ書かない
- **`q` は全検索計算の基底 predicate**。適用先は
  実結果 / 総件数 / 種別チップ件数 / Facet選択肢件数 / Mobileシート内のpreview件数 **すべて**
- 検索対象フィールド（PC/Mobileで同一の意味論）
  | 種別 | 対象 |
  |---|---|
  | RIG | rig名 + model + maker |
  | PARTS | パーツ名 + brand |
  | LOG | title + 紐づくRIG + 紐づくRIG由来のmaker |
- **ユーザー名 / `@handle` は検索対象に含めない**
- 関連度ランキングはモックでは持たない（後続 Search Service の責務）
- 検索トップの Enter と固定CTA（「この条件で検索」）は**同一の Search State serializer** を通す

### `type`

- **URLの外部語彙は `rig` / `parts` / `log`**。PC内部の `logs` はmappingの内側だけに閉じる
- 未知のslugは無視する（指定が全滅したときだけ既定へ）

### Facet の語彙と検証

- **正典語彙（canonical vocabulary）と fixture存在値を分離する。**
  fixtureに在るかどうかは「URLとして有効か」の判定に使わない
- 正典上有効だが今回0件の値 → **条件を保持して0件表示**（選択肢にも出して解除できるようにする）
- 存在しない/旧語彙/壊れた値 → **解除して通知**（silent clear 禁止）
- `manufacturer` は閉じた値集合を持たない（Research所有）ため**判定不能**。
  判定できない値は解除せず保持する（fixtureに無ければ0件）。
  これは暫定処理であって「任意の非空文字列が正規メーカー値」という仕様ではない

### Facet の適用規則

- 同一Facet内は **OR**、異Facet間は **AND**
- 種別固有Facetは、**単一種別に絞っているときだけ**出す（規則C）
- 種別固有Facetを選んだ時点で、**対応する `type` へ state を正規化する**
  （車種カテゴリ→`rig` / パーツカテゴリ→`parts`。両者は同時に保持しない）
- scope変更で無効になった条件は**実際に解除し、必ず通知する**（隠すだけにしない）
- `maker` は RIG/PARTS では正本属性。
  **LOG は linked RIG から確実に導出できる場合のみ派生**（明示的な関連属性を使う。
  表示名の部分一致・推測紐付けは禁止）。未紐付けLOGは NULL 相当

### ページングと復元

- PCの `page` / `per` は**実際に結果カード集合を切り出す**（表示だけ変えない）
- reload / 戻る / 進む で**カードの同一性まで**復元する
- 結果 `total === 0` は **Empty State** へ接続する（デモ状態ではなく通常のSearch State）

### 検索基盤の実装原則（2026-08-23 裁定・未実装）

Next.js実装時の検索基盤は、**ページごとに独立した検索エンジンを作らず、共通の Search Service を1つ持つ**。
検索面ごとの差は、検索対象indexとranking/filter profileの切替で表現する。

- **Community index**: RIG / ユーザー登録PARTS / LOG を対象。標準検索の主対象。
- **Catalog index**: Research所有のmasterデータを検索用ドキュメントへ同期・索引化したもの。Library検索の主対象。
- **User index**: profile / handle 等のユーザー検索用。
- **Search profile**: Global / Library / User / Registration / Feed内検索等で、対象index・重み・フィルター・ソートを切り替える。
- query正規化、alias/synonym解決、typo tolerance、公開可否/権限フィルター等の共通処理はSearch Service側へ集約し、各ページへ重複実装しない。
- Feedの通常表示（おすすめ/フォロー中等）は検索ではなく推薦・ランキング責務として分離する。将来Feed内自由語検索を設ける場合は共通Search Serviceを利用する。

**未確定のまま残すもの:** Meilisearch / Typesense / Algolia / PostgreSQL FTS 等の具体製品選定、index物理構成、同期方式、関連度の数式・重み。実装時に比較・実測して決める。
この原則は「同じ語なら全画面で同じ順位になる」という意味ではない。検索面ごとにranking profileは変えてよいが、検索基盤と正規化ロジックは共通化する。
