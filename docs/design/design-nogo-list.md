## NG-1: 角丸カードの片側に、色付きの帯・影をずらして置くデザイン 【最重要】

**イタヤ裁定（2026-07-29・複数回）:**
> 「角丸カードの左側とか上側とかに色付きの影みたいなのをずらして使うデザインが結構あるんだけど、
> これがいらないっていう意味ですね。（中略）事あるごとにこれをやってきて、本当禁止してるんだけど
> やってきちゃうんだよね。このデザインは絶対使わないよっていうのです。」

**再発（2026-08-17）:**
> 「えっと、このデザイン大嫌いって、言わなかったっけ？」
> モバイル `library*.html` の「探し方を選ぶ」3枚（`.lb-door`）が
> `border-radius:12px` ＋ `border-left-width:4px` ＋ カテゴリ色のまま残っていた。

### 具体的に何がNGか

角丸のカードやパネルに対して、**上辺だけ／左辺だけに太い色帯**（3〜4px以上）を付ける表現。
カードの角丸と直線の色帯が噛み合わず、色帯だけが浮いて「ずれた影」のように見えるため。

該当例（実際にコード内に存在した）:

- `pc/myrig-library-v3.html` の `.door--rig { border-top: 4px solid var(--cat-rig) }`（車種カタログの緑帯）
- 同 `.door--parts { border-top: 4px solid var(--cat-parts) }`（パーツカタログの紫帯）
- `pc/myrig-home-v3.html` の `.home-dir .dir-card--active { border-left: 4px solid var(--cat-rig) }`
- `pc/myrig-feed-v3.html` の `.act-item { border-left: 3px solid <カテゴリ色> }`（P22-C7で中立へ）
- `pc/myrig-browse-category-v3.html` / `-parts-v3.html` の `.dir-subheader { border-left: 3px solid <カテゴリ色> }`（P22-C7で塗りバッジ→C9で横長の帯へ）
- GPT提案の「中立＋色線」ボタン（角丸ボタンの上辺に3pxのカテゴリ色）
- **モバイル `library*.html` の `.lb-door--rig / --parts / --maker`**（7ページ×3件・P22-B19cで撤去）
- **モバイル `rig-detail` / `parts-detail` / `garage-parts-detail` の `.rd-shop__store`**
  （`border-radius:10px` ＋ `border-left:3px solid var(--brand)`・P22-B19cで撤去）

**このパターンはコードベース全体で30箇所が検出済み**（2026-07-29時点）。
**2026-08-17 時点でモバイル側は処理完了**（カテゴリ色の片側太ボーダーは実測で残存0）。
細い区切り線（`border-left: 1〜2px` の `--ms-border` 等の中立色、コメント返信のインデント線など）は
構造上必要なので対象外。

### 何がNGでないか（重要・以前この線引きを誤った）

- **リスト行の背景色**（現在地・ホバーの塗り）は別物。禁止ではない
- **細い中立色の区切り線**（1〜2px、`--ms-border` 系）は構造として必要。禁止ではない
- **行の内側に置く左端の縦棒**も別物。下記NG-2の条件を満たせば使ってよい

### 代替として許容されるもの

- 全面塗り＋白抜き（または黒）文字
- 薄い色地＋濃い色文字
- 小型の塗りバッジ（カード上のバッジと同じ形）
- 横長の帯（サイドバーの種別ラベルはこの形を採用。P22-C9）

**P22-B19c で採った形が今の見本**: カードに既にあったアイブロー
（VEHICLE CATALOG / PARTS CATALOG / MAKER INDEX）を**小型の塗りバッジ**に変え、左の色帯は撤去した。
種別は伝わり、線は1本も増えていない。**「色帯を消したら種別が分からなくなる」ときは、
線を別の場所に移すのではなく、既にある要素を塗りバッジに変えられないかをまず探すこと。**

## NG-2: 白地・黒地に、色だけで輪郭を作らせる

**イタヤ裁定（2026-07-29）:**
> 「ライトモード時のイエローRIGカラーでは色が識別できないから、という意味です。
> ダークモードの時はむしろ黄色が映える。」

**絶対禁止ではなく条件付き。判定は「地が形を作っているか」で分かれる。**

数値根拠: レモンイエロー `#FBFF00` と白地 `#ffffff` のコントラストは **1.08**（基準3.0）。
淡いグレー地 `#e3e6ea` に対しても **1.15**。つまり黄色は明るい地の上で輝度差をほぼ持たない。

### 不可: 地の上に単独で置いて、それ自体で形を示させる場合

- 白地の上に浮かぶ5px前後の装飾ドット（`.list__dot` / `.log-dot` / `.fr::before` は
  `--cat-rig` だったためライトで完全に消えていた。P22-C7で中立へ）
- 白地の上の細い区切り線・アンダーライン
- 白地に黄色を面として置いて、境界だけで形を認識させる場合
- **カテゴリ色を「文字色」「線色」として使うこと**（P22-B19で追加）。
  RIG黄の文字は白地で 1.08。PARTS赤・LOG紺もダークで 3.7〜4.0 と基準割れする。
  チップやラベルは**塗り**にして、対の文字色（`--cat-*-on`）を乗せる。

### 可: 別の要素が形を作っていて、色は識別のためだけに乗る場合

- **行の内側に置く左端の縦棒**（P22-C9で採用）。現在地の行には一段濃い地
  （ライト `#e3e6ea` / ダーク `#2d333b`）が付いており、行の形は地が作っている。
  縦棒は「どの種別の中にいるか」を言うだけなので、**RIG=黄 / PARTS=赤 でライト・ダーク共通**。
  イタヤ裁定 2026-07-30:「パーツの時はここは赤の縦線でいい。リグのところは黄色の縦線だと自然じゃない?
  背景はこの色でいいんだけど」。1pxの縁を足した版と実測で見比べたが実寸で差がほぼ無く、素のままとした。
- 塗りバッジ・塗り帯の上の文字（黄地に黒文字16.87 / 赤地に白文字4.83）
- **押して切り替えるチップの「小さなドット」**（P22-B19で採用）。
  チップの形は中立の線が作っており、8pxのドットは種別を言うだけ。

一度この線引きを誤って「ライトは両方とも中立にそろえる」と実装し、差し戻された。
**NG-2は「色だけで輪郭を作らせるな」であって「ライトで黄色を使うな」ではない。**

## NG-3: ライトモード用に色をくすませる

**イタヤ裁定（2026-07-29）:**
> 「初期のバージョン1モックの時はライトモードにすると色がくすんだ色になって
> こんな風になるみたいな風にしてました。ただこれだとちょっと全く変わってしまって
> 意味がないのでそれはこの感じはやめたいんだよね」

**対象:** 同じカテゴリ色について、ライトモードで彩度・明度を落として別の色に見えるまで変えること
（例: レモンイエロー `#FBFF00` → マスタード `#B8940A`）。

**代替:** 色の値は両モードで保つ。輪郭が必要なら枠・スクリムで確保する。
同一色相内の軽い明度調整（例: LOG青をダークのみ `#2F5F8F` → `#3F709E`）は
「別の色に見える」範囲ではないので該当しない。

## NG-4: 一覧の中で1行だけ反転（黒地に白抜き）にする

**イタヤ裁定（2026-07-29）:**
> 「こりゃダメだ(笑) ライトモードの方、黒が濃いし、文字がギリギリだし、バグってるようにしか見えない。
> ダークは文字が同化して消える。その前にダサイし、デザインが破綻してる。」

サイドバーのカテゴリ一覧やナビで、現在地を示すために1行だけ中立色で反転させる表現。
一覧の中で1行だけ極端に重くなり、異物に見える。

**代替:** 太字を主役にし、地の差は控えめにする（ホバーより一段強い程度）。
P22-C9の最終形は「地を一段濃く（#e3e6ea / #2d333b）＋太字＋4px×18pxの縦棒＋
現在地を含むグループの箱も一段浮かせる」。反転はしない。

モバイルの下タブも同じ考え方。P22-B19b では**淡いグレーのピル＋黒の太字**にした
（Yahoo!オークションの下タブと同じ作り）。塗りで反転はさせない。

### 関連して却下: 現在地の行をカテゴリ色で塗りつぶす

**PARTS側では現在地が赤くなり「エラー・警告・削除」に見える。**
状態を示す色が危険を示す色と同じになってはいけない。

## NG-5: 罫線を足して整理しようとする

**イタヤ裁定（2026-07-30）:**
> 「なんかこの枠を含めてさ、まず大きな枠があって、その中に罫線があって、
> さらにそのカテゴリー、オフロード・オンロード種別の枠があって、罫線だらけなんだ。
> エディトリアルデザインとかでも、線を足すとデザインがごちゃつくっていうルールがあるので」

セクション見出しに「ラベル＋右へ伸びる1pxの罫線」を提案して却下された案がこれ。
サイドバーは既に **外枠 → グループの枠（OFF-ROAD / ON-ROAD / SCALE & SPECIAL）** と
枠が二重になっており、そこへ罫線を足すと線の層がもう一段増える。

**代替:** 区切りが必要なら、線ではなく**面**（帯・塗り・地の段差）で行う。
帯そのものが区切りになるので、線を1本も足さずに済む。

## NG-6: ナビゲーション項目に二次色（グレー）を使う

**イタヤ裁定（2026-07-30）:**
> 「左サイドバーの文字色がなんか全体的にすごいこうグレー薄くなってて、
> 目立たないというよりもなんとなく気持ち悪いんだよね。（中略）
> ナビゲーションの部分だしこれはもうちょっと黒くていいのかなって気はする」
> 「ダークモードにした時に（中略）右側のカードタイトルと同じくらいパキッと目立たせてもいいのかな」

**実測した差（P22-C12以前）:**

| | サイドバーのカテゴリ行 | カードのタイトル |
|---|---|---|
| ライト | `#656d76` CR **5.25** | `#1f2328` CR **15.80** |
| ダーク | `#8b949e` CR **6.15** | `#e6edf3` CR **16.02** |

ナビゲーション項目が本文の 1/3 の強さしかなかった。

**原因は GitHub のトークンの使い方を取り違えていたこと。**
GitHubのサイドバーでもナビ項目（All issues / All pull requests / All repositories / Projects / Discussions …）は
**本文色**で、薄いのはセクション見出し（Top repositories）だけ。二次色をナビ項目には使っていない。

**加えて、和文は英字より線が細く見える。** 同じグレーでも日本語のほうが弱く出るので、
英語圏のUIから色を借りるときは一段濃くする前提で見積もる必要がある。

**規約: 「行の名前は本文色、添え物は二次色」。**

- カテゴリ行の名前 → `--color-text`
- 件数・日付・@ユーザー名などの添え物 → `--color-text-secondary`
- セクション見出し（OFF-ROAD 等）→ `--color-text-secondary`（項目より薄いが、CR 4.5は下回らせない）
- 現在地との差は**文字色ではなく** 太字 ＋ 濃い地 ＋ 縦棒 で作る（NG-4の教訓）

## NG-7: カテゴリ色を操作・アバター・通知に流用する（P22-B19で追加）

**イタヤ裁定（2026-08-17）:**
> 「たしかにこれはBかな。黄赤青以外の色味はうるさすぎる。ナビ系は普通に白黒系でいい。
> ただ、YAHOOとかみたいに、単純にベタ白黒っていうか、上手い事処理して、重くないようにして欲しい。」

**確定した職域:**

| 用途 | 色 |
|---|---|
| 種別の識別 | RIG `#FBFF00` / PARTS `#D92D20` / LOG `#2F5F8F`（dark `#3F709E`）**のみ** |
| 操作 | 中立。ライト `#1F2328` / ダーク `#E6EDF3`（純黒・純白は使わない） |
| 現在地・選択 | 淡いピル＋太字。塗りで反転させない |
| アバターのプレースホルダ | 無彩色の3階調 |
| 通知・未読・NEW | 赤に集約（`#D92D20` / dark `#E5534B`） |

**黄・赤・青と白黒以外の色を新しく足さないこと。** 緑・紫・橙はこの裁定で全廃した。

**「重くしない」の具体:**

- 黒を塗るのは**主操作だけ**（登録する / この条件で検索 / 適用）
- 数が多いもの（フォロー等）は**線＋文字**。並んだときの重さはここで決まる
- 押した後の状態は淡い地に沈める（`--color-action-quiet-bg`）
- 中立色にしたら**影は外す**（色が無い分、影が重さとして残る）

## 参考: 実測で判明している制約（デザイン判断の前提）

- カード上のバッジが乗る領域の輝度は、実画像68枚で **0.03〜1.00 と全域にばらつく**
  （中央値0.37、彩度中央値7%）
- そのため **平坦な色は、どのパレットでも半数以上の写真で輪郭が立たない**
- **バッジの可読性は色相ではなく輪郭処理（枠・スクリム）で決まる**
- 白背景に白文字を乗せられない色: 黄 (1.64)、ライム緑 (2.47)、オレンジ (2.57)
- レモンイエロー `#FBFF00`: 黒文字 16.87（最良）／白地との差 1.08／淡グレー地 `#e3e6ea` との差 1.15
- **Barlow Condensed は英字が同ポイントでも和文より小さく見える。**
  帯やバッジに入れると特に沈むので、和文と並べるときは一段〜二段上げる
  （サイドバーの種別ラベルは 13.5px → 17px・字間 .1em）
- **ヘッダーのロゴ画像は文字が画像の端まで来ていて余白を持たない**（画像の右端＝Gの右端）。
  隣が塗りのピルだと視覚的に接するので、外側余白は通常より広く取る（40px）

## 検査の盲点（2026-07-30 / P22-C7・C9・C12で判明、2026-08-17に追記）

### 1. カードは Web Component で、CSSは shadow DOM の中にある

`myrig-rig-card` / `myrig-part-card` / `myrig-log-card` の見た目は
`pc/assets/js/SoT_card-components.js` 内のスタイルが決めている。

- **ページ側の `<style>` は shadow DOM 内の要素に届かない。**
  カスタムプロパティ（`--cat-rig` 等）だけが境界を越えて継承される。
  カードの中身を変えたいときは、値をトークン経由で渡すか、コンポーネントファイル自体を直す。
  ページに `.br__badge--rig { ... }` と書いても無効。
- **検査ハーネスも `document.querySelectorAll('*')` では shadow DOM を貫通しない。**
  従来の `catcheck.mjs` がこれで、そのため **home でも RIGバッジが
  黄地に白文字（コントラスト1.08）のまま見逃されていた**。
  必ず `if (e.shadowRoot) recurse(e.shadowRoot)` を入れる。
  背景色を遡る処理も、`parentElement` が null になったら `getRootNode().host` へ続ける。

### 2. 詳細度で勝っていても、宣言が無ければ下のルールが生きる

共有CSS `pc/assets/css/SoT_browse-sidebar.css` に
`.dir-branch::before, .dir-branch::after { display:none; content:none; }`
（tree connectorの装飾線を全廃した名残）がある。

`.dir-branch.is-current::before` 側で `content` `width` `height` `background` を
`!important` で上書きしていたが、**`display` を書いていなかった**。
競合する宣言が無いので `display:none` がそのまま生き、
**P22-C5 以降ずっと現在地の縦棒が1本も描画されていなかった**（P22-C9で発覚・是正）。

しかも当時の検査は `background` の計算値だけを見て「黄色になっている」と判定していた。
実際には `display:none` で存在しなかった。

**教訓:** 疑似要素を検査するときは `display` `content` `width` `height` を必ず一緒に読む。
既存のリセットを打ち消す場合は、打ち消したいプロパティを漏れなく明示する。

### 3. 共有CSSを直しても、ページ本体の `!important` が打ち消していることがある

ヘッダーのロゴ余白を共有CSS `SoT_app-shell.css` で 6px → 28px に直したが、
**home 本体に v0.8.32 の `.app-logo--image { margin-right: 6px !important }`**
（当時「ロゴ〜Browseをさらに詰める」意図で入れたもの）があり、home だけ効いていなかった。
検証を browse-category で行ったため 28px と出て見逃した（P22-C12で発覚・是正）。

**教訓:** 共有CSSを変えたら、**検証は必ず複数ページで行う**。
特に home は `!important` が743個あり、共有CSSの変更が届かない可能性が最も高いページ。
`grep -rn "<直したプロパティ>.*!important" pc/*.html` で打ち消しの有無を先に確認する。

### 4. 修飾子ルールは背景しか持たず、文字色は親ルールにある（2026-08-17 / P22-B19で判明）

`.gcard__type { color:#fff }` ＋ `.gcard__type--rig { background: var(--cat-rig) }` という分け方が多い。
**同一ルール内で `background` と `color` を突き合わせる置換では届かない。**
「背景がカテゴリ色のルール」を見つけたら、そのルールに `color` 宣言が無い場合こそ危険で、
親から白が降ってきている。P22-B19 ではこの形が **56種／のべ300箇所超**残っていた。

### 5. ダークテーマの計算色スナップショットは比較に使えない（2026-08-17 / P22-B19で判明）

ページ側のテーマ初期化とハーネスの `data-theme` 設定が競合し、
**同一コードを2回測っても dark では632件の差分が出る**（light は6件）。
視覚回帰ゼロを検証するときは **light で比較し、dark は別途コントラスト実測で担保する**。

### 6. 一方のテーマにだけ古い宣言が残る（2026-08-17 / P22-B19bで判明）

`[data-theme="dark"] .btn-follow { background: ... }` が別行に残っており、
ライトだけ直してダークが**白地に白文字**になっていた。
`[data-theme="dark"]` 側は詳細度が高く後勝ちしやすいので、
**ルールを直したら必ず同名の dark 宣言も grep すること。**

## コード衛生上の既知問題（2026-07-29 実測）

`pc/myrig-home-v3.html` 単体で:

- `.dir-branch.is-current` の定義が **13回**
