## この依頼の位置づけ

PC版の検索ページのフィルタを「実DBに沿った形」に作り直す作業の中で、
**スキーマに存在しない軸／古い値セット／自由テキストのため絞り込みが成立しない軸**が出てきました。

いずれもUIの都合ではなく、**データ設計を決めないとMVP実装で詰まる**ものです。
Q1〜Q4は着手前に決めたい優先度、Q5以降は実装と並行で構いません。

回答は「決まっている」「未定」「そもそも持たない方針」のいずれかを明示していただければ十分です。
未定のものはこちらでHOLDとして扱い、モックには要確認の印を付けたまま進めます。

## Q1【最優先】スケールをどこに持つか

**現状:** `rigs` にも `rig_masters` にもスケールのカラムがありません。

**なぜ困るか:** RCでは 1/10 と 1/24 は互換性が全くありません。
タイヤ・ホイール・ボディ・シャーシのどれも共用できないので、
**スケールで絞れない検索は実用になりません。** 1/10 のクローラーを探している人に
1/24 のクローラーが混ざるのは、別のジャンルが混ざるのと同じ体験です。

**確認したいこと:**

1. スケールは正規化カラム（`rigs.scale` / `rig_masters.scale`）を持ちますか。
   それとも `rig_masters.specs` JSONB のキーとして持ちますか。
2. `specs` JSONB に入れる場合、絞り込みに使う前提でよいですか。
   （JSONBでも GIN インデックスで絞れますが、値の表記揺れを防ぐ仕組みが別途必要になります）
3. 値の形式はどうしますか。文字列 `"1/10"` か、分母だけの整数 `10` か。
   分母整数なら「1/10以上1/8以下」のような範囲指定ができます。
   文字列だと `1/10` `1:10` `110` の揺れが起きます。
4. **スケールはマスター由来か、ユーザー申告か。**
   `rig_masters` に持たせて `rigs` は継承するのか、`rigs` にも独立して持たせるのか。
   ボディだけ載せ替えた・ホイールベースを伸ばした場合に実質スケールが変わることがあります。
5. ジャンルによってスケールの意味が変わる点はどう扱いますか。
   ミニ四駆は 1/32 固定、Mini-Z は 1/27 前後で、RCと同じ軸に混ぜると意味を持ちません。

**イタヤ所見（2026-07-30）:** 「スケールは無いなんて事あるのかな? オフィシャルのスケールサイズDBってことか。」

## Q2【最優先】`rig_type` の現行の確定値セット

**現状:** スキーマv1.6 は
`CHECK (rig_type IN ('rc','mini4wd','miniz','drone','airplane','boat'))`

**イタヤ指摘（2026-07-30）:** 「Mini-Zは大大カテゴリからは外してあるよ。これ古いスキーマだね。」

**確認したいこと:**

1. 現行の確定値セットを教えてください。`('rc','mini4wd')` だけですか。
   ドローン／飛行機／ボートは値として残しますか（サイドバーでは「計画中」として席を確保しています）。
2. **外した Mini-Z の受け皿はどこですか。**
   モックでは `rigs.product_line`（ブランドシリーズ）に置く前提にしました。
   それが正しいですか。それとも `categories`（サブカテゴリ）ですか。
   Mini-Z は「スケール 1/27 前後の小型RC」という括りなので、
   Q1のスケール軸で表現されるなら `product_line` で足ります。
3. `profiles.preferred_rig_type` / `parts.compatible_types` / `categories.rig_type` /
   `rig_masters.rig_type` / `parts_masters.rig_type` も同じ値セットに揃いますか。
4. MVPで `rc` 以外のデータは0件の想定でよいですか。
   0件なら、UIは「RCのみ選択可、ミニ四駆は予定表示」で作ってあります。

## Q3 パワーソース（電動 / エンジン / ガソリン）は持たない方針か

**現状:** どのテーブルにもありません。モックからは撤去しました（イタヤ「無くてOK」）。

**確認したいこと:**

1. 意図的に持たない方針でよいですか。
2. 持たない場合、「これはエンジンカーです」という情報はどこに現れますか。
   パーツ側は `categories` に「エンジン・燃料系」があるので表現されますが、
   **RIG単体を見たときに電動かエンジンかを言う場所がありません。**
   `build_details` JSONB の `mechanics` に「Engine: ...」と入るだけ、という理解で合っていますか。
3. 将来ニトロ／ガソリン勢が増えたときに絞り込み軸として必要になる可能性はありますか。
   必要になるなら、Q1のスケールと同じ場所（`specs`）に置いておくと後で楽です。

## Q4 `platform` / `product_line` はマスター化するか

**現状:** `rigs.platform`（例: SCX10 III, BB-01）と `rigs.product_line`（例: Mini-Z, Clod Buster）が
どちらも自由テキスト（TEXT, NULLABLE）です。`rig_masters` 側にも同じ2カラムがあります。

**なぜ困るか:** 自由テキストだと表記揺れで絞り込みが成立しません。
`SCX10 III` / `SCX10-3` / `SCX10III` / `scx10iii` が全部別値になります。
モックでは「シャーシ / プラットフォーム」を絞り込み軸に入れましたが、
**このままでは実装できません。**

**確認したいこと:**

1. `platform` / `product_line` をマスターテーブル化しますか（`platforms` / `product_lines`）。
2. しない場合、`rigs.platform` は `rig_masters.platform` からの**継承のみ**にして、
   ユーザーの自由入力を許さない運用にしますか。
   （マスターに紐付いていない `rigs` では NULL になる）
3. 表記の正規化ルールを設けますか（大小文字・空白・ローマ数字とアラビア数字の統一など）。

## Q5 `maintenance_logs` の `surface` / `weather` の候補値

**現状:** どちらも自由テキストです。

**確認したいこと:**

1. 固定値セット（`CHECK` または参照テーブル）にしますか。
   それとも自由入力のまま、頻出値を集計して候補提示しますか。
2. 固定値にする場合、候補を教えてください。
   モックでは 路面=岩/土/芝/アスファルト/カーペット/砂、天候=晴れ/曇り/雨/雪 を仮置きしています。
3. `location` は自由テキストのままでよいですか（地名の正規化はしない前提）。
4. `tags` TEXT[] はユーザーの自由入力ですか。運営側の正規タグ集合を持ちますか。
   フィルタに出すなら、頻出タグの集計が必要になります。

## Q7 全文検索の対象範囲

**確認したいこと:** 検索窓に文字を入れたとき、何をヒット対象にしますか。

1. RIG: `model_name` / `nickname` / `description` / `base_model` /
   `manufacturer_name_cache` / `platform` / `product_line` /
   **`build_details` JSONB の中身**（「Reefs RC 299」で検索したらそれを積んでいるRIGが出るべきか）
2. Parts: `product_name` / `part_number` / `description` / `manufacturer_name_cache`
3. Library: `parts_masters.aliases`（GINインデックスあり）。
   **`rig_masters` に aliases 相当がありませんが、必要ではないですか。**
   車種も通称・旧名・海外名の揺れがあります（例: ハイラックス / Hilux / TF2）。
4. Logs: `title` / `body` / `tags` / `location`
5. Users: `username` / `display_name` / `bio`

日本語の分かち書きをどうするか（`pg_trgm` / `pgroonga` / Supabase の `websearch_to_tsquery`）も、
決まっていれば教えてください。

## Q11 「写真あり」「ログあり」で絞るための集計

**現状:** モックのフィルタに「写真あり」「整備・走行ログあり」「パーツ登録あり」を入れました。

## Q12 `rig_masters.specs` / `parts_masters.specs` のキー設計

**現状:** どちらも `JSONB DEFAULT '{}'` で、中身が未定義です。

**なぜ困るか:** Q1のスケールをここに入れる案が出ています。
また Library の比較機能（車種同士を並べて見る）を作るなら、
キーが揃っていないと比較表が組めません。

**確認したいこと:**

1. `specs` のキー設計は決まっていますか。
2. 決まっていない場合、少なくとも以下は入りますか。
   車種側: スケール / 駆動方式（4WD・2WD） / 全長 / ホイールベース / 幅 / 車重 /
   モーター種別（ブラシ・ブラシレス・エンジン） / 防水 / キットかRTRか
   パーツ側: 適合スケール / 適合シャーシ / 材質 / 寸法 / 重量 / 電圧・トルク（サーボ）
3. キーは `rig_type` ごとに変わりますか（ミニ四駆に「防水」は無意味）。
   変わる場合、キー定義をどこで管理しますか（アプリ定数 / テーブル）。
