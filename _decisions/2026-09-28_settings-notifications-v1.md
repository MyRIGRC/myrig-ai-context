## D1 アプリ内通知を MVP に含める

- schema Domain 9 `notifications` を「将来用・MVP では作成しない」から **MVP 実行分へ移す**。メール・Push は MVP の外
- 種類 = `like` / `comment` / `comment_reply` / `follow` / `favorite`
- **favorite は名前を出さない通知**。通知行に `actor_id` を**保存しない（NULL）**。表示で隠すだけだと API から読める
- **like / favorite / follow は「その人がその対象に初めて行った時」だけ通知を作る**（元テーブルに同じ actor × 対象の行が、論理削除済みも含めて無いとき）。comment / comment_reply は毎回
- 自分の行為（自分の RIG へのいいね等）は通知しない。pin は通知しない。System 通知は後段

**なぜ**
- MyRIG の中核は「見せる → 反応が来る → 気づく → 戻る」。like / comment / follow を MVP に入れて通知だけ後回しは、戻る理由の無い片道になる（Claude・GPT 一致）
- 「将来用」とあるだけでコスト・技術上の理由は書かれていなかった（L2）

**罠**
- favorite の個別行は RLS で本人しか読めない（schema RLS favorites）。通知に actor を持つと別経路で「誰が保存したか」が漏れる（ASTRA 指摘）
- actor を持たない通知を単純に数えると、保存 → 解除 → 再保存で「2 人に保存」と誤表示する（ASTRA 指摘）→「初回だけ」で件数 = 人数になる
- 同じ穴が like / follow にもある。付けたり外したりで通知を連打でき、嫌がらせの経路になる（Claude）
- 「公開数と同じ情報しか漏れない」は言いすぎ。通知には時刻と、解除後も残る履歴が加わる。**「名前を開示しない通知」として採用**（ASTRA 訂正）

## D2 通知は 1 件ずつ保存し、表示の時に束ねる

- 束ねるのは **like / favorite だけ**（同じ種類・同じ対象）。comment / comment_reply / follow は 1 件ずつ（人と内容が大事）
- **既読は `read_at TIMESTAMPTZ NULL` で持つ**（`is_read BOOLEAN` を置き換え）。既読の束 = 同じ種類・同じ対象・同じ `read_at`
- 「すべて既読」は**押した時刻より前に作られた未読**だけに `read_at` を入れる
- 書き込み規則（ASTRA 補足 19:06）: 1 回の既読操作は**サーバーで決めた同一時刻**を全行に入れる（行ごとに時刻がずれると束が割れる）／**未読の行だけ**更新し、既読の `read_at` は上書きしない
- 通知の生成元: `likes` / `favorites` / `follows`（**初回判定あり**）・`comments`（毎回。親コメントの有無で `comment` / `comment_reply` を決める）
- 初回判定: **成功した INSERT に対し、論理削除済みを含む過去の履歴から初回かを判定し、同じトランザクション（トリガー）で通知を作る**。部分 UNIQUE（`deleted_at IS NULL`）が止めるのは「今有効な行」の重複だけで、解除後の再 INSERT は通る → 「初回だけ」を保証するのは履歴判定の方。再試行・同時実行・解除後の再登録で重複しないことは実装時に検証する（ASTRA 訂正 19:15）
- 履歴判定は **物理 DELETE 禁止（L1）が前提**。元テーブルの行を物理削除すると「初めて」に戻り、通知を再び作れてしまう
- 一覧は各束の**最新の出来事の時刻順**。未読を上へ寄せる並べ替えはしない
- 一覧を表示しただけでは既読にしない（開く / 既読にする操作で既読）
- タブ（すべて / 未読）の有無・既読履歴の見せ方は **mock が仕様**（正典に固定しない）

**罠**
- 「同じ日」で束ねる（ASTRA 初案）→ 0 時をまたぐと同じ盛り上がりが割れ、3 日ぶりに開くと同じ RIG が 3 行並ぶ
- 「対象ごとに全期間」で束ねる（Claude 初案）→ 読んだ分と新しい分の境目が消える
- 「未読だけ束ねる」だけでは、12 件の束を既読にした瞬間に 12 行へばらける実装も成立する（ASTRA 指摘）。`is_read` の真偽値では**どの操作で読んだか**が残らないので束を保てない → `read_at`
- 未読を上に固めると、既読にした行が突然下へ飛ぶ
- `last_seen_at` のような「前回見た時刻」をユーザー側に持って束ねの基準にしない（GPT）。基準は通知行自身の `read_at`

## D3 ログイン方法の案内（救済）

- **独立したログイン方法が 1 つだけ**の場合に、別の方法を足すよう**軽く案内**する（19:06 ASTRA 指摘で修正）
  - 数え方: つながっている方法を数え、**メールログインのアドレスが Google のアドレスと同じなら、その 2 つは 1 つとして数える**（Google アカウント＝その受信箱なので一緒に失う）
  - 例: Google だけ → 案内 ／ Google ＋ 同じアドレスのメール → 案内 ／ Google ＋ Facebook（＋同じアドレスのメール）→ 案内しない
  - Facebook とメールのアドレスが同じことは、同じ依存として扱わない（Facebook の失効と受信箱の喪失は別物。根拠なし）
- メールは追加候補の 1 つで**必須ではない**。連絡専用メールの欄は作らない（メールログインに一本化）
- メールは、コードの確認後に**追加前と同じ MyRIG ユーザー（同じ `auth.users.id`）としてメールログインが成立する**ことをサーバー側で確かめた時点で「ログイン方法」として数える。ユーザーにログアウト → 入り直しはさせない。単なる「メールアドレス変更の確認」と区別する。OAuth が返したアドレスを持っているだけでは数えない
- **表示の規則: `auth.identities` に実在する identity だけを「ログイン方法」として出す**（GPT 19:15）。Google の identity_data にメールアドレスがあることと、メールでログインできることを混同しない。D3 の「Google と同じアドレスのメールは 1 つと数える」も、**email identity が実在する場合だけ**
- 「最後に使った日」は **各 `auth.identities.last_sign_in_at`**（方法ごと。`auth.users.last_sign_in_at` はアカウント全体なので使わない）。公式に定義あり・実環境での取得と更新は未検証。取れない時は出さない（日付を作らない）。控えめな補助情報で、古いことを「使えない」と判定しない
- ⚠️ **要確認（実装前・テスト環境）**: 次の 3 つを同じ検証で確かめる（ASTRA 19:15）
  1. Google で作ったユーザーに、同じアドレスでメール OTP（新規ユーザー作成は無効）を送ると届くか・コード検証後に**同じ `auth.users.id`** のセッションになるか
  2. そのとき email identity が作られるか（作られれば上の表示規則で自然に「メール」の行に出る）
  3. email identity を外した後も、`auth.users.email` 宛ての OTP でログインできてしまわないか（できるなら「メールログインを解除しました」とは表示できない）
  - 経緯: Claude が「automatic linking で Google 登録者は同じアドレスのメールログインが通るかも」と書いた → GPT は公式の「OAuth 登録済みのアドレスで email サインアップすると曖昧な応答になり確認メールは送られない」を根拠に撤回を提案 → ただしその一文は**サインアップ（新規作成）の話で、既存ユーザーへの OTP ログインの話ではない**（Claude）。どちらも推測なので、テストで決める
  - mock ではこの仮定の状態を作らない（表示規則が identity の実在だけで決まるので、検証結果がどちらでも画面は壊れない）
- 方法が複数あっても「安全」「復旧を保証」とは表示しない。警告色を常時出さない

**罠**
- 「確認済みメールが無い人に警告」（Claude 初案）→ メールを持たせることを安全策の代わりにする思想になり、Auth D3「必要な個人情報だけ」とずれる（GPT 指摘）。Google ＋ Facebook の 2 つがある人に不要な要求をする
- 「方法の数」だけ（GPT 案）→ Google と同じ Gmail でメールログインを足すと、その Gmail を失えば両方失う（ASTRA 指摘）
- 「メールのアドレスが Google / Facebook と同じなら案内」（Claude 確定案の初稿）→ Google ＋ Facebook ＋ 同じアドレスのメールという 3 方法の人にまで追加を勧めてしまう（ASTRA 指摘 19:06）→ 条件を「独立した方法の数」に直した
- メールアドレスの比較だけでは本当の独立性は判定できない（別アドレスでも同じ受信箱かもしれない）→ **独立性を採点する機能は作らない。軽い案内に留める**（ASTRA）

## D4 退会・復帰

- 論理削除済みの `profiles` を持つ人は、**Onboarding へ送らない・自動で復帰させない**。ログイン後の専用画面で本人が「再開する」を選んだ時だけ `deleted_at` を戻す。「再開しない」はログアウト
- **username は他人へ再配布しない**（古い投稿 URL・ガレージ URL・外部リンクのなりすまし防止。後から変えるコストが大きい）
- 未決（退会画面を作る時に決める）: 復帰期限 / 期限後の保持・匿名化 / 退会中の公開範囲 / 他人の投稿に残るコメントの扱い。**「30 日」を画面の文言で先に約束しない**
- auth-guard-spec v1.3 §4.3 判定順 ①「特別扱い（PENDING）」の中身は本裁定の骨格。仕様書側の改訂は退会画面を作る時にまとめて行う

## D5 通知設定を MVP に含める（2026-09-28 20:30 イタヤ裁定で改訂）

- 設定「利用設定 → 通知」: **MyRIG 内の通知 全体 ON/OFF ＋ 種類ごと（いいね / お気に入り / コメントと返信 / フォロー）**。初期値は全部 ON
- 全体 OFF の間は**新しい通知を作らない**。過去の通知は消さない・勝手に既読にしない。ON に戻しても OFF 中の分を遡って作らない（通知は活動の正本ではない。いいね等は元テーブルに残る）
- 全体 OFF でも種類ごとの値は保つ（ON に戻せば元の選び方に戻る）
- ⛔ 出さないもの: メール通知 / Push / ブラウザ通知 / 頻度・まとめ・時間帯（存在しない配信経路を画面で予告しない）
- 将来の運営・セキュリティ上の通知はこの設定に巻き込まない（別の責務）
- 保存先: `notification_settings`（1 ユーザー 1 行）。**行が無い = 全部 ON**（登録時に行を作らない・既存ユーザーの移行が要らない）→ schema v1.6-r8
- ⚠️ 初回だけ通知（D1）との関係: OFF の間に起きた「初めてのいいね」は、その後 ON にしても通知されない（初回を使い切る）。仕様として受け入れる

**D5 の補足（21:24 / D7）**: お知らせ（全員宛て）の ON/OFF を 1 行足す。全体スイッチはアクティビティとお知らせを止めるもので、重要なお知らせは止まらないと必ず書く。

**失効した旧 D5（20:30）**: 「MVP では通知設定ページを作らない（アプリ内だけで止めたくなる理由が少ない・まず全種類を届けて要否を確かめる）」
- なぜ失効: 設定が無いと「MyRIG が決めた通知を全員が同じ条件で受け取る」ことになり不親切（イタヤ）。**MVP は実装範囲を最小にすることで、考えるのを後回しにすることではない**（イタヤ・プロジェクト初期からの方針）。
  Claude・ASTRA・GPT の 3 者とも「MVP だから削る」に寄っていた。罠として残す

### D6 ブロック・ミュートを MVP に含める
- **ブロック**（ミュートを含む強い状態）: 相手は自分の投稿に コメント・返信・いいね・お気に入り・フォローができない。相手由来の新しい通知を作らない。**既存のフォローは両方向とも論理解除し、ブロックを解いても自動で戻さない**
- ⛔ ブロックは公開 Web の閲覧を止めると約束しない（ログアウトすれば見える。偽の安心にしない）。見られたくない人には「ガレージの非公開」を案内する
- **ミュート**（相手には分からない）: Feed から除く / **相手からの新しい通知を作らない**（作って隠すと、解除した瞬間に古い通知が大量に戻る）/ 自分の投稿に付いた相手のコメントは畳む（「ミュート中のユーザーのコメント」）/ 検索・Library・公開ガレージの直接表示では除かない（自分で探したものは見せる）
- 設定: 新グループ「**プライバシーと安全**」→「ブロック・ミュート中のユーザー」。入口は相手の公開ガレージとコメントの「…」
- 保存先: `user_blocks` / `user_mutes`（schema v1.6-r8）
- 罠: GPT 初案は「ミュートは Feed・検索・おすすめへの効き方を一緒に設計しないと中途半端 → 後回し」。これは「考えていないから後回し」の形。範囲はこの場で決められた

### D7 通知は画面で 3 種類・データは 2 系統
| 画面 | 中身 | 設定 |

### D8 退会（30 日の猶予 → 確定処理）
- **退会の手続き**: 本人確認 → 影響の説明 → 明示の確認 → `profiles.deleted_at = now()`。ログアウト
- **公開の止め方 = 持ち主のプロフィールを親の門にする**: 公開の RIG・パーツ・LOG・画像・コメント・関係（いいね等）・件数は、**それ自身が有効 かつ 持ち主の profile が有効（`deleted_at IS NULL`）** のときだけ出す（RLS / 集計）

- **30 日以内**: ログインすると「再開しますか？」の専用画面（Onboarding へ送らない・自動で戻さない）。再開 = `profiles.deleted_at = NULL` だけ（子の状態は触らない）
- **30 日を過ぎたら確定処理（元に戻せない）**:
  - プロフィールの個人情報を匿名化（表示名・自己紹介・国・地域・サイト・SNS・興味など）。アバター・カバーは実ファイルを消し URL を外す
  - 投稿（RIG・パーツ・LOG）の行は FK と履歴のために残すが、**本人が書いた自由入力と個人情報性のある値（説明・本文・メモ・外部リンク・購入先など）は NULL / 空へ**。投稿の画像は実ファイルを消し、画像の行は論理削除
  - ほかの人の投稿へのコメント: `status='withdrawn'`・`body=''`。画面が「退会したユーザーのコメント」と描く（システム文言を本文に保存しない = 英語版でも同じデータから描ける）。`parent_id` は残す（返信の流れを保つ）。本人削除の `deleted` とは別の値（見せ方が違う）
  - Auth: **ソフト削除（`auth.admin.deleteUser(id, shouldSoftDelete=true)`）を確定処理のときだけ**行う（元に戻せないので猶予中はしない）。`auth.users.id` は残る → `profiles.id` の FK は壊れない。メール・識別子の難読化は upstream 実装で確認済み（GPT）・**本番前に非本番環境で 1 件実測**
  - ユーザー名: 元の名前は残さない。**正規化したユーザー名のサーバー秘密鍵 HMAC** を予約表 `username_reservations` に入れて再利用を止める（素のハッシュは候補が少なく辞書で戻せる）。`profiles.username` は `withdrawn-<ランダム>`（内部 ID を出さない）
- 罠: Claude 初案「Auth を完全削除」は `profiles.id → auth.users.id` の FK で匿名化した profiles 行ごと消える（Claude 指摘）→ ソフト削除
