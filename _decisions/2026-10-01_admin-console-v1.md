# MyRIG 管理画面（Admin）設計仕様 v1.0

## 1. 目的と原則
- 管理画面は MyRIG 運営の肝。運営の仕事を流す仕組みとして作る（機能の寄せ集めにしない）
- 運営者はイタヤ 1 人。軽く・速く・事故を起こさない
- 設計は完成形、実装は MVP で外す（CORE L1）
- Admin Home =「今日やること」。何も無い日がいちばん良い
- 呼ぶのは管理画面の外から（非常ベル）
- AI は判断しない。下調べと下書きだけ
- 取り消せない操作は 2 段階・理由・記録。解除は設定より慎重に
- 停止（制裁）と保全（保存の根拠）を混ぜない
- 管理画面を唯一の非常口にしない（Upstash・DNS など外の手順を残す）
- 運営のデータも個人情報を最小に（本文を写さない・保存期間を持つ）

## 2. 決定一覧
- A-1 端末は PC（1280px 以上）。Mobile は緊急の確認と「一時非表示・一時停止」だけ（/admin/m）
- A-2 カテゴリ色を使わず、状態（要対応・期限切れ・急ぎ）を主役に
- A-3 App 側にある Master の同期コピーは直接編集しない。Master は管理アプリの Catalog 区画で Research の正本を直す
- A-4 管理者はイタヤ 1 人。権限の分割は将来。2 段階認証・操作の記録・危ない操作の前の再確認は最初から
- A-5 作る前に文字の設計図で詰める
- A-6 設計は完成形・実装は MVP で外す
- Q1 中核 = Case / Job / Audit。子表（受付のつながり・期限・送受信）・保全・ベルの記録を別に持つ
- Q2 非常ベル = 件名に「緊急」のメール。中身は理由の区分・対象の種類・#ID・/admin/m の入口だけ。2 つ目の経路は R7 で比べる
- Q3 停止中の人が退会しても 30 日の確定処理は止めない。必要なデータにだけ保全をかける
- Q4 メンテナンス中も管理アプリは使える（別配置で解決）
- Q5 Task Package（AI への手渡し）は MVP の後（B）。形は本書で決める
- Q6 Master が入っても利用者の Custom を自動で紐付けない。候補を持ち、本人が編集時に選ぶ
- Q7 Home の 1 行はお知らせの 1 項目（B）。120 と 125 の 2 本の関係は Home レーンで先に裁定
- Q8 申し立ての資料（ファイル）は MVP では受け付けない（URL と説明だけ）
- Q9 操作の記録（Audit）の保存期間 = 5 年（本文は写さない）。法務の確認事項 R2 に足す
- Q-K1 管理アプリを 1 つ新しく作り（App 区画 ＋ Catalog 区画）、利用者のサイトと別に置く（例 admin.myrigrc.com）
- Q-K2 A-3 の言い直しを採用
- Q-K4 投稿の管理（通報が無くても探す・開く・非表示）を MVP に入れる
- Q-K5 → **§11 で確定**（提携が有効なお店の購入先だけ・PR 強制・Library Detail と RIG ベースモデルだけ）
- 既存の Research アプリ（rc-master-data-app-v2）は使わない。参考だけ（イタヤ 16:33）

## 3. 構成
- 管理アプリ 1 つ・利用者のサイトと別の配置。ログインは App の Supabase Auth ＋ 2 段階認証
- App 区画: App の DB を扱う
- Catalog 区画: Research の DB（Master の正本）を扱う
- 2 つの DB をまたいで JOIN しない。区画ごとにデータ層と鍵を分ける
- 橋（Research Bridge）: App → Catalog = Master に無いもの・表記の揺れの候補・誤りの報告・0 件の検索語／Catalog → App = 同期
- 書き込みはサーバー側の操作ごとの狭い関数だけ。何でも通る service role の窓口は作らない。物理 DELETE なし（例外はストレージの実ファイル）
- 管理者の判定 = Auth の app_metadata。運営者は通常の退会・停止の対象外。運営者 ID の正本は r12 で決める

## 4. データの形（r12 で設計・名前は案）
- admin_cases: 案件（種類・優先度・状態・対象・決定・内部メモ）。状態の正本
- admin_case_sources: 案件 ↔ 元の受付（通報 3 表・お問い合わせ・リンク承認など）。(種類, ID) を一意。論理参照（元が消えても画面は落ちない）。ここに無い受付 = 未着手
- admin_case_deadlines: 期限ごとに 1 行（制度・数え始めの事実と日時・暦日 / 営業日・期限・届いたか）。日数は焼かない
- admin_case_events: 送った文（そのまま）・受けた返事・状態の変化
- admin_jobs: 非同期で失敗しうる処理だけ（退会の確定・保存期間・書き出し・メール・再送）。冪等・再開可・二重実行させない
- admin_alerts: 非常ベルを鳴らした記録（届いたか・確認したか・重複止め）
- admin_audit_log: 追記だけ。誰が・いつ・何を・どの行に・理由の区分・結果。5 年
- legal_holds: 範囲つきの保全（どの表・行・列・理由・見直し日・解除者と理由）
- 停止の状態: auth-guard が直接読める現在の状態（状態・理由・期限・誰が）
- 運営の非表示: 投稿・コメントに、利用者の公開設定とは別に持つ

## 5. 領域と MVP 区分（A = 公開時 / B = 早め / C = 規模・収益が出てから / D = 作らない）
- Operations（今日やること・期限・処理の失敗・費用と上限）: A
- Content（全投稿を探す・開く・非表示）: A ／ 注目に選ぶ・一括: B
- Moderation（通報 3 表・プロフィールの処置・スパムの一括処置・個人サイトのリンク承認・画像は親ごと非表示）: A ／ 画像 1 枚だけの処置: B
- Rights / Legal（権利侵害・緊急・違法・7 日の照会・開示請求・書面・漏えいの最小手順）: A ／ DMCA: C
- Support（お問い合わせ・異議・救済・運営者情報の請求）: A（本人確認の手順は法務 HOLD）
- Users（探す・全体像・停止と解除・13 歳未満・登録取り消し）: A ／ 予約語: B ／ 公式アカウント認証: C
- Data Lifecycle（退会の確定・保存期間・保全・書き出し・未完了登録・運営データの期限）: A（書き出しは本人確認済みの案件からだけ）
- Publishing（お知らせ・文のひな形）: A ／ Home の 1 行・規約の画面: B
- Page Composer（ウィジェットの足し引き・並べ替え・カードの型・並べ方・プレビュー・予約・戻す。自由 HTML なし）: B
- Catalog（Master・別名・画像と許諾・調査の依頼と指示書）: B（許諾の記録は R9 で A）
- Commerce（アフィリエイトリンク: B〔Q-K5 次第で A〕／キーワードとの結びつけ・企業 / 有料バナー・AdSense の枠・広告の表示ルール: C。広告・PR の表示は必須）
- 検索の調整（0 件の言葉の記録: B ／ 同義語・優先: C）・サイトの設定: B ・SEO・i18n・Analytics・企画: C
- Security / System（2 段階認証・操作の記録・処理・費用・締め出しからの復旧手順）: A ／ 独自の異常検知・縮退の切り替え画面・記録の検索画面: B

## 6. 非常ベル
- 鳴らすもの: 緊急の申し立て／退会・保存期間の処理の停止／管理者ログインの異常／漏えいの疑い／費用 100%
- 載せない: 本文・名前・メール・対象の URL・画像・利用者が書いた文

## 7. 軽く速く
- サーバーで組み立てる・大きなグラフや常時更新なし・一覧は必ずページ分け・件数は軽く数える・リアルタイムなし・画像は縮小版・利用者のサイトとコードを分ける・キーボード操作

## 8. 公開前に要るもの（管理画面の外）
- 緊急時の外の手順（Upstash・DNS・各サービス）・管理者の締め出しからの復旧手順・ベルが届くかの試験・画像の配信を止める方法（G21）

## 9. 残っている抜け（r12 / 他レーン）
- G1 停止の状態の保存先／G6・G15 運営の非表示（投稿・コメント）／G7 退会と対応中の連絡先／G8 退会で NULL にする列の一覧／G9 r12 候補／G10 修正報告の付け替え／G11 page_blocks の作り直し／G14 運営の処置の通知の語彙／G16 運営者 ID／G18 Home の 1 行（Home レーン）／G21 画像の URL／G23 予約語／G24 広告表示／G25 0 件の検索語／G26 表記の揺れの受け渡し

## 11. 追補 v1.1 — Page Composer / Commerce / Research Bridge（イタヤ 2026-10-01 16:52）

元: `_proposals/2026-10-01_admin-composer-commerce-bridge_claude-v0.4.md`（GPT 確認済み）。**すべて推奨どおり。補正 2 点つき**

- Q-P1 `page_blocks` を作り直す → `page_layouts`（ページ × 版・draft / scheduled / published / archived・プレビュー・前の版に戻す）＋ `page_layout_blocks`（棚・layout_type・card_variant・query_preset・params・棚ごとの starts_at / ends_at）
- Q-P2 部品の種類は**現行のレジストリを 7 種類で始める**（content_shelf / manual_pick / feature_banner / editorial_banner / library_links / announcement_slot / ad_slot）。**永久に固定ではない**。新しい block_type は**コード側のレジストリへ明示的に足したときだけ**増やせる（管理画面から作れない）。自由 HTML なし・ランキング系のプリセットなし・「注目に選ぶ」は選んだ順のまま
- Q-C1 購入先は表示のときにサーバーで引く。転送 URL は提携先の規約を確かめるまで使わない
- Q-C2 検索結果の広告は MVP では 0
- **Q-K5 公開時に購入先を出す**: 提携が「有効」なお店の購入先だけ／PR 表示は部品で強制（消す設定なし）／**Library Detail と RIG のベースモデルだけ**／提携前・不確実・リンク切れ（broken）は出さない。公式サイトは INFO として別枠で出せる
- Q-B1 橋は片方向 2 本（App の候補 → Research の依頼 → Research の Master → App へ同期）。依頼の状態は Research 側だけが持つ
- Q-B2 0 件の検索語を、利用者を特定しない形（言葉と日ごとの件数）で残す。**保存期間は Audit の 5 年と同じにしない**。利用の傾向のデータとして、運用に要る期間を別に決める（法務の確認の対象には含める・期間は後で決める）

これで MVP 区分は: 購入先（commerce_merchants / commerce_offers ＋ PR を強制する部品）= **A** ／ Page Composer の画面 = B（MVP はコードの既定の編成）／ キーワード・バナー・AdSense = C ／ 橋の候補と依頼 = B ／ **同期の方式 = MVP までに必須**
