## 1. 🔴 fixture値をURLの有効語彙に使うと、正当な条件を壊す

**踏んだ事故**

Facetの選択肢を「いまのデータに実在する値」から生成していた。それ自体は正しい。
問題は、**同じ集合を「URLとして有効な値か」の判定にも使ってしまった**こと。

その結果、検索トップが正典どおり出す `トラックトライアル`（rig_categories 24値の1つ）を選んでも、
結果ページが「知らない値」と判定して**条件ごと解除**していた。
`アクセサリー・電飾`（part_categories 親14の1つ）も同じ。

「未知値は解除＋通知」という規則自体は正しい。**未知の定義が間違っていた。**

**原則**

> **canonical vocabulary（正典語彙）と fixture存在値は別物。分けて持つ。**
>
> | 判定 | 使うもの | 結果 |
> |---|---|---|
> | 値として正しいか | 正典語彙 | 正しければ**保持** |
> | 今回ヒットするか | 実データ | 0件なら**0件と表示** |
>
> - 正典上有効だが0件 → **条件を保持して0件表示**（選択肢にも出して解除できるようにする）
> - 存在しない/旧語彙/壊れた値 → **解除して通知**
> - 判定できない軸（`manufacturer` のようにマスターがResearch所有で手元に無いもの）
>   → **解除せず保持**する。判定不能を無効と扱うと正当な指定まで消える

**なぜ実装で再発するか**

Next.js でも「選択肢はDBから引く」を書いた瞬間、同じ集合をバリデーションに流用したくなる。
検索インデックスに1件も無いだけのカテゴリが、URL共有した先で黙って消える。

## 2. 🔴 `q` が表示だけで、実結果に効いていなかった

**踏んだ事故**

自由語 `q` は、見出し・ハイライト・URL・`document.title` を更新していた。
しかし結果抽出（`filteredItems()` / `buildBlendList()`）は type と facet しか見ておらず、
**`?q=TRX-4` と `?q=絶対存在しない文字列XYZ` で結果集合が同じ**だった。

フィルタ・ソート・ページャを直したあとで初めて目立った。
それまでは「検索できている」ように見えていた。

**さらに派生していた事故**

`q` を実 predicate にした直後、**件数計算の一部が `q` を通っていなかった**。
- PC `facetOptionCount()` … Facet横の件数だけ「検索語で絞る前の母集団」を数えられた
- Mobile の絞り込みシート内 `draftMatches()` … 「N件を表示」と各選択肢の件数が別母集団になり得た

**原則**

> **`q` は全検索計算の基底 predicate。**
> 適用先は 実結果 / 総件数 / 種別チップ件数 / Facet選択肢件数 / シート内preview件数 **すべて**。
>
> ```
> 実結果            = q AND 全active facet
> Facet選択肢件数   = q AND 他のactive facet AND 候補値（候補自身の軸だけ除外）
> シート内preview   = q AND draft facets
> ```
>
> 一箇所でも通し忘れると、画面のどこかに**別宇宙の数字**が出る。

## 3. 🔴 UI状態だけ変わって、実データが変わらない

**踏んだ事故（3種類）**

| 箇所 | 症状 |
|---|---|
| ソート | 「いいね順」「装着例が多い順」が選択肢として存在するのに、並び替え処理が無く順序が変わらない |
| ページャ | `page=2` で URL・現在地・「31〜54件」表示は変わるが、**表示カードは全件のまま** |
| 絞り込み | Library・Feed・ガレージ一覧のチップは `is-active` が付くだけで結果が変わらない（検索外・未修正） |

いずれも「クリックできて、見た目が反応する」ので、**操作テストでも通ってしまう**。

**原則**

> **PASS条件は「状態が変わったか」ではなく「結果データが変わったか」。**
>
> 4段すべてを通って初めてPASS:
> `state が正しい` → `DOM が正しい` → `実際に見えるUIが正しい` → `操作後の結果データが正しい`
>
> ソートなら「並びが変わったか」ではなく **その指標の降順になっているか**を実値で見る。
> ページャなら「現在地が動いたか」ではなく **カード集合が分割されているか**を同一性キーで見る。

## 4. 🔴 `hidden` 属性が CSS の `display` に負け、透明な当たり判定が残る

**踏んだ事故**

`.sfbar`（検索トップの条件バー）は `display: flex` を持つ。
`hidden` 属性は UA スタイルシートの `display: none` にすぎないので、**クラス指定に負ける**。

結果、条件が0件で「非表示」のはずの状態でも画面下端に見えない板が残り、
**クリックを横取り**していた。メーカー軸を開くタップが通らなかった。

同型が `.rc`（検索履歴行）、`.srch-empty`、`.srch-filter-backdrop` にもあった。
2026-08-20 の `.sfbar` 導入時からの潜在バグ。

**なぜ見つからなかったか**

- DOM上は `hidden` → DOM検査で異常なし
- 静的解析でも `hidden` → 差分レビューで異常なし
- スクリーンショットにも写らない → 目視で異常なし
- **実際にクリックして初めて出る**

**原則**

> `hidden` 属性で表示制御する要素には **`[hidden] { display: none }` を必ず併記する。**
> もしくは表示制御を `hidden` 属性ではなくクラスへ統一する。**混在させない。**
>
> 検証には**実操作**を含める。`elementFromPoint` で
> 「`hidden` な要素が当たり判定を持っていないか」を機械的に確認できる。

Search外の同型候補は `myrig-mockup` の `docs/WEB_GRAMMAR_QUEUE.md` に列挙してある。

## 5. 検証のやり方（L1）

Searchで実際に効いた検証手順。後続の面でも同じやり方を使う。

1. **同じ生URL文字列をPC/Mobileへ投入する。** テスト側で語彙を正規化して差を隠さない
2. **件数の一致は求めない。** モックのfixtureが別なので原理的に不可能。
   契約は「同じURLが同じ**意味**になること」
3. **可視UI全体を見る。** スコープを絞ったセレクタ（`#fsFacets` だけ等）で判定しない。
   実際にこれで、旧サイドバー全体が画面に出たままなのを1バッチ見逃した
4. **`pageerror` / `console.error` を収集する。** スコープ事故はこれでしか出ない
5. **FAILが出たら、まずテストを疑う。** Searchでは「FAIL」の約半分がテスト側の前提誤りだった
   （カード名の重複を無視した同定、fixtureの性質を踏まえない期待値、
   スコープの違うセレクタ、仕様変更に追随していない旧assert）

**恒久的なassertにしてはいけないもの**

- 「Facet option count ≤ 現在の結果件数」
  → 同じ軸に既に選択がある場合、その軸自身を除外して数えるので**超えるのが正当**。
  期待値は `q AND 他のactive facet AND 候補値` から動的に算出する

## 6. 推測で埋めない（再確認）

Searchで実際に「テストを通すために意味を作り替えかけた」事例。

- `Scale` / `Scale Trail` は `build_tags` の値であって `rig_categories` ではない。
  対応する車種カテゴリが特定できないので、**近い値へ寄せずNULL相当のままにした**
- LOG のメーカー派生は、表示ラベルの部分一致ではなく**明示的な関連属性**から導出する。
  一致しないものは未紐付け（NULL）として扱う
- `manufacturer` の表記ゆれ（`TAMIYA`/`Tamiya`、`Vanquish`/`Vanquish Products`）は
  **大小文字無視・部分一致・独自aliasで救わない**。Research 正本の取得待ちHOLD

> 検証を通すために値を作ると、**モックが嘘をつく**。
> 嘘をついたモックは、実装時に「仕様どおり作ったのに動かない」を生む。

## 7. 正典化しないもの

CORE「正典化判断基準」に従い、以下はここにも `search-page-plan-v2.md` にも書かない。

- 表示件数・カード位置・カードサイズ・余白・シート高さ・通知の位置
- Library棚を何件目に差し込むか
- ダミーデータの中身

これらは実装とコードコメントに置き、モックを触りながら決める。
