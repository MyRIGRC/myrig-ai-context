## この記録で残す罠

1. **entity の対称性でナビを設計すると沼にはまる。** 押したくなるかで決める（§1）
2. **ラベルに定義を全部しゃべらせない。** 厳密さは押した先が担う（§5）
3. **DBで辿れない関係を名乗らない。** `パーツのLOG` は現行スキーマでは作れない（§4）
4. **件数を面ごとに手打ちしない。** 定義が無いと総数が置きっぱなしになる（§6）
5. **実測値がおかしい ≠ 構造がおかしい**（§2 の Cowork 誤診）

## 0. 何が起きたか

`revision 036` で PC Browse V5 を CLOSE したが、実画面レビューで
**ローカルナビのラベルが「そのRIG・パーツ・LOGが何を基準に集まっているのか」を
説明していない**ことが判明した。CLOSE を限定的に再オープンする。

再オープンは **「ローカルナビの構成・意味・表記」と「Root current の見せ方」だけ**。
WORLD selector / Root entry 文法 / Breadcrumb / Directory / 表札 / 色 / 基準画面は**凍結**。

症状:

- PARTS 面で `RIG` を押すと「そのパーツを装着しているRIG」が出るが、ラベルからは分からない
- RIG 面の `パーツ` に何を出すべきかが決まっていなかった
- 関係で絞られていない件数が放置（Rock Crawler の LOG = 3,241、
  モーター・ESC の RIG = 3,241。どちらもグローバル総数）
- 是正の過程で `装着RIGのLOG` まで作り、今度は**ナビが重くなった**

## 1. 🔴【L1】全面共通の「4軸」は失効。面ごとに本数が変わる

**036 の「4軸はページによって出たり消えたりしない」を明示的に失効させる。**
無理に対称化したことが沼の入口だった。**全部を同じナビ構造にしなくてよい。**

| 面 | スコープ | ローカルナビ |
|---|---|---|
| すべてのRCカー（RIG ROOT） | RCカーWORLDの全RIG | **トップ / RIG / LOG** |
| Rock Crawler（RIG CATEGORY） | Rock CrawlerのRIG | **トップ / RIG / パーツ / LOG** |
| すべてのパーツ（PARTS ROOT） | RCカーWORLDの全パーツ | **トップ / パーツ / LOG** |
| モーター・ESC（PARTS CATEGORY） | モーター・ESCのパーツ | **トップ / パーツ / LOG** |

**WORLD ROOT（HOME）にはローカルナビを置かない**（V5 §6 のまま）。

### 判断基準は「押したくなるか」

entity の対称性ではない。

| | 性質 | 置き場所 |
|---|---|---|
| **LOG** | **閲覧モード。** その場所に関する活動・経験を見る | **全面のナビに常設** |
| RIG↔PARTS 相互参照 | **発見コンテンツ。** 眺めて気づくもの | **必要な面だけ。原則は棚** |

**LOGだけ全面にあってよい理由:** LOG は別entityを横断しに行くのではなく、
**いまいる場所に関する活動を見る**もの。「Rock Crawlerに関するLOG」
「モーター・ESCに関するLOG」はユーザーの言葉として直感的で、押す動機がある。

**相互参照を主ナビから外す理由:** `すべてのパーツ → 装着RIG` `すべてのRCカー → 使用パーツ` は
関係として正しくても、**主ナビとして押したくなる概念ではない**。棚で十分。

### 軸化の基準は階層差ではなく「閲覧需要の非対称性」

Rock Crawler も モーター・ESC も**どちらも Category**。階層は同じ。
分かれるのは**大量に閲覧したい需要があるか**。

| 方向 | 需要 | 置き場所 |
|---|---|---|
| **RIG Category → PARTS** | 「どんなタイヤ・ESC・サーボが使われているか」を**大量閲覧したい** | **軸** |
| **PARTS Category → RIG** | 参考・発見が中心（モーターを積んだRIGはほぼ全部になる） | **棚** |
| **ROOT 同士の相互参照** | 大量閲覧軸としては弱い | **棚** |

**構造的な対称性で軸を決めない。** その方向に大量閲覧の主要目的があるかで決める。

**Root は構造上の Hub。** `すべてのRCカー` / `すべてのパーツ` は超重要な目的地ではない。
あれもこれも機能を持たせなくてよい。

## 2. 🔴 判断が二転した経緯（そのまま残す）

同じ「ROOT から相互参照軸を外す」という結論に、**別の理由で二度たどり着いている**。
理由の質が違うので、両方残す。

### 2-1. Cowork 提案（不採用）— 理由が間違っていた

> 「すべてのRCカーの `パーツ` ≒ すべてのパーツROOT で母集団が退化する」

**却下。母集団は退化しない。** `rig_parts` があるので

- すべてのパーツ = 登録されている全パーツ
- RIG ROOT の使用パーツ = 公開RIGに `rig_parts` で紐づくパーツ（**真部分集合**）

**誤診の性質:** fixture の件数がすべてグローバル総数だったのを見て
「構造的に退化する」と結論した。実際は**定義が無いから件数が総数のまま置かれていた**だけで、
原因と結果を取り違えていた。`rig_parts` の存在を正典で確認せずに一般化したのが直接の原因。
**「実測値がおかしい」は「構造がおかしい」の証拠にならない。**

### 2-2. イタヤ裁定（採用）— 理由が正しい

母集団の話ではなく、**主ナビとして押したくなるか**で判断した（§1）。
結果として ROOT の相互参照軸は外れたが、**外す根拠がまったく違う**。
外れても関係ビュー自体は消えず、**棚として残る**。

## 3. スコープと関係の定義【L1】

`rig_parts.removed_at IS NULL`（＝**現在装着中のみ**）を関係条件とする。
過去の装着は含めない。必要になったら「使用履歴」等の別概念として扱う。

| 軸 / 棚 | 定義 |
|---|---|
| RIG | scope内のRIG数 |
| パーツ（Rock Crawler ではナビ / 他面は棚） | scope内RIGに `rig_parts.removed_at IS NULL` で結合する **DISTINCT `part_id`** |
| LOG（RIG系） | scope内RIGの `rig_id` に**直接**紐づく **DISTINCT log**。棚見出しでは `RIGのLOG` |
| パーツ | scope内のPARTS数 |
| 装着RIG（棚） | scope内PARTSに `rig_parts.removed_at IS NULL` で結合する **DISTINCT `rig_id`** |
| LOG（PARTS系） | 上記「装着RIG」の `rig_id` に紐づく **DISTINCT log**。棚見出しでは `装着RIGのLOG` |

## 4. 🔴【L1】関係を名乗るときは、DBで辿れる経路だけを名乗る

正典 `docs/schema/myrig_db_schema_v1_6.md` の現物確認:

| テーブル | 事実 |
|---|---|
| `rig_parts` | `rig_id` / `part_id` / `installed_at` / **`removed_at`**。RIG↔PARTS は**明示的関係** |
| `maintenance_logs` | `rig_id`（FK→rigs, **NULLABLE**）。**`part_id` は無い** |

したがって **PARTS → LOG は直接関係ではない。**
辿れるのは `パーツ → 装着RIG → そのRIGのLOG` の2ホップまでで、
そのLOG本文が当該パーツについて書かれている保証はない
（そのRIGの走行LOGまで拾ってしまう）。

| 表記 | 可否 |
|---|---|
| パーツのLOG / モーター・ESCに関するLOG | ❌ **現行スキーマでは作れない** |
| 関連LOG | ❌ 根拠をぼかす語 |
| **装着RIGのLOG** | ⭕（棚見出しで名乗る） |

`maintenance_logs.rig_id` は NULLABLE なので、RIG系の LOG も常に部分集合である。

### 🔴 PARTS系の LOG軸 — UIは採用、データ取得は PENDING【L1】

> **PARTS系の LOG軸は UI/UX として採用する。**
> 意味は **「当該パーツ／パーツカテゴリについて記録されたLOG」**。
> ただし現行DBでは直接関係を表現できないため、**実データ取得方式は PENDING**。
> **`装着RIG → そのRIGの全LOG` を代替して「関連LOG」と偽装しない。**

モーター・ESC を装着したRIGの「今日は河原を走った」というLOGまで拾ってしまう。
それは**モーター・ESCのLOGではない**。

**Cowork は現行の `rig_parts → rig → 全LOG` で勝手に実装しないこと。**
モックで面を見せる必要がある間は、棚を `装着RIGのLOG` と正確に名乗り、
**「パーツのLOGは未モデル化のため、暫定で装着RIGのLOGを置いている」ことを画面上にも明記する。**
名前を `関連LOG` などへ丸めて正体を隠さない。

### 🔵 PENDING — パーツに直接紐づくLOGを実現するApp側関係モデル

**これはUI案を捨てる理由ではなく、App側データモデルに必要な機能が見えたと考える。**

候補: `maintenance_logs ↔ maintenance_log_parts ↔ parts` の**多対多**。
1つの整備LOGで「ESC交換 / モーター交換 / ピニオン変更」を同時に扱うことがあるため、
`maintenance_logs.part_id` 1本より中間テーブルの方が筋がよい。

実現すれば

- 「パーツ」のLOG = 何らかのパーツに**明示リンク**されたLOG
- 「モーター・ESC」のLOG = Motor/ESCカテゴリのパーツに明示リンクされたLOG

が本当に作れる。**UIとは分離し、Appスキーマ検討事項として別途扱う。**
それまで「パーツのLOG」へ昇格させない。

> **PENDING（別件）**: `maintenance_logs.rig_id IS NULL` のLOGは、
> RIG起点Browseのどの軸からも到達しない。
> 「RIG非紐付けLOGのBrowse上の発見経路」として別途扱う。

## 5. 🔴【L1】ナビは「何を見るか」だけ。厳密な関係は押した先で説明する

**ラベルに定義を全部しゃべらせない。**

| 場所 | 役割 |
|---|---|
| ローカルナビのラベル | **何を見るか**だけを短く示す |
| 押した先の棚見出し・サブ・表札 | **どういう関係で集まっているか**を厳密に説明する |

押した先の例:

> **装着RIGのLOG** / このパーツを現在装着しているRIGに紐づくLOG
> **RIGのLOG** / このスコープのRIGに紐づくLOG

これで内部の厳密な定義を保ったまま、**ユーザーに JOIN 図を読ませずに済む。**

### 却下したラベル候補

| 候補 | 却下理由 |
|---|---|
| `パーツ・使用中` | 「使用中」が**状態**に見える |
| `RIG・使用例` | 「使用例」が**実例紹介コンテンツ**に見える |
| `関連パーツ` / `関連RIG` / **`関連LOG`** | 「関連」は根拠をぼかす語（§4）。**字面が軽くなるからといって採らない** |
| `RIGのLOG` / `装着RIGのLOG` をナビに置く | **ナビとして重い。** `装着RIGのLOG` は1語に「装着」「RIG」「LOG」の3概念。押した先の見出しへ移した |

**採用: 素の `RIG` / `パーツ` / `LOG` のみ。ナビ側では関係を修飾しない。**
スコープは表札が示している。`RIG` を「全RIG」と読む人はいない以上、
LOG だけスコープを名乗らせるのは一貫性が無い。

## 6. 🔴【L1】関係件数を面ごとに手打ちしない

**症状:** 件数が PC 4か所（HTML 3ファイル ＋ `js/parts-category-demo.js`）に直書きされ、
関係で絞られていない値が放置されていた。
036 で扱った「visible 判定が5か所に分散」と**同じ形**である。

**規則:**

- **関係件数は1か所へ集約する。** HTMLごとに数字を散在させない
- 実DB値が無い間はモック集計値でよいが、**MOCK値であることをコード上に明記する**
- **同じ scope では同じ関係件数を返す**
- **使用パーツ ≤ 全パーツ** / **装着RIG ≤ 全RIG** を必ず満たす
- 主役軸の件数は Directory の同カテゴリ件数と**同じ出所から取る**

## 7. 同時に確定: Root current は Category current 文法へ統一

**036 の Root current 専用デザイン（全面の薄い帯 ＋ 下罫線の濃色化）は失効。**

`すべてのRCカー` / `すべてのパーツ` が current のときは、
`ロッククローラー` / `モーター・ESC` の Directory current と**同じ表示文法**にする
（文字サイズ / weight / 行高 / 左右 padding / 薄い角丸背景 / 左の neutral バー / 件数表示）。

**current 時に使わないもの:** Root専用の全面帯 / 件数前の縦罫 / 強い下罫線。
**非current 時の Root entry 文法は現状維持。**

Root であることは、`RIG` / `PARTS` 見出しの直下という位置、Directory の上という配置、
ページ上部の表札で既に伝わる。**current だけ別デザインにする必要はない。**

> **Cowork の設計判断の誤り（記録）:** 「Root entry の寸法を変えない」を最優先にした結果、
> Root current 専用の視覚言語を発明してしまった。**制約を守ることと、
> 既存の語彙を再利用することは別**で、後者を優先すべきだった。
> なお `.myrig-sidebar` は `overflow: auto` のため、左バーを内余白の外へ逃がす案は
> クリップされて成立しない（実測確認済み）。current 時に内余白を取るのが唯一の実装。

## 8. 引き継がれるもの / 失効するもの

**有効:**

- **036 の表示グループ裁定。** `RIG=rig+rig_master` / `PARTS=part+parts+part_master` / `LOG=log`。
  ナビの本数が面ごとに変わっても、**押したときにどの棚が残るかの規則は同じ**
- **基準画面 = Rock Crawler Category Top は変更しない**
- 036 の「チェッカーの原則【L1】」

**失効:**

- 「4軸はページによって出たり消えたりしない」（§1）
- 「Root と Category で文法は同じ。軸の本数は4面すべてで4本」（§1）
- ナビラベルの `使用パーツ` / `装着RIG` / `RIGのLOG` / `装着RIGのLOG`（§5。棚見出しへ移動）

## 9. 検査で塞ぐこと

`_audit/browse_sidebar_v5_check.py`:

- **ローカルナビが面ごとの定義どおり**（ラベル・本数・`data-view-link` の並び）
- **その軸を押したときに棚が空にならない**

- Root current が子カテゴリ current と同一の表示文法
- 関係件数の不変条件（`使用パーツ ≤ 全パーツ` / `装着RIG ≤ 全RIG` / Category ⊆ Root /
  Category が Root と同値の軸を持たない）

## 🔵 正典化しないもの（2026-08-30 / revision 037）

**文言・余白・表示件数などのUI調整は正典で縛らない。** 実装側で調整可能にしておく。

| 正典化する | 正典化しない |
|---|---|
| どの面にどの閲覧モード（ローカルナビ）が存在するか | 具体的な日本語ラベル（`トップ` `LOG` など） |
| 相互参照をナビにするか棚にするか | 見出し・説明文の言い回し |
| どういう関係を根拠に表示してよいか | 余白・表示件数・棚の並び順 |

後から `トップ` や `LOG` の語を変えたくなっても情報構造は壊れない。
**文言を磨くために構造を開け直さない。**
