## 3. 確定仕様

### 3-1. 標準検索の責務

**標準検索 = MyRIGコミュニティの投稿を探す。**

- 対象：RIG / パーツ / LOG
- 製品情報を探す → **Library の責務**
- 人を探す → **ビルダー探索の責務**（検索トップに入口）

判断根拠（イタヤ）: MyRIGはショップサイトではない。「双葉のサーボ」で検索したとき、
Libraryの製品エントリが100〜200件流れ込むと検索結果がカタログ化する。
同じ100件でも、ユーザー投稿100件は「作例が100個ある」で価値だが、
製品エントリ100件は「カタログの行が100個ある」でしかない。
みんカラ（愛車登録／パーツレビュー／整備手帳＝RIG/パーツ/LOG）と同じ性格であり、
製品情報は投稿を成立させる裏方であって表に出す答えではない。

### 3-2. コンテンツタイプ

```
[すべて] [RIG] [パーツ] [LOG]
```

- 初期状態は「すべて」
- **「すべて」は独立した状態ではなく、3種すべてONかどうかの計算値**
- 「すべて」から個別を押す → その種別だけに絞る（3つから1つ外して2種になる挙動は直感に反するため採らない）
- 絞り込み中は個別トグル。全部OFFになったら「すべて」へ自動復帰
- 表示件数は**選択中チップの合計と常に一致**（隠れたプリセットを持たない）

### 3-3. 並び替え

| 選択状態 | 選択肢 |
|---|---|
| すべて / 2種選択 / 0件 | 関連順・新着順（種別を跨いで定義できるのはこの2つだけ） |
| 単一種別のみ | その種別固有の選択肢（例：パーツ＝装着例が多い順） |

### 3-4. Library補助導線

#### 固定する（責務レベル）

- Community件数に**合算しない**（別母集団）
- 検索結果カードと**同じ見た目にしない**
- 1回だけ。繰り返さない（繰り返すと広告になる）
- 広告・アフィリエイトではない。**MyRIG内部の回遊導線**。購買導線はLibrary側の責務

#### 固定しない（現時点の実装値。動かすのに裁定は不要）

| | PC | Mobile |
|---|---|---|
| 位置 | 結果グリッドの後・ページャの前 | 12件目の直後にインフィード |
| 形式 | Libraryカード4列×2段＝8件 | 横スクロール棚・150px固定カード |
| CTA | 「128件の製品を見る →」 | 「128件 →」（見出し行の右端） |

#### ⚠️ 触る前に読む罠

**① モバイルの末尾に置いてはいけない**
無限スクロールで**下端が無い**。54件のモックなら最後まで行けるが、実データ（数百件）では
誰も到達しない。「下に置く」は「隠す」と同義になる。
PCはページャで下端があるので末尾配置が成立する。**同じ設計をそのまま移植できない**。

**② 通常カードと同サイズにしてはいけない**
Community結果と区別がつかず「検索結果の別タイプ」に見える。
初版は横長の小さな行にしたが、今度は「関連記事・レコメンド」に見えてLibrary導線として弱かった。
**PCはカードを大きく＋囲みで区切る／モバイルは小さく＋横スクロールで棚にする**、と面ごとに解が違う。

**③ 抜粋の枚数を「◯件を見る」に使ってはいけない**
モックのDOMには抜粋しか無いため、素直に実装すると「Libraryで8件を見る」になる。
8枚表示して「8件を見る」では導線の意味が消える。**総ヒット数を別に持つこと**
（実装では `data-total` / `LIB_TOTAL`）。

**④ 縦に積むと主結果を分断する**
インフィードで縦積みにすると1画面まるごと専有する。実測でPC版と同じ作りは328px、
横スクロール棚に変えて200px、見出しを整えて246px。**高さがそのまま「邪魔さ」になる**。

### 3-5. 0件のとき

Libraryに製品はあるが投稿がまだ無い場合、完全な行き止まりになる。
空状態は結果ストリームではないので、ここにLibrary導線を出してよい（**未実装**）。

### 3-6. 検索トップ（Mobile）

PCには独立した検索トップを設けない（ヘッダー検索から結果へ直行）。Mobileのみ維持。

```
MyRIGで探す        ← 対象
[RIG] [パーツ] [LOG] [ビルダー]

もっと詳しく探す    ← 方法
[条件で探す] [製品名・型番で探す] [自分のRIGから探す]
```

**入口を2層に分ける際の原則**: 対象で表せるものと、方法でしか表せないものを厳密に切り分ける。
両方に同じ4枚グリッドを置くと「どちらを押すのか」が発生する。

- RIG/パーツ/LOG → 検索結果へ直行（`?type=` は初期フィルター）
- ビルダー → 同一画面パネル
- 検索窓プレースホルダは全面で「RIG・パーツ・LOGを検索」に統一

### 3-7. 自由語検索とサジェスト

- 自由語検索の入口は**ヘッダー検索1本**。結果内キーワード欄は作らない
- Amazon型の検索語拡張サジェスト（現在の語＋候補語）で再検索する
- **再検索してもサイドバーのフィルターは保持する**（検索語だけ差し替え）

「結果内キーワード欄を作らない」という旧判断は維持されるが、**理由が変わった**。
旧：第二検索欄を禁止する。新：自由語はヘッダー1本に統一し、サジェストで語を伸ばす。

## 4. 廃止

**FEATURED（検索結果内への注目枠差し込み）を廃止。**

ブレンド検索では検索順位の途中に別ロジックのカードを差し込むことになり、
「上から関連度順」という期待を壊してノイズになる。
将来、主結果とは別の「関連する注目コンテンツ」枠として再検討する余地は残す。

## 6. 実装で踏んだ罠（モックが消えても残す）

コードコメントにも書いてあるが、**Next.js化でHTMLモックが無くなると消える**ため、
理由の側をここに残す。

| 罠 | 内容 |
|---|---|
| **`vw` を使わない** | モックの `.mobile-viewport` は固定幅の枠。`vw` はブラウザ幅を拾うので、幅広ウィンドウでカードが枠を無視して巨大化する。実際に `44vw` で破綻した。**px か 親要素基準で書く** |
| **`<span>` に `aspect-ratio` は効かない** | インライン要素のため。カード内部を span で組むなら `display:block` を明示する。忘れると画像が意図より縦に伸び、ブロック全体が高くなる |
| **共有JSの単一選択ハンドラと衝突する** | `js/mobile-shell.js` の `[data-chipgroup]` は「クリックで兄弟の is-active を全部消す」単一選択前提。複数選択チップに付けると壊れる。**共有ファイルは変更せず、該当要素から属性を外す**（フィルターシート側は単一選択のままなので属性を残す） |
| **Web Componentの複製ノードを使い回さない** | 同じノードを付け外しすると `connectedCallback` が2回目の `attachShadow` で例外を吐く（同一ホストへのshadow root二重生成は禁止）。**描画のたびに `cloneNode` で新規ノードを作る** |
| **flexで `margin-left:auto` を2箇所書かない** | 余白を分け合って中央寄りに浮く。右寄せは1箇所だけにする |
| **`compare.html` は独自のPAIRS配列を持つ** | ランチャーを直しても同期されない。忘れると遷移が先頭（ホーム）へフォールバックして「両ペインにホームが出る」壊れ方をする |
| **`type="search"` の Escape はネイティブで入力をクリアする** | サジェストを閉じるだけのつもりが入力ごと消える。`preventDefault()` が要る |

## 7. ランチャー／compare への波及

- ランチャー検索セクションは**3項目**（検索結果(PC) / 探す(Mobile検索トップ) / 検索結果(Mobile)）
- 「検索結果『種別』(Mobile)」カードは廃止。種別はページではなく状態
- `compare.html` は独自の `PAIRS` 配列を持つため**同期が必要**。
  ここを忘れると、ランチャーからの遷移が先頭（ホーム）へフォールバックして壊れる
