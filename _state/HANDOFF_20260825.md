## 3. この作業から得た「効く」教訓

**次スレッドで最も価値があるのはここ。** 詳細は `_decisions/2026-08-25_search-closure-v1.md`。

### 検証は4段で見る（L1）

```
state が正しい → DOM が正しい → 実際に見えるUIが正しい → 操作後の結果データが正しい
```

1〜3段だけ見て「完了」と報告する事故が複数回起きた。
**「クリックできて見た目が反応する」だけではPASSにしない。結果データが変わることを見る。**

### 実際に踏んだ罠（同型が他画面に残っている）

| 罠 | 内容 |
|---|---|
| **`hidden` がCSSに負ける** | `hidden` はUAスタイルの `display:none` にすぎず、クラスの `display` 指定に負ける。DOM上もスクショ上も正常なのに**透明な当たり判定だけ残る**。実操作でしか出ない。`[hidden] { display: none }` を必ず併記する |
| **fixture値を語彙検証に使う** | 「今のデータに在るか」と「値として正しいか」は別。混ぜると正当な条件が消える |
| **表示だけ更新して結果を更新しない** | sort / page / filter / 検索窓のすべてで踏んだ |
| **同じmarkupが面で別の意味** | PCには `data-href` ハンドラが無く、Mobileと同じ形なのに何も起きなかった |
| **既定値が権限境界を決める** | カードテンプレートの引数既定値が `garage-rig-detail.html`（owner版）で、publicからownerへ入れた |

### FAILが出たら、まずテストを疑う

Searchでは「FAIL」の**約半分がテスト側の前提誤り**だった。

- カード名が重複していて集合比較が成立しない（`name+user+date` の複合キーが必要）
- fixtureの性質（Mobile RIG 18件が全部タイトルに `TRX-4` を含む）を踏まえない期待値
- スコープを絞ったセレクタで全体を判定
- 仕様変更に追随していない旧assert

### 恒久的なassertにしてはいけないもの

「Facet option count ≤ 現在の結果件数」— 同軸に既に選択があるとき、その軸自身を除外して数えるので**超えるのが正当**。

### 推測で埋めない

- `Scale` / `Scale Trail` は `build_tags` であって `rig_categories` ではない → 近い値へ寄せずNULL相当のまま
- LOGのメーカー派生は表示ラベルの部分一致ではなく**明示的な関連属性**から
- `manufacturer` の表記ゆれは**大小文字無視・部分一致・独自aliasで救わない**（Research正本待ちHOLD）

> 検証を通すために値を作ると**モックが嘘をつく**。嘘をついたモックは、実装時に
> 「仕様どおり作ったのに動かない」を生む。

## 7. 知っておくと詰まらない実務メモ

- **Mobileは `.mobile-viewport` が固定高のスクロール容器**。通常の full page 撮影ではファーストビューしか写らない
- `vw` 単位はモックの固定幅フレーム内で壊れる（ブラウザ幅に対して解決されるため）
- Web Components（PC）は **`cloneNode` で毎回作り直す**。接続済みノードを使い回すと2回目の `attachShadow` で例外
- PC検索の内部キーは `logs`、URLは `log`。mappingの内側に閉じてある
- `pc/img/` に `:` と `"` を含むファイル名の画像が3枚あり、**配信URLで404する**（PC Homeで1件発生）
- Playwright は `LD_LIBRARY_PATH=$HOME/.local/lib` ＋ `--no-sandbox` で動く
- サンドボックスに **git push の認証は無い**。commitまでがCowork、pushはイタヤさん
