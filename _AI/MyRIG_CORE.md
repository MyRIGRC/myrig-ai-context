# MyRIG CORE

MyRIGプロジェクトの恒久ルール。頻繁には変更しない。
現在地・最新裁定・HOLDは MyRIG_CURRENT.md を参照。

## プロジェクト概要

MyRIG RC（myrigrc.com）はRC車両の愛好家向けプラットフォーム。
ユーザーがRIG（車両）・パーツ・活動ログを登録するガレージ管理＋コミュニティ。
日本語・英語のバイリンガル対応。

最終判断者はイタヤ（板谷広智）。GPT・Geminiはクロスチェック、Claudeが裁定案を出す。

## 責務分離

App領域とResearch領域を混同しない。

- App: user / content系スキーマ、UI、モックアップ、実装
- Research: master系スキーマ（manufacturers / rig_masters / part_masters / rig_categories /
  part_categories / master_aliases 等）、マスターデータ収集ルール、カテゴリ構造
  ※Research側は part_masters（単数形）。App側の parts_masters（複数形）とは同名別義。混同しない

App相談とDB Research作業を同一セッションで混ぜない。
UI設計とDB設計を混同しない。

## DB恒久ルール

- 物理DELETEは禁止。inactive / NULL / archive / mv で代替する
- Production DBへの接触は禁止。明示指示がある場合のみ例外
- 値の優先順位: 公式根拠 > HOLD > 空欄/unknown > 推測 > 偽値
- compatible_platforms を公式根拠なしに具体補完しない
- 不確実なものは採用せず、HOLDまたは後続キューに回す
- 表示事故につながるリンク・画像・entity参照を軽視しない

## 正典の拘束力と、いま求められている姿勢

**現在はモックアップ制作フェーズ。** デザインとサービス概念を議論しながら作る段階であり、
**AIが自由に意見を出せることが価値**。Next.js実装に入れば厳密な正典が要るが、今は違う。

docs/ の各文書は冒頭に拘束力を明示している。

| レベル | 意味 | AIの振る舞い |
|---|---|---|
| **L1** | 恒久ルール・逸脱禁止 | 従う。提案しない |
| **L2** | 現在の確定仕様 | **出発点。より良い案があれば提案する** |

L2に対して、**「既存仕様と異なる」ことだけを理由に案を捨てないこと。**
これは禁止事項ではなく**義務**。正典に書いてあるからという理由で沈黙するのは、
「ガードレールが線路になっている」状態であり、避けたい失敗そのもの。

提案するときは差分を明示し、採用はイタヤ裁定を待つ。

**L1はごく少ない。** design-nogo-list 全体、各文書のセキュリティ節、
DB禁止事項、責務分離、HOLD原則。それ以外は議論してよい。

## 正典化判断基準（2026-08-24 追加）

**すべての設計判断を正典へ固定してはならない。**

MyRIGは仕様が先にある業務システムではなく、**作る → 触る → 違和感を見つける → 直す**
で品質が上がるUI発明型のプロジェクト。細かいUI仕様まで正典化すると、
次の作業時にAIが古い答えを守り始め、正典が進化を止める壁になる。

### 昇格の基準

判定は重要度ではなく、**「黙ってズレたときのコスト」**で行う。

> **2人（2つのAI）が独立に判断して食い違ったとき、何か壊れるか？**

以下に該当するものを正典対象とする。

- 変更すると複数箇所が壊れる
- 後から変更するコストが高い
- 実装者やAIが知らずに変更すると重大な不整合になる
- **UIを見ただけでは判断理由が分からない**

### 正典へ固定しないもの

- 表示件数 / カード配置 / 棚の位置 / 余白量 / 文言調整
- モック段階のUIチューニング全般

これらは**実装・モック自体を仕様とする**。必要な判断理由は決定履歴へ記録する。

### 4階層の役割分担

| 階層 | 持つもの |
|---|---|
| **CORE** | なぜ固定するか（恒久ルール・判断基準） |
| **CURRENT** | 現在採用している状態。差分と索引 |
| **DECISIONS** | **なぜそうしたか。罠と失敗理由**（＝「罠の地図」） |
| **コードコメント** | 実装固有の注意点 |

⚠️ **コードコメントだけに頼らないこと。** Next.js化でHTMLモック → React/CSS/Design System へ
分散した時点で消える。実装が変わっても残すべき理由は DECISIONS へ書く。

### 記録するのは結論ではなく理由

AIにとって一番危険なのは「知らないこと」ではなく、
**過去に失敗した理由を知らずに、同じ改善案をもう一度提案すること。**

だから記録は「何をやめたか」ではなく「**なぜやめたか / 何を踏んだか**」を残す。

- ❌ 「Library棚は12件目に配置する」（数値だけ。次に触る人は理由が分からず動かせない）
- ⭕ 「モバイル検索結果は無限スクロールで下端が無く、末尾配置は到達されない。
  また通常カードと同サイズだとCommunity結果と区別できないため、横スクロール棚＋別デザインにした」

**新しい情報が入って設計が変わるのは「正典違反」ではなく、設計探索による更新。**
そう扱えるように、旧裁定は削除せず「失効」として理由ごと残す。

## HOLD原則

未裁定事項は推測で埋めない。HOLDとして明示し、判断を止める。
「たぶんこうだろう」で仕様を作らない。
矛盾を発見したら進めず報告する。

**HOLDには2種類ある。混同しないこと。**

- **裁定待ちHOLD**: 判断材料が揃っていて、イタヤ裁定を出せば確定できるもの。
  → AIは案・提案書を作って裁定を求めてよい
- **将来議論項目HOLD（「モック未着手」型）**: モックプロジェクトでそのUI/機能自体が
  まだ着手されておらず、今決めると将来の議論の選択肢を潰す可能性があるもの。
  → **AIは催促・裁定要求を出さない。** 触るタイミングは「そのUI/機能の議論を
  始めるとき」まで待つ。CURRENTには「将来議論項目」と明示する

**現在はモックの詰め作業がまだ始まったばかりのフェーズ**であり、多くのHOLDは後者
（将来議論項目）に該当する。「HOLDを潰す」動き方は的外れになりやすい。

**裁定したら、その場で正典側へ移すこと。**
`_proposals/` は正典扱いしないため、裁定内容を提案文書に置いたままにすると
**「裁定した事実」ごと参照不能になる**。2026-08-22に検索の裁定4件がこの形で消えていた
（②PC非ブレンド化／④答えカード／⑤絞り込み候補チップ／⑥保存検索）。
実装が先でも、確定した判断は docs/ 側に「裁定済み・未実装」として記録する。

## スレッド／環境をまたぐ運用

イタヤはセッション消費を抑えるため、**デスクトップCowork / ブラウザCowork /
ブラウザ通常チャットを切り替えながら**作業する。スレッドは頻繁に変わる。

そのため **CURRENT.md 冒頭の「🔴 いまやっていること（NOW）」節が、
スレッド間の唯一の引き継ぎ手段**である。

- **新しいスレッドを始めたら、まずNOW節を読む。** 前スレッドの記憶や会話履歴に依存しない
- **作業の区切りでNOW節を更新する。** 進行中レーンの状態と次のアクションを書く。
  「あとで書く」は不可（次のスレッドが迷子になる）
- 過去スレッドの内容を探しに行かない。**NOW節に無い＝引き継ぐ必要がなかった**と解釈する
- 環境ごとに読める範囲が違う（ローカル直読み可否・Sync now要否）。
  詳細は本書「Claude Project（通常チャット）のGitHub Integration」節

## 実行レーン分離

- 判断レーン（通常チャット）: 設計判断、仕様検証、整合性確認、文書作成
- 実行レーン（Cowork / Claude Code）: ファイル操作、コミット、実装

DB書込・ファイル操作・大量変更は実行レーンに渡す。
チャット内で「実行済み」と言わない。
commit / push は明示指示がある場合のみ。
git add -A は使わない。常に明示的にファイルを列挙する。

## GitHub複数WRITE経路の競合防止

### 🔴 2026-08-24 裁定: 正典のWRITEはCoworkに一本化

**`myrig-ai-context` へ書き込むのは Cowork / Claude Code のみ。GPTはREAD専用。**
GPTが読むのは自由だが、修正してpushしない。

**この裁定の理由（実際に起きた事故）**: 2026-08-24、Cowork側とGPT側が独立に
revision **027** を採番していたことが判明した（Cowork=NOW節新設 / GPT=共通Search Service原則）。
共通祖先026から両者が分岐し、同じ番号の異なる正典が2つ存在する状態になっていた。
マージで統合したが、**気づかずにforce pushしていれば片方が消えていた。**
番号の一意性は単一WRITE経路でしか担保できない。

以下は、それでも複数経路が生じた場合に備えた手順として残す。

- Cowork / Claude Code:
  ローカルcloneを編集し、git commit / push
- GPT:
  GitHub API / connector経由でrepositoryを直接更新（**現在は行わない**）

そのため、WRITE開始前には必ずGitHub mainの最新版との同期を確認する。

### Cowork / Claude Code

ファイル編集前に必ず、

1. working treeに未処理変更がないか確認
2. git fetch
3. local HEAD と origin/main の差分確認
4. 必要ならgit pull

を行う。
origin/mainがローカルより進んでいる状態で、
古いローカル内容を基準に編集・commitしてはならない。
未commit変更等により安全にpullできない場合は、
勝手にmerge/rebaseせず停止して報告する。

### GPT

GitHub WRITE前に必ず、

1. revision.txt
2. _AI/MyRIG_CURRENT.md
3. 書き換える対象ファイル

をGitHub mainから再取得する。
取得済みの古い内容・古いSHAを使ってWRITEしてはならない。

**取得元は `api.github.com/repos/.../contents/...?ref=main` を使う。**
`raw.githubusercontent.com` はCDNキャッシュ（最大5分）で古い内容が返ることがあり、
「CURRENT_STALE」の誤検出につながる。revision照合・監査・WRITE前確認のいずれも
API経由で取得すること（GitHub Appのconnectorは通常API経由なので既定でこれを満たす）。

### Claude Project（通常チャット）のGitHub Integration

同期対象フォルダは **`_AI` / `_audit` / `_decisions` / `_proposals` / `_state` / `docs`
＋ `README.md` / `revision.txt`** とする。

- **`_backup` は同期対象に入れない。** 監査前スナップショット（旧CURRENT 006・旧docs）が入っており、
  検索で現行版と並んで出て取り違える。2026-08-22に実際に発生した
- `_archive` は退役文書。通常は不要（容量に余裕があれば任意）
- **GitHub Integrationは自動同期ではない。** pushしただけでは反映されず、Sync now の手動実行が要る。
  「revisionが古い」と感じたらまずSync nowを疑うこと（連携切れではない）
- **`revision.txt` は1行ファイルのため検索索引に乗らないことがある。**
  通常チャット側では CURRENT.md 本文の revision を正として扱ってよい
更新APIがSHA不一致・競合を返した場合は、
再取得して勝手に上書きせず停止し、競合を報告する。

### 共通

- WRITE経路にかかわらず、最新mainを確認してから編集する
- 他AIが直前に更新した可能性を常に考慮する
- force push / 強制上書きは禁止
- commit / push / GitHub WRITEはイタヤの明示指示がある場合のみ

## セキュリティ

secret / DSN / API key をチャットに出さない。
これらをCORE.md / CURRENT.md に書かない。

## 回答姿勢

- 結論を先に出す
- 日本語で簡潔に
- 不明な点は推測で埋めず「不明」「要確認」と言う
- 指示が矛盾したら進めず止める
- ユーザーに不要な判断を戻さない
- 複数案を出す場合は最終推奨案を明示する
- 別AIへ貼る文面は完成形をコードブロックで出す

## セッション終了時

そのセッションで以下が発生した場合、返答の最後に「CURRENT反映候補」を提示する。

- 確定裁定 / HOLDの発生・解除 / Active Override
- **進行中レーンの状態変化（NOW節の更新対象）**
- Task Routingの変更
- 後続スレッドが知らないと事故になる事項

形式:

```
### CURRENT反映候補
[種別: OVERRIDE / HOLD / STATE / NOW / PENDING]
内容を1〜3行
```

自動確定はしない。イタヤの承認後にのみCURRENT.mdへ反映する。
該当なしの場合は「CURRENT反映候補なし」とだけ書く。省略禁止。

## 検証原則

少数の確認結果や推測から全体を断定しない。
「問題ない」「完了」「全て正常」「存在しない」は十分な根拠がある場合のみ使う。
「見つからない」を「存在しない」と判断しない。
標準機能・公式仕様・既存機能を確認せず独自実装へ進まない。
実装前に影響範囲と副作用を確認する。
作業完了後、自分の結論が間違っている前提で反証確認を1度行う。

## ファイル生成

タイムスタンプは必ずJST(UTC+9)で記録する。
datetime.utcnow() や naive な datetime.now() は使わず、
ZoneInfo("Asia/Tokyo") で明示的にJSTを取得する。
xlsx生成は xlsxwriter を使う（openpyxlはMac Excelで修復警告が出る）。
