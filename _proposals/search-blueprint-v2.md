## 0. v1 → v2 で何が変わったか

### 0-1. 構造の変更（GPT指摘・採用）

**v1 は「検索画面の設計」であって「検索エンジンの設計」ではなかった。**

フィルタの位置より、`TRX4` `TRX-4` `TRX 4` `トラクサス TRX4` `1.9タイヤ TRX-4` `岩場で食うタイヤ`
を入力したときに MyRIG がどこまで同じ世界を理解できるかのほうが、検索の価値を左右する。
v2 は **§B「検索Core」を新設**し、画面設計（§A）と分離した。

### 0-2. ★正典の見落とし2件（本書で是正）

**① 日英2言語はMVP時点から。検索の言語横断は「実装着手前の必須議題」として既に起票されている。**

> `mobile-feedback-ledger-v1.md` #24 多言語方針（2026-07-23 イタヤ言明・実装要件）
> MyRIGは日本語/英語で公開する。**時期はMVP時点から**（「将来対応」ではない）。
> i18n設計（ルーティング・辞書・言語判定・Library英語表記・**検索の言語横断**等）は
> **実装着手前の必須議題**として別途1回議論する。

v1 はこれを完全に落としていた。GPTの指摘が正しい。
**したがって aliases / normalization / locale は「新規提案」ではなく、既に必須と決まっている議題の消化である。** §B-2 で扱う。

**② 「検索スコープ正典表の新設」は既に起票済み。GPTの言う Search Contract はこれに接続する。**

GPTが提案した `search-facet-registry` は、この起票済み項目の具体化。新しい枠を作る必要はない。

**③ 注目ワード不採用は、私の推論ではなく既裁定だった。**

v1 では v3.1 のアンチパターンを根拠にしていたが、**同じ判断が既に個別裁定されている**。根拠を強い方へ差し替える。

# §A 画面設計

## A-1. 3つのレーン（骨格）

MyRIG の「探す」は3本。**役割が違うので統合しない。**

| レーン | 入口 | ユーザーの状態 | 例 |
|---|---|---|---|
| **① 最速レーン** | グローバルヘッダーの検索窓 | **欲しいものが分かっている** | `TRX-4` / `AXI03007` / `Holmes Hobbies` |
| **② 回遊レーン** | ヘッダーのカテゴリ／メガメニュー → Browse | **眺めたい** | 「タイヤ見たいな」「ロッククローラーを眺めたい」 |
| **③ 精密探索レーン** | ヘッダーナビ **「探す」** → `/search` | **条件を組み合わせて探したい** | 「Traxxasの1/10でロッククローラーだけ」 |

**メガメニューは検索トップの代わりにならない。**
`RIG > Rock Crawler / Buggy / Drift` は **Browse への移動**（1軸のナビ）、
`Traxxas + 1/10 + Rock Crawler + 装着例あり` は**検索**（多軸の絞り込み）。置き換えられない。

**逆に③は①の代わりでもない。** PCでもキーワードを打つほうが速いので、③を主導線にしない。

### ★ナビ名は「詳細検索」ではなく「探す」（GPT指摘・採用）

v1 は「詳細検索」としていたが、これは使わない。

- モバイルの BottomNav が既に「探す」。**PCも同じ語にする**
- 「詳細検索」は *普通の検索より難しそう* に見える。MyRIGで最も面白くなり得る機能を、
  advanced user 用の奥まった機能に見せない

「探す」の中に「条件で探す」がある、という入れ子にする。

## A-2. 「検索トップ」は必要か

### 結論: **必要。ただし独立したランディングページとしては作らない。** `/search` を1ページ2状態にする。

```
/search                      → 探す開始状態（ゼロクエリ）
/search?q=... / ?maker=...   → 検索結果状態
```

### 4月モックの扱い

| 要素 | 扱い | 理由 |
|---|---|---|
| 大見出し「何を探していますか？」＋説明文 | **撤去** | 検索を説明するページは一手増えるだけ |
| 大きな検索窓 | **撤去** | ヘッダーに既にある。論点1でC案確定 |
| 「⚙ 詳細検索」ボタン | **昇格**（ヘッダーナビ「探す」へ） | ③レーンの入口。ページ内ボタンではなくグローバルナビに置く |
| **注目ワード チップ** | **復活させない** | **ledger #18 既裁定**「Overlay空欄時の『注目の検索キーワード』はトレンド表示にあたるため不採用」。v3.1 §5 三者一致とも一致 |
| 「Official Library でも探す」帯 | **形を変えて残す** | スコープ誘導（Baymard: 46%のサイトができていない）。帯ではなく結果側のスコープリンクとして |

### ゼロクエリ状態に何を置くか（論点5の裁定）

**欲張らない。検索画面はポータルホームではない。**（GPT2巡目）

**置くもの（これで十分）:**

| 位置 | 内容 |
|---|---|
| 左 | 条件ファセット（既存のサイドバーをそのまま） |
| 右 | **自分のRIGから探す** — 所有RIGのチップ |
| 右 | **最近の検索** |
| 右 | **保存した検索**（将来・Phase 4） |
| 右 | **Official Library** への入口 |

**未ログイン時**は「自分のRIG」の代わりに軽いガイドを置く:

> **条件を選んで探す**
> メーカー、カテゴリ、スケールなどを組み合わせられます

**置かないもの:**
- 注目ワード／トレンド／ランキング（ledger #18 既裁定）
- ライブフィード（探すレーンが回遊レーンに化ける）
- 代表車種ハブ（選定基準が説明できない）
- **「最近更新された公式ライブラリ」** — Gemini案②。v2初稿では採用したが**撤回**。新着ではあるがランキングではない、という理屈は通るものの、ここで賑わいを足しにいくと結局ポータル化する
- **「自分のRIGに関係する新着」** — 同じく撤回。将来やるなら**保存検索または基準RIGからの導線**として出すほうがきれい（GPT2巡目）

**「寂しいこと」自体を欠陥として扱わない。**

### P2. `/search?q=...` — 検索結果・すべて

```

│ 条件   リセット │  「servo」の検索結果  1,284件                     │
│ コンテンツタイプ │  [ キーワード: servo × ][ メーカー: Traxxas × ] 全解除│
```

- **ブレンドをやめ、種別セクションを縦に積む**
  根拠: Lalmas / Arguello *Aggregated Search* は blended の中核的困難として「異質な情報アイテムは特徴量が異なるため同一アルゴリズムでランク付けできない」と明記。1,296セッションの実験で **blended ではクリックが位置効果を受けるが non-blended では受けなかった**とし、「関連度を横断的に測定できない場合は non-blended の方が適切」と結論。

- 件数0の種別セクションは出さない
- **種別タブを置かない**（左サイドバーの「コンテンツタイプ」と二重）
- **ソートは結果直上**（左サイドバーから移す）。左＝何を残すか、右上＝残ったものをどう並べるか
- **キーワードは条件チップ `キーワード: servo ×` として表示。**クリックでヘッダー検索窓へフォーカス

### P3. `/search?q=...&type=parts` — 種別選択時

- 左の「コンテンツタイプ」で選ぶ＝P3。**別ページにしない**
- 左の軸が `data-for="parts"` 相当の群へ入れ替わる
- **PCはページャ**。ledger #25「サイト既定はページネーション維持」と整合（#26 の無限スクロールはモバイル検索結果限定の例外で、PC既定は「別途」＝未定のまま残っていた）
  NN/g: 目的志向の探索・比較にはページネーション。PCの検索結果は比較用途が主
- `表示件数 60 ▾` の既存UIはそのまま活かす

### 条件だけ・キーワードなしの見出し（論点6・GPT案採用）

条件が4〜5個になると「読み上げ」は破綻し、i18nも困難になる。

```
H1:  条件に一致するRIG   412台
     [ ロッククローラー × ][ 1/10 × ][ Traxxas × ]
```

## B-4. Query Understanding ★semantic より先（GPT提案・採用）

### 何をするか

`TRX-4に合う1.9のタイヤ` を、全文検索にかける前に解釈する。

```
TRX-4   → RIG / platform 候補
合う     → fitment intent
1.9     → tire diameter 候補
タイヤ    → part category
```

そして**画面に解釈結果を出す**:

```
検索条件として解釈しました
[ 基準RIG: TRX-4 × ] [ パーツ: タイヤ × ] [ サイズ: 1.9 × ]
```

**間違っていたらユーザーが消せる。**

### なぜこれが MyRIG に合うか

**LLM や分類器に答えを作らせない。「ユーザーが何を探しているか」だけを理解させる。**
検索結果そのものは MyRIG のDBから出す。
これなら正典の **「公式根拠 > HOLD > 空欄/unknown > 推測 > 偽値」** を壊さない。

### UI上は既存部品の再利用

解釈結果のチップは、既に設計済みの**適用中条件チップ**と同じ部品。
新しいUIを作るのではなく、**チップの出所が増えるだけ**（ユーザーの選択 / クエリ解釈 / 基準RIG）。

### Entity Resolution（曖昧さの解消）

答えカードの**前段**に置く。

| 状況 | 出すもの |
|---|---|
| 1つに特定できる | 答えカード（製品＋登録台数＋よく使われるパーツ） |
| 候補が複数 | 「TRX-4」はどれですか？ → `TRX-4` / `TRX-4 Sport` / `TRX-4M` / `TRX-4 Bronco` |
| 意図が複数 | 製品として見る / ユーザーRIGを見る / 対応パーツを見る |

**Baymard: 曖昧クエリで自動遷移するな。候補リンクを出せ。**

### 「Ask MyRIG」チャットは作らない（MVP）

AI検索というとチャット画面を作りたくなるが、MVPでは作らない。
**検索窓そのものを自然言語対応にする**ほうが先。
`SCX10 IIIで岩場向けに使われている1.9タイヤ` と普通の検索欄に書ける、で十分未来的。
**AIを検索の玄関に置くより、検索の中に溶かす。**

## B-5. ファセット件数（論点4・3者一致＋2つの追加）

### 原則: **結果・総件数・ファセット件数はすべて同じ検索インデックスから取る。SQLの `COUNT(*)` を混ぜない。**

PC の現物にはこう書かれている:

> 総件数の COUNT は10,000件で打ち切り「10,000+」表示にし、ページャも上限で止める（`part_masters` 実測 103,526件）。
> **ファセットの件数はマテビュー＋日次更新の概数で、検索語や条件が乗った状態では数字を出さない**

一方イタヤ指摘は「表示されるフィルターは、検索されたキーワードで引っかかるもののフィルター」。
**両立しない。** これは SQL の `COUNT(*)` を前提にした制約であって、検索エンジンなら消える。

### Gemini の追加: 同期ラグ

RDB → 検索エンジンの非同期レプリケーションで数秒〜数分のラグが出る。
**`/search` は100%インデックスから取り、RDBに `COUNT(*)` を発行しない。**
**Search Index を検索表示上の正本とし、DBの即時状態と完全一致させることを目標にしない。**

### ★GPT2巡目の訂正: 「総件数＝ファセット合計」は成立しない

Gemini は「これで総件数とファセット合計件数が完全に一致する」としたが、**これは誤り。採用しない。**

結果が100件でも、メーカーのファセットが `Traxxas 50 / Axial 40 / RC4WD 30` = 合計120 になることは普通に起きる。
**1アイテムが同じ軸で複数の値を持てる**ため（例: 1つのパーツが複数プラットフォームに適合）。
加えて、未分類値・複数選択OR・facet sampling・approximate count・disjunctive count のいずれでも合計は一致しない。

**正典に書くべき定義:**

> 検索結果件数とファセット件数は、**同一 Search Index・同一クエリ文脈**から取得する。RDB COUNT との混在は禁止する。
> **ただし、総件数と各ファセット値の合計が一致することは保証しない。**
> ファセット件数は **「その値を選択した場合に該当する結果数」** と定義する。

### GPT の追加: disjunctive faceting と概数

**「ほぼ無料」と考えるのは危険。**

- Traxxas を選択している状態で「Axial を追加すると何件か」を出したい ＝ **その軸自身のフィルタだけ外して再集計**する disjunctive faceting が要る
- Typesense は複数 facet について facet ごとの追加クエリを `multi_search` にまとめる方法を公式FAQで説明している
- 大規模結果では facet sampling / 概数がある。Meilisearch も exact facet count は計算コストが増えると明示

**したがって仕様は:**
1. 結果・総件数・ファセット件数は同じ Search Index から取る
2. 選択中の軸は disjunctive（自分のフィルタを除いて集計）
3. 大規模時は **`約12,400` のような概数表示を許容する**
4. SQL件数と Search Index 件数を**画面上で混ぜない**

## C-3. 適合（fitment）— 加工・流用文化を尊重する

**単一の真偽値にしない。出所つきの3値で持つ。**

| レイヤー | 意味 | 表示 |
|---|---|---|
| ① 公式適合 | メーカー一次資料に記載 | 「適合: 公式」 |
| ② 装着例あり | MyRIGのUGC集計。**保証ではない** | 「装着報告 12件」 |
| ③ 適合情報なし | 根拠が無い | 「適合情報なし」 |

### ★「適合情報なし」と「要加工」を混ぜない（GPT2巡目・採用）

Gemini は③を「適合情報なし/要加工」とまとめたが、**これは採らない。**

**適合情報なし ≠ 要加工。** 根拠が無いだけで、無加工で付く可能性もある。
まとめた瞬間に「加工が要る」という**データが持っていない主張**を発生させる。
正典の **「公式根拠 > HOLD > 空欄/unknown > 推測 > 偽値」** に真正面から反する。

**「要加工」は、ユーザー記録または一次情報から確認できる場合にだけ別ラベルとして出す。**

### ③を除外しないのは積極的な設計思想

RCは**加工・流用が文化**であり、「公式に適合しない」ことは「使えない」ことを意味しない。
非適合品をブロックするのは、この文化に誤ったモデルを押し付けることになる。

- 既定は①②③すべて表示。「公式適合のみ」は**ユーザーが選ぶオプション**
- **UGC集計から `compatible_platforms` を自動補完しない**（正典「公式根拠なしに具体補完しない」）
- eBay型の「保証」という語は使わない（返品制度が裏付けている表現で、MyRIGにその裏付けがない）
- PCPartPicker型の warning 表現を借り、断定を避ける

### ★バッジを出す条件（GPT2巡目・採用）

**通常の検索カード全部に「適合情報なし」の灰色バッジを出さない。**
出すと画面がバッジ祭りになり、しかも情報量はゼロ。

**基準RIGが指定されているとき、または適合を探している文脈のときにだけ表示する。**

### ★基準RIGは MVP では絞り込みではなく並び替え（GPT2巡目で再確認・採用）

Gemini は「compatible_platforms や装着実績から『無加工適合』『装着例あり』に一発で絞る」としたが、
**MVPでそこまで強く絞らない。**

適合データが薄い時期に hard filter すると、

> 「TRX-4に使えるタイヤは3件しかありません」

という表示になり、**MyRIG側のデータ不足を、世の中の事実のように見せてしまう。**

| 段階 | 挙動 |
|---|---|
| **MVP** | 「My TRX-4 に関係が確認できるものを上へ」＝**ランキングboost。件数を減らさない** |
| **データ成熟後** | 「公式適合のみ」「装着例あり」を**フィルタとして選べる**ようにする |

## C-4. マネタイズ

# §F 優先順位

**GPTの指摘に同意する。ここでUIだけ磨き続けると、操縦席は立派だがエンジンが未設計になる。**

ただし「モバイルUIを凍結してPCモックを止める」必要はない。
**Search Contract（B-1）は PCモックの前提でもある**ので、先に確定させると PCモックの質が上がる。

| 優先 | 内容 | 種類 |
|---|---|---|
| **P0** | **Search Contract**（B-1）。HTML `data-for` を正本から外す。ledger #19⑥ の消化 | ドキュメント |
| **P0** | **`master_aliases` / 日英 / 型番normalization**（B-2）。ledger #24 の必須議題の消化 | ドキュメント＋DB照会 |
| **P0** | **5 vertical の検索対象field・ranking**（B-3） | ドキュメント |
| **P0** | **facet count の意味と Search Index 設計**（B-5） | ドキュメント＋技術判断 |
| **P1** | **PC検索3状態のモック化**（A-4） | モック |
| **P1** | モバイル Phase 2（絞り込みを Contract 駆動へ／URL・履歴） | 実装 |
| **P2** | 検索品質ログ・評価セット（B-6） | 実装 |
| **P2** | Hybrid / semantic 導入 | 実装 |
| **P3** | Query Understanding / Entity Resolution / 答えカード（B-4） | 実装 |
| **P4** | 保存検索 / personalization / Ask MyRIG | 実装 |

**P0 は4件ともドキュメント作業なので、PCモック（P1）と並行できる。**
ただし Contract が固まる前にモバイル Phase 2 の実装に入ると、後で全部やり直しになる。

**GPTは「PCモックよりSearch Coreを優先したい」という、より強い立場を取っている。**
主査の見立てもほぼ同じで、違いは「並行可能か」だけ。
理由は、**Search Contract は PCモックの前提でもある**から。軸の定義・ラベル・複数選択可否・件数可否が決まっていないと、PCモックで作った左サイドバーはまた作り直しになる。
したがって実務上は **P0 →（Contract確定）→ P1 PCモック** の順が最も無駄が少ない。
