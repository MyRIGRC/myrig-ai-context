## 0. 本書の前提

### 0-1. 正典の扱い

**正典は制作時点のスナップショットであり、改訂していくもの。**
「正典と違うから採用しない」という判断はしない。食い違う場合は ①明示 → ②実用の観点で判断 → ③正典側が古い/不足なら**改訂提案として起票**（§11）。

### 0-2. 根拠の扱い

- **観察データと因果を区別する。** 「Aを入れたらBが上がる」と書けるのは対照実験がある場合のみ
- **一次資料を添えられない主張は断定しない**
- 出典のない主張（Gemini報告など）は方向性の参考にとどめ、根拠としては使わない

## 2. MyRIGの検索原則（確定）

1. **型番・メーカー型番の完全一致を最優先**
2. **製品名、通称、旧名、海外名、表記揺れを次順位**
3. **型番・数値属性では過剰な typo tolerance を使わない**（`M3` と `M4`、`1.9` と `2.2` を寄せない）
4. **ファセットには件数を表示する**
5. **フィルター種別間は AND、同一種別内は OR**
6. **適用中条件を結果面に常時表示し、個別解除・全解除を可能にする**
7. **0件時は 条件解除候補 / 表記候補 / 関連マスター / 装着例 へ誘導する**
8. **検索状態を URL と戻る操作で復元する**
9. **モバイルの「すべて」は29件ダイジェスト、種別タブは無限スクロール**（既裁定）
10. **未ログイン検索・閲覧は許可し、mutate時のみ Auth Guard を適用**
11. **キーワードとガイドの2レーンを共存させる。** どちらから始めても同じ検索結果モデルへ合流する
12. **検索前と検索後を別状態にする**
13. **広告を自然検索のスコアに混ぜない**

## 4. 軸マトリクス（全ページ共通の単一定義）

1箇所で定義し、モバイル検索トップの条件行・結果の絞り込み・PC左フィルターを同じ定義で駆動する。**別々に持つと必ずズレる。**

| 種別 | 出る軸（この順） |
|---|---|
| 未選択 | 車種カテゴリ / パーツカテゴリ / メーカー / スケール |
| RIG | 車種カテゴリ / スケール / メーカー / build_tags / ★作例あり |
| パーツ | パーツカテゴリ / ★適合シャーシ / ★スペック(段階導入) / メーカー / ★装着例あり |
| LOG | 車種カテゴリ / ログ種別※ / メーカー |
| 製品情報 | メーカー / ★作例あり |
| 人・ガレージ | なし（キーワードのみ） |

★＝新規　※＝正典改訂待ち（§11-1）

**順序の根拠**: 本質属性（何であるか・どれに付くか）→ 供給属性（メーカー）→ 商業属性。
モノタロウの六角ボルトは実測で **ねじの呼び → 長さ → 材質 → 種別 → ピッチ → 表面処理 → ねじ山種類 → 頭部形状 → ブランド → レビュー → 価格 → 出荷目安** の順。**価格が下位**なのが日本の工業パーツ系の作法。

**件数表示について**: 全ファセット値に件数を併記し、0件の値は出さない。
根拠は Baymard の現行ガイド（件数表示をフィルタUIの推奨実装とし、ゼロ件になる組み合わせを選ばせることを失敗パターンとしている）。
※ Flamenco(CHI2003) の数値は**インターフェース全体の比較**であり、件数表示単体の効果ではないため根拠から外した。

## 5. ページ①: `/search`（検索ハブ）

```
┌──────────────────────────┐
│ 🔍 RIG・パーツ・LOGを検索      │
└──────────────────────────┘

最近の検索                    履歴を消す
[TRX-4 ×] [SCX10 ×] [1.9 タイヤ ×]

──────────────────────────
何を探す？
  [RIG] [パーツ] [LOG] [製品情報]
  人・ガレージを探す              ›
──────────────────────────
条件から探す
  車種カテゴリ                    ›
  パーツカテゴリ                  ›
  メーカー                        ›
  スケール                        ›
──────────────────────────
[ロッククローラー ×] [Traxxas ×]

        [ 2条件で検索 ]
──────────────────────────
```

**※ この構成は確定ではない。§16 の A/B/C 比較で裁定する。**

### 共通の受入条件（どの案でも守る）

- 「何を探す？」は**必須ではない**。未選択なら「すべて」で検索
- 複数条件を積める（AND/OR は原則⑤に従う）
- **条件行は `›` 付きのナビ行の文法。罫線を足して表組みにしない**（NG-5）
- 選択肢に**件数を併記**し、0件の値は出さない
- 選択肢が多い軸（車種24・メーカー）は初期6〜8件＋「もっと見る」
- メーカーは**インクリメンタル検索窓**（既存実装を維持）
- 展開・折りたたみで**スクロール位置が飛ばない**
- 検索実行後に戻ったとき、**選択条件と開閉状態が復元される**

### サジェスト

- **テキストのみ。画像入りリッチ候補は作らない**（NN/g: 遭遇60回中利用7回。バナーブラインドネスで完全一致すら見落とされる）
- モバイル **4〜8件**上限
- **スコープ付き候補**を出し、スコープ部分は薄色＋インデントで区別

```
検索: "servo"

サーボを検索
  → パーツ > プロポ・受信機 > サーボ
製品情報で "servo" を検索
すべてから "servo" を検索
```

- **結果が出る候補だけ出す**
- カテゴリ名と1:1一致するクエリは、検索結果でなく**そのカテゴリ面へ誘導**

### アンチパターン（3者一致）

- **トレンドキーワード／ランキングを置かない**（既存の「ランキング表現を使わない」裁定とも一致）
- **レコメンドフィードにしない**（楽天は検索と「発見」を別タブに分離している）
- **大型広告を置かない**

## 6. ページ②: `/search?q=TRX-4`（すべて＝29件ダイジェスト）

**既裁定どおり29件の有限ダイジェスト。構造は現行維持。**

### 足すもの

- **タブと各セクション見出しに件数**
- 件数0の種別セクションは出さない
- **フェデレーション検索にする**（§8-2）。RIGのタイトル一致スコアとLOG本文一致スコアを1本のランキングに混ぜない

### ゼロ件のとき

**出すもの（原則⑦）**
1. **条件解除候補** — どの条件を外せば結果が出るか
2. **表記候補** — 「Hilux → ハイラックス で検索しますか？」（§10）
3. **関連マスター** — 近い製品情報
4. **装着例** — そのキーワードに関連するRIG/LOG
5. クエリを検索窓に**残す**
6. 「◯◯に一致するものはありませんでした」を**明確に**（小さく薄い文字にしない）

**やらないこと**
- 「検索のコツ（スペル確認・語を減らす）」だけのページ ← 読まれず実行されない
- 静的カテゴリリンクだけの汎用ページ
- **ユーモアで茶化す** ← 苛立っているユーザーは「笑われている」と受け取る（NN/g）

**フィルタ由来の0件は別扱い**: 「システム故障」と誤解されるので、変化が見えるよう結果先頭へスクロールさせる。

## 8. 検索アーキテクチャ

### 8-1. URLを検索状態の正本にする

```
/search
/search?q=TRX-4
/search?q=TRX-4&type=rig
/search?type=rig&rig_category=rock-crawler&maker=traxxas&size_class=1-10
```

複数選択は同じキーを複数回（`URLSearchParams.getAll()`）。

**URLへ持たせる**: `q` / `type` / `rig_category` / `part_category` / `maker` / `size_class` / `build_tag` / `sort`
**URLへ入れない**: アコーディオンの開閉など、**検索結果を変えないUI状態**

**必ず slug で持つ。日本語ラベルを入れない。**
```
OK  ?rig_category=rock-crawler
NG  ?rig_category=ロッククローラー
```
実際にパーツ親カテゴリ5件の表示名が今回変わっている（電動パワー→モーター・ESC 等）。**表示名は変わる前提で設計する。**

### 8-2. フェデレーション検索（type quota型）

`all` では1つの共通スコアにまとめない。

```
RIG top6 / PART top6 / PRODUCT top4 / LOG top6 / USER top3  ← 計29件（既裁定と整合）
```

**RIGのタイトル一致スコアとLOG本文一致スコアを直接比べても、ユーザーにとって同じ意味を持たない。**

### 8-3. 型番は exact-match 専用フィールドを持つ

```
型番完全一致            × 非常に強い
title完全/前方一致       × 強い
メーカー + title         × 強い
カテゴリ一致            → filter
本文一致                 × 中
新しさ                   × 小
人気・閲覧               × 小・上限あり
広告                     → スコアへ混ぜない
```

**型番・数値属性では過剰な typo tolerance を使わない。** `M3`/`M4`、`1.9`/`2.2`、`TT-02`/`TT-02D` を寄せると実害が出る。

### 8-4. 検索API境界をMVPから切る

**「最初からElasticsearch必須」ではない。** 初期データ量ならDBでよい。ただし**抽象化はMVPから必須**。

```
GET /api/search
GET /api/search/facets
GET /api/search/suggest
```

DB直結ロジックをReactコンポーネントに書かない。後から OpenSearch へ切り替えられる境界を作る。
深いページングは `OFFSET` でなくカーソル式へ寄せる。

### 8-5. 認証ガード

**検索面は未ログインでも完全に閲覧可能。** 検索にログインを強制しない（SEO・新規流入の両面で不可）。

| | 対象 | 挙動 |
|---|---|---|
| P1 | `/garage/*` `/settings/*` | ログイン画面へリダイレクト |
| **P3** | 検索結果上の ♥ / ★ / 📌 / フォロー | **Login Modal。閉じれば検索状態を維持** |
| P2 | 新規登録の起動 | 検索画面を背後に維持したまま Modal |

### 8-6. モバイル検索の3導線

| 導線 | 挙動 |
|---|---|
| ヘッダー検索 | タップで**全画面オーバーレイ**。ページ遷移せずサジェスト。入力にネイティブフォーカス |
| BottomNav「探す」 | `/search` へ遷移。**自動フォーカスしない**。探索ハブとして見せる |
| 検索結果 | ヘッダーが横幅いっぱいの検索窓に変化（**SearchHeader variant**）。**画面内に検索窓を2つ作らない** |

## 9. マネタイズ

### 9-1. 検索結果面に広告を入れない理由（差し替え済み）

~~価格.comは広告なしで成立している~~ ← **撤回。価格.com検索には[PR]商品が混在する。**

**採用する理由**
1. **初期段階では検索信頼性と適合根拠を優先する。** MyRIGの検索は「このパーツが自分の機体に合うか」を判断する装置であり、そこに広告が混ざると判断材料そのものが疑われる
2. **オーガニック順位と報酬額を完全に分離する**
3. **購買導線は Library / Master 詳細へ集約する**（検索面に置かない）
4. **既存アーキテクチャと整合する** — `page_blocks` の `block_type='adsense'` は対象が index / category_top / subcategory_top で、**検索面は対象外**。「広告はブラウズ面、検索面は自然結果のみ」という分担が既に設計に入っている

**補足（判断材料として保持）**: FTC訴状で明らかになったAmazonの内部実験では、無関連広告は「検索体験を悪化させたが**広告収益には悪影響がなかった**」。**短期KPIは警告を出さない**ため、guardrailを事前に定義しない限り検知できない（§9-4）。

### 9-2. 段階

| 段階 | 内容 | 判断 |
|---|---|---|
| **MVP** | **検索面の広告ゼロ。** 検索品質指標のベースラインを取る | **確定** |
| 収益の主軸 | **Library/Master詳細のBUY/INFO導線**（§9-5） | **確定** |
| 拡張① | 「すべてダイジェスト」の**セクション境界**枠 | 保留（guardrail必須） |
| **不採用** | 検索結果**上位**へのスポンサー枠 / 検索連動CPC / 保存検索通知への広告 | **却下** |

### 9-3. 保存検索の通知に広告を入れない

通知の信頼性が最優先。ここを汚すと保存検索機能そのものが使われなくなる。

### 9-4. 広告を入れるときの guardrail

**広告CTRだけを成功条件にしない。** ZOZOはホーム推薦の5週間A/Bで4群へ25%ずつ割り当て、受注系指標だけでなく多様性も評価し、**KGI/KPIが悪化する場合はリリースしないと事前に定めていた**。同じ運用にする。

```
収益側     広告CTR / 外部ショップ遷移率 / 収益 per 1,000検索
品質側     検索→詳細閲覧率 / 再検索率 / 0件率 / 離脱率 / 「すべて見る」遷移率
Guardrail  自然結果CTR低下 / 詳細閲覧率低下 / 戻る直後の離脱増
```

### 9-5. 購入導線 ★全面書き換え（ledger #34 準拠）

**大前提（イタヤ言明・トーン原則・2026-07-24承認）**

> MyRIGは**ショップではない**。購入導線はアフィリエイトへのマネタイズ動線でしかなく、ユーザーは「買いに来ている」のではなく**参考にしに来ている**。したがって**押しの強いアフィリエイト導線はやらない**。控えめ・邪魔しないを常に優先し、**迷ったら出さない側に倒す**。

**表示しないもの（確定）**
- **価格**
- **在庫**
- **SALE / 最安 / ポイント**
- 価格比較テーブル形式そのもの

**表示する形（#34 ④／#35 で実装済み）**

```
┌─────────────────────────────┐
│ この製品を扱っているショップ      PR │
│  [Amazon] [楽天] [Yahoo] [海外SHOP] │
└─────────────────────────────┘
```

- **BUY/INFOは本文と別枠のカード＋PR明示**（コンテンツと広告の区別を曖昧にしない）
- ショップはブランド色チップで並列表示。**どこが安いかは言わない**
- 置き場は **Library / Master 詳細**（`affiliate-link-modal-spec-v1` に準拠）

**表示条件（#34 ①）**
- `affiliate_links` に `is_active` なリンクが**存在する製品のみ**出す
- `is_discontinued`（廃盤）は購入バーを出さず、**「製品情報を見る」導線のみ**に切替

**頻度（#34 ②）**
- **確率式は不採用**（「参考にしたい人の体験を不安定にする」）
- **frequency cap 方式**: 1セッションN回まで／✕タップ後24時間サプレス／同一RIG詳細では1回
- cap の初期値は**控えめ側**に設定

**運用（#34 ③）**
- 頻度・対象・cap は**管理画面で調整可能**にする

**禁止**
- **アフィリエイト報酬率でソート順を変える**
- 高報酬店を「おすすめ」と呼ぶ
- 単一ECへの独占送客（規約変更に対する単一障害点になる）

### 9-6. PR/提供関係の管理（7フィールドへ分離）

「提供有無 boolean」1つでは不足。措置命令3例目（大正製薬 2024/11/13）は **`#PR` 付き投稿を自社サイトへ転載する際に表記を落とした**ことが違反の中身だった。

```
commercial_relationship_kind      関係の種類（提供/報酬/貸与/モニター/なし）
compensation_or_free_product      金銭・現物の授受
requested_or_directed_by_business  事業者からの依頼・指示の有無
disclosure_required               開示義務の有無（上記から判定）
disclosure_label                  実際に出すラベル文言（PR / 提供 / 広告）
original_source / provenance       出所（自社/ユーザー投稿/外部転載）
platform_reuse_status             MyRIG内での再利用状態（トップ掲載/SNS転載等）
```

**転載時に `disclosure_label` が自動で付く実装にする。**

**運用基準が名指しでNGとする表示**（そのままUIのNGリスト）
- 末尾に表示 / 周囲より小さい文字 / 長文に埋没 / ハッシュタグに埋没 / 本文外（ツリー・リプライ）に記載

### 9-7. 禁じ手

## 11. 正典改訂提案（3件）

### 11-1. LOG種別を5値へ統一（schema v1.7）

| | 値 |
|---|---|
| schema v1.6 | 4値（`maintenance` / `custom` / `run` / `memo`） |
| UI実装 | **5値**（＋`setting`「セッティング」） |
| 7月末裁定 | **5値で確定**。旧 `setup` は復活させない |

**schema と UI が食い違っている。裁定は既に5値で出ているので schema を追随させる。**
改訂されれば LOG検索の絞り込み軸として `log_type` を使える。

### 11-2. パーツの `spec_data` を絞り込み軸として解禁 ★実用上の最重要

DB Research の回答内に矛盾がある。

> 「『タイヤ・ホイール → タイヤ → 1.9インチ』の3階層目は分類ではなくスペック。`spec_data` で表現し、**絞り込みも `spec_data` 側で行う**」
> 「パーツ側 `spec_data` のキー設計は**未定**」「**App側は当面 `spec_data` を絞り込み軸に使わない**」

**両方守ると、タイヤをサイズで絞る手段が存在しない。**
RCのタイヤは 1.9 / 2.2 / 2.6 / 1.55 で選ぶのが当たり前で、これができない検索は実用にならない。モノタロウが「ねじの呼び」「長さ(mm)」を最上位ファセットに置いているのと同じ構造。

**提案**: 検索で実際に要るキーだけ先行確定する。

```
tire_size_inch     1.55 / 1.9 / 2.2 / 2.6
hex_size_mm        12 / 14 / 17
thread_size        M3 / M4 / M5
material           aluminum / steel / brass / plastic / carbon
```

RIG側が11キーのホワイトリストで確定できているので、**同じ方式でパーツ側も段階確定できるはず**。

### 11-3. `aliases` の正本を一本化

| 出典 | 定義 |
|---|---|
| App正典 `myrig_db_schema_v1_6` | `parts_masters.aliases TEXT[]` ＋ GINインデックス |
| DB Research `db-schema-answers-v1` | **`master_aliases` が正本。`rig_masters` に `aliases` 列は追加しない。** `entity_type='rig_master' / 'rig_master_variant' / 'part' / 'manufacturer'`、`alias_kind` と `locale` で区別 |

**主査の見立て**: `master_aliases` 型が優れている。
- RIG側にもエイリアスが要る（App正典は `parts_masters` にしかない）
- `alias_kind`（通称/旧名/海外名/型番揺れ）と `locale` を区別できる
- メーカー名も同じ仕組みで扱える（Traxxas / トラクサス）
- **`rig_master_variant` を entity_type として持てる** — §12-3 のバリエーション問題に直結する

**あわせて `owner` を確定する。** `owner=common` は避け、軸ごとに最終決定権を一方に置く。
（`log_type` / `surface` / `weather` は既に「App側が正本」と確定しており、この方式は半分できている）

## 12. 適合（fitment）— MyRIGの中核

### 12-1. 表示レイヤーを3つに分離する ★最重要

**この3つを絶対に混ぜない。**

| レイヤー | 定義 | 表示例 |
|---|---|---|
| **① 公式適合** | メーカー・一次資料・検証済みマスターに基づく | 「メーカー公式対応」 |
| **② 装着例あり** | MyRIGの公開RIG構成からの集計。**適合保証ではない** | 「このシャーシで**使用例 18件**」 |
| **③ 要確認** | 公式根拠も十分な装着例もない | 「適合情報なし」 |

**禁止事項**
- **UGC集計から `compatible_platforms` / `compatible_types` を自動補完しない**
- **「よく付く」「無加工で付く」と自動断定しない**
- ②を①の代わりに使わない

**必須**
- 装着例には**加工内容・追加部品・注意点へ遷移できる導線**を付ける
- 「使用例18件」から、その18件のRIG・LOG・加工内容へ辿れること

### 12-2. 適合フィルタの挙動（MyRIG独自方針）

~~PCPartPickerは排除でなく警告~~ ← **撤回。** 実際のPCPartPickerは既定で互換候補へ制限し、利用者がフィルタを解除できる方式。

**MyRIGは以下を独自方針として定義する。**

RCは**加工・流用が日常**で、「非互換だが実際に付いている」が大量に存在する。したがって:

1. **既定は「公式適合」で絞る**（レイヤー①）
2. **「装着例あり」を含めるトグルを別に置く**（レイヤー②）— 排除ではなく**段階的に広げる**
3. **除外された理由を必ず書く。** 「ホイールハブ12mm六角に対し本品は14mm」。**理由なしのグレーアウトは絶対にやらない**
4. **逃げ道を置く。** 「すべて表示する」「適合情報を報告する」
5. **適合データの不完全さを前提にする**

```
[ 公式適合のみ ]  [ 装着例も含む ]  [ すべて ]
     ①               ①+②            ①+②+③
```

> 互換性依存商品を扱うサイトの**32%が互換性フィルタ非搭載**、互換性タスクの完了率は**35%**（Baymard）。RCでは致命的な水準。

### 12-3. バリエーション確認レイヤ（タミヤ・一次資料あり）

タミヤ公式「WEBを使って上手に対応パーツを探そう！」より原文引用:

> 「TT-02シャーシについては、オンロードカー限定モデルのほとんどが『TT-02シャーシ』ですが、その他ドリフトカーは『TT-02Dシャーシ』、バギータイプは『TT-02Bシャーシ』があり、**それぞれ対応パーツが異なる場合があります**。」

**同一シャーシ名でも派生で適合が変わる**ことが、業界大手の公式ガイドで明示されている。
MyRIGでも `TRX-4` / `TRX-4M`、`TT-02` / `TT-02D` / `TT-02B` は別物として扱う。

```
選んだのはこれで合っていますか？
  ● TT-02              （オンロード）
  ○ TT-02D             （ドリフト）
  ○ TT-02B             （バギー）
```

※ `master_aliases` の `entity_type='rig_master_variant'` がこの粒度に対応（§11-3）。

### 12-4. フォールバック導線（タミヤ・表現を訂正）

同ページ原文:

> 「ご存じなければ、アイテム（ITEM）の（アイテム）番号を用いて検索する方法もあります。」

~~「シャーシを選択できない場合、使用パーツで検索」~~ ← **訂正。正しくはアイテム番号での検索。**

**MyRIGでの実装**: シャーシが特定できないユーザーを行き止まりにしないため、
- 「シャーシがわからない」→ **型番/製品番号から探す**
- それも不明なら → **写真から探す**（Phase 3）
- 最終手段 → **キーワード検索へ戻す**

### 12-5. 「自分のRIGから探す」

Webike の「Myバイクから探す」に相当。**MyRIGは `rigs` を本業として持っている**ので、登録済みRIGがそのまま検索スコープになる。

**ただし**
- **車種選択を必須にしない。** 汎用品（工具・ケミカル・バッテリー）の探索を邪魔する
- **明示的な検索コンテキストとして扱い、利用者が解除・切替できるようにする**（勝手に効かせない）

## 13. 差別化の中心

MyRIGの中心価値は**単なる適合表ではない**。

```
① 公式適合情報
      ↕
② このシャーシで実際に使われているパーツ
      ↕
③ そのRIG・LOG・加工内容
```

**この3層を、根拠を分けたまま往復できること。**

Rebrickable の「**所有パーツによって組めるセットが変わる**」構造に近い。
**My Garage のデータが検索結果の意味を変える**点がMyRIG独自性であり、メーカー公式が構造的に持てない資産（社外品・流用・加工の実績）がここに溜まる。

### 13-1. カタログ面に「ユーザー面」タブ（Ravelry方式）

```
RIG製品ページ:   概要 | 持っている人(N) | LOG(N) | 適合パーツ(N) | 使用例(N)
パーツ製品ページ: 概要 | 装着しているRIG(N) | LOG(N)
```

**全タブに件数。件数0のタブは出さない**（空タブは信頼を削る ← Ravelryは「project数が十分なときだけ People Also Like を出す」条件付き表示を採用）。

### 13-2. 「作例あり」ファセット（Printables `with makes`）

カタログの死蔵レコードを検索結果から沈める。立ち上げ期にデータの薄さを隠す手法。

### 13-3. 「フォロー中の人が持ってる」フィルタ（Ravelry `Friends Made This`）

実装コストが低く、体験の質への寄与が大きい。

### 13-4. 保存検索＋新着通知

| 項目 | 仕様 |
|---|---|
| 起動位置 | **検索実行後の結果画面**に「この検索条件を保存する」 |
| 頻度 | すぐに通知 / 1日1回 / 3日に1回 / 通知しない |
| 置き場 | マイページ ＞ フォロー中 ＞ 検索条件 |
| 対象 | **新規登録のみ**（既存の更新では通知しない）と明記 |
| 上限 | 保存50 / 通知20 程度 |
| 保存形式 | **URLのquery paramsをそのまま保存**（§8-1のslug設計が効く） |
| **禁止** | **通知への広告挿入**（§9-3） |

### 13-5. UGCの操作可能性（仮説として）

PowerReviews（1,200ブランド・1,500万商品ページ・2022年）の**観察データ**:

| 接触 | CVR差 |
|---|---|
| UGCが表示された | +3.8% |
| UGCを操作した | +102.4% |
| ★1フィルタ | +71.9% |

**これは対照実験ではなく観察データ。** 「操作した人はもともと購買意欲が高い」という逆因果が説明として成立する。

**したがって因果として扱わず、次の仮説としてMyRIG内で検証する。**

> 仮説A: 作例を絞り込み・検索できるようにすると、閲覧だけより後続行動が増える
> 仮説B: 「うまくいかなかった記録」を隠さない方が、信頼と後続行動が増える

仮説Bは**トーン原則（参考にしに来ている）とも整合する**ので、優先的に検証する価値がある。

## 14. SEO / インデックス制御

- **任意の `/search?q=...` と複合フィルターURLは原則インデックス対象にしない**
- **SEO対象は、安定したメーカー・カテゴリ・製品マスターの公開ランディングページ**
  - `/browse/category/[slug]` / `/browse/parts/[categorySlug]` / `/library/parts/[masterSlug]` / メーカーページ
- **canonical は重複代表URLの指定であり、noindex の代替として乱用しない**
- **noindex を読ませるページは robots.txt でクロール自体を遮断しない**（読まれなければ noindex が効かない）
- **無限スクロールとは別に、クローラが辿れるページURLとリンクを用意する**

## 15. 語彙契約とガバナンス

**表示名は変わる。slugで契約する。**

### 15-1. 契約の最小単位 = `axis + slug`

```json
{
  "contract_version": "1.0",
  "axis": "rig_category",
  "slug": "rock-crawler",
  "owner": "research",
  "consumers": ["app", "search"],
  "lifecycle_status": "active",
  "decision_state": "approved",
  "name_ja": "ロッククローラー",
  "name_en": "Rock Crawler",
  "parent": { "axis": "rig_type", "slug": "rc-car" },
  "replaced_by": null,
  "app_visibility": ["search_top", "search_filter", "rig_registration"],
  "filterable": true,
  "searchable": true,
  "db_location": "rig_categories.slug"
}
```

### 15-2. `deprecated` と `HOLD` を別フィールドにする ★

```
lifecycle_status : active / deprecated / retired / pending   ← 語彙のライフサイクル
decision_state   : approved / hold / review                  ← 運用判断
```

**同じ `status` に入れると「deprecatedだから自動移行してよい」という誤実装が起こる。**

現在の `mini-micro` / `size_class` はこの類型:
```
mini-micro
  lifecycle_status = deprecated
  migration_state  = hold      ← 移行先の size_class が未確定
```

引き継ぎdoc §7 の HOLD 矛盾（「2026-07-30 決定済み・固定13値」vs「2026-08-20 これから審議」）も、
`lifecycle_status=active` / `decision_state=review` と書けば矛盾なく記述できる。

### 15-3. 検索側での deprecated 値の扱い

- 新しいフィルターの選択肢には出さない
- **既存データに残っている場合は検索可能にしておく**
- 旧URLは alias / replacement 情報で互換表示する
- **replacement が HOLD なら勝手に置換しない**

### 15-4. CIで機械検査する

```
契約にないslugをAppが使用        → FAIL
deprecatedを新規fixtureで使用     → FAIL
HOLD値をmigration対象にする       → FAIL
Research-owned値をAppで再定義     → FAIL
表示名だけ違う                   → WARN
```

今回の作業だけで「スケールトラック21箇所」「Micro & Mini」「オンロードGT」「メンテ・工具（旧名）」が手作業で見つかっている。**この検査があれば毎回の突き合わせが不要になる。**

## 16. 次工程: 検索トップ3案の比較

**実装指示書はまだ作らない。** 既存の検索トップ構成を基準に3案を比較する。

| 案 | 内容 |
|---|---|
| **A. 現行構成** | 種別チップ ＋ 車種24 ＋ パーツ14 ＋ メーカー ＋ スケール13 を全部縦に展開（現状） |
| **B. 主要グループのみ開いたアコーディオン** | 種別は露出。条件4軸は畳む。1軸だけ既定で開く案も含む |
| **C. 検索意図別の段階選択** | 「型番で探す / 条件で探す / 自分のRIGから探す」を先に選ばせる |

### 比較軸（この軸で実機裁定する）

| # | 軸 | 測り方 |
|---|---|---|
| 1 | **初期表示の縦の長さ** | 390px幅で1画面に収まるか（実測px） |
| 2 | **最初の一手が分かるか** | 開いた瞬間に何をすればいいか判断できるか |
| 3 | **型番を知っている人の速さ** | 検索窓に到達するまでのタップ数・視線移動 |
| 4 | **型番を知らない人の到達性** | 目的の条件に着くまでのタップ数 |
| 5 | **複数条件の積みやすさ** | `Traxxas × ロッククローラー × 1/10` を組むまでのタップ数と迷い |
| 6 | **条件の見通し** | 今どの条件が効いているか常に分かるか |
| 7 | **軸ラベルだけで判別できるか** | 畳んだ状態で「自分が使う軸」を選べるか |
| 8 | **戻ってきたときの復元** | 結果→戻るで条件・位置が保たれるか |
| 9 | **将来の軸追加に耐えるか** | スペック軸・適合軸を足しても破綻しないか |
| 10 | **PCへの写しやすさ** | 同じ状態モデルでPC面を作れるか |

### 進め方

1. 比較軸をイタヤ承認
2. 3案の実モックを作る（`_compare/` に並べる。操作色A/B/C比較と同じ方式）
3. **実機で確認 → 裁定**
4. 裁定後に実装指示書へ落とす

## 17. リスクと回避策

| リスク | 影響 | 回避策 |
|---|---|---|
| 条件を増やして再び縦長になる | 高 | 初期は軸のみ表示。値は展開 |
| 検索トップと詳細検索の境界が曖昧 | 高 | `/search` はハブ。結果カードを初期表示しない |
| 「すべて」と種別が同じに見える | 高 | 件数見出し・専用フィルタ・並び替えで差を作る |
| PCとモバイルで別ロジック化 | 高 | URL/query schema と Search API を共通化 |
| App/Research の slug 差分 | 高 | `axis+slug` 契約＋CI |
| deprecated 値を誤移行 | 高 | lifecycle と decision_state を分離 |
| 全文検索で型番を落とす | 高 | exact identifier を別フィールド・高boost・typo tolerance を効かせない |
| 異種結果を1つの関連度で混在 | 高 | `all` は type quota 型 |
| **UGC集計を公式適合と誤認させる** | **最高** | **3レイヤー分離。自動補完しない。「使用例N件」表記で保証しない** |
| 無限スクロールから戻ると位置喪失 | 高 | URL＋cursor＋scroll restore をテスト |
| 広告で自然結果が信用されなくなる | 高 | MVPはゼロ。別枠・明示ラベル・guardrail |
| **購入導線がショップ化する** | **高** | **価格・在庫・最安を出さない。frequency cap。迷ったら出さない側へ** |
| 意味検索を早期導入して複雑化 | 中 | まず0件率と再検索率を基準化 |
| 固定バーが操作を覆う | 中 | WCAG 2.2 Focus Not Obscured / Target Size で検証 |
