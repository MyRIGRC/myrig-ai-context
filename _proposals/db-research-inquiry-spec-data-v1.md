# A. `spec_data` を検索の絞り込み軸として使えるか

## A-1. 何が起きているか

DB Research の回答内に、**両立しない2つの記述が併存しています。**

| # | 記述 | 意味 |
|---|---|---|
| ① | 「絞り込みは `spec_data` 側で行う」 | パーツの細分（タイヤ径 1.9 / 2.2 / 2.6 など）は分類ではなくスペックなので、`part_categories` を増やさず `spec_data` で絞る |
| ② | 「App側は当面 `spec_data` を絞り込み軸に使わない」 | App の検索UIでは `spec_data` をファセットにしない |

**この2つを両方守ると、タイヤを 1.9 / 2.2 / 2.6 で絞る手段が MyRIG から消えます。**

これは実用上かなり深刻です。RCクローラーのタイヤ選びは**まずサイズで絞る**のが実務であり、
「タイヤ・ホイール 3,441点」を出したあとサイズで絞れないと、検索として成立しません。
モーターのターン数、サーボのトルク、ショック長も同じ構造です。

---

## A-2. こちらの理解（間違っていたら訂正してください）

- `part_categories` は **level=1 の親14件で凍結**。サイズ等の細分は分類ではなくスペック
- したがって `1.9インチタイヤ` というカテゴリは作らない
- スペックは `parts_masters.spec_data`（JSONB）が持つ
- **`part_categories.spec_schema` が存在する** ＝ カテゴリごとに「どのスペック項目を持つか」を定義できる仕組みが既にある

この理解が正しければ、**`spec_schema` を使って「カテゴリごとに、どのスペックを絞り込み軸へ昇格させるか」を定義できる**はずです。
つまり②の「当面使わない」は、**軸の定義が無かった時点での暫定判断**だったのではないか、というのがこちらの見立てです。

### Q-A1. 2つの記述のどちらが後発・有効ですか

- ①が有効なら、②は失効として扱ってよいですか

### Q-A2. `part_categories.spec_schema` の現在の定義を共有してもらえますか

- どのカテゴリに、どんなキーが定義されていますか
- キーの型（数値 / 列挙 / 文字列）と単位はどう持っていますか
- 値の許容集合（enum）は定義されていますか、それとも自由入力ですか

### Q-A3. 「絞り込み軸へ昇格させるスペック」をどう決めますか

こちらの案は次のとおりです。**`spec_schema` に軸昇格フラグを持たせる**形です。

```
part_categories.spec_schema の各キーに
  facetable: true/false     ← 絞り込み軸に出すか
  facet_order: 1,2,3...     ← UI上の順番
  facet_type: enum / range  ← 選択肢か数値範囲か
  unit: "inch" / "T" / "kg-cm" / "mm"
を持たせる
```

こうすれば、**App側は `spec_schema` を読むだけで軸を生成でき、値リストをUIに持たなくて済みます。**
（検索設計の原則として「UI側に値リストをハードコードしない」を置いています）

この方式で問題ないか、あるいは Research 側で別の想定があるかを教えてください。

### Q-A4. 昇格させたい具体的なスペック（App側の希望）

MVP で軸にしたいのは以下です。**実在するキーかどうかを確認してください。**

| カテゴリ | スペック | 想定する値 | 型 |
|---|---|---|---|
| タイヤ・ホイール | タイヤ径 | 1.0 / 1.55 / 1.7 / 1.9 / 2.2 / 2.6 / 2.8 | enum（inch） |
| タイヤ・ホイール | ホイール取付 | ビードロック / 非ビードロック | enum |
| モーター・ESC | ターン数 | 13T / 21T / 27T / 35T / 45T / 55T ほか | enum or range（T） |
| モーター・ESC | 種別 | ブラシ / ブラシレス | enum |
| ステアリング | トルク | 数値範囲 | range（kg-cm） |
| サスペンション | ショック長 | 数値範囲 | range（mm） |
| バッテリー・電源 | セル数 | 2S / 3S / 4S ほか | enum |

**「実在しない」「別のキー名である」「値の揺れが激しく enum にできない」等があれば指摘してください。**
架空のスペックで検索UIを作りたくないので、**存在しないものは軸にしません。**

# B. `aliases`（別名）の正本を一本化してほしい ★最重要

## B-1. 何が起きているか

**同じ「別名」が2か所に定義されています。**

| 出所 | 形 |
|---|---|
| App正典 `myrig_db_schema_v1_6.md` | `parts_masters.aliases TEXT[]`（カラムに配列で持つ） |
| DB Research | `master_aliases` テーブル（別テーブルで持つ） |

**どちらが正本か決まっていません。**

## B-2. なぜ検索にとって最重要か

MyRIG は **日本語/英語の2言語で公開する**ことが決まっています（MVP時点から）。
そして検索では次の揺れをすべて吸収しなければなりません。

| 種類 | 例 |
|---|---|
| 型番の区切り | `TRX4` / `TRX-4` / `TRX 4` |
| 型番の連結 | `SCX10III` / `SCX10 III` / `SCX10 3` |
| 日英の製品名 | `Hilux` / `ハイラックス` / `Bronco` / `ブロンコ` |
| 英綴りの揺れ | `Tire` / `Tyre` / `タイヤ` |
| メーカー名 | `Traxxas` / `トラクサス` |
| 単位 | `1.9` / `1.9"` / `1.9 inch` / `1.9インチ` |
| 旧製品名・日本での通称 | メーカー公称と実際の呼ばれ方が違う |

**これらを解決する仕組みが `aliases` です。** 正本が2つあると、検索インデックスをどちらから作るかが決まらず、
**検索の入口そのものが作れません。**

## B-3. App側の見立て（間違っていたら訂正してください）

**`master_aliases` テーブル型のほうが優れている**と考えています。理由:

1. **別名ごとに属性を持てる** — 「これは日本語通称」「これは旧製品名」「これは型番の表記揺れ」を区別できる。
   配列だと全部フラットで、`ハイラックス` と `TRX4` が同じ扱いになる
2. **言語を持てる** — `locale: ja / en` を別名ごとに付けられる。2言語公開の前提として必要
3. **出所を持てる** — メーカー公称由来か、運用で追加したかを区別できる（正典の「公式根拠 > 推測」に沿う）
4. **RIG と パーツで共通化できる** — `parts_masters.aliases` だとパーツ専用になり、
   `rig_masters` 側に同じ問題が再発する

## B-4. 照会したいこと

### Q-B1. `master_aliases` を正本としてよいですか

よければ、App正典側の `parts_masters.aliases TEXT[]` は**失効**として扱います。

### Q-B2. `master_aliases` の現在の定義を共有してください

- どのカラムを持っていますか（別名の種類・言語・出所などを持てますか）
- `rig_masters` と `parts_masters` の両方を参照できますか
- メーカー名（manufacturers）の別名も同じ仕組みで持てますか

### Q-B3. 正規化はどちらの責務ですか

`TRX4` → `TRX-4` のような**表記の正規化**を、

- **DB側で正規化済みの値を格納する**のか
- **App側の検索インデックス構築時に正規化する**のか

どちらの想定か教えてください。
（App側は別途「正規化・別名・日英」の設計を進めており、担当範囲を確定させたいためです）

### Q-B4. 日英の対応はどこで持ちますか

`Hilux` ⇔ `ハイラックス` は、

- `master_aliases` に locale 付きで並べる
- 製品名そのものを `name_ja` / `name_en` で持つ
- 両方

のどれですか。
