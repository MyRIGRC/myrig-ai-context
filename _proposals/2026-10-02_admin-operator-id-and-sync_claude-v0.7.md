## A. 運営者 ID

### A.1 v1.2 の Claude 案を変える
v1.2 では「Auth のユーザー ID（auth.users.id）をそのまま運営者の恒久 ID にする」と書いた。**これを撤回して、運営者の表を 1 つ置く案に変える。** 理由は 2 つ。

1. **Catalog 区画は Research の DB に書く。** Research の DB は App の Auth を知らない。Research 側の記録（誰が Master を直したか）にも同じ「誰が」を書く必要がある。App の Auth の ID を Research に持ち込むより、**運営者の ID を 1 つ決めて、両方の DB に同じ値を書く**方が素直
2. **管理者の締め出しからの復旧（X8）で、Auth のユーザーを作り直すことがある。** そのとき auth.users.id が変わると、過去の Audit・保全・公開の「誰が」がつながらなくなる。**ログインの手段を付け替えても、運営者の ID は変わらない**作りにしたい

### A.2 案

**`admin_operators`（App の DB）**
| 列 | 中身 |
|---|---|
| operator_id | 運営者の恒久 ID（UUID）。**Audit・保全・公開・Research 側の記録の「誰が」はすべてこれ** |
| display_name | 記録に出す名前（例「MyRIG 運営 / イタヤ」） |
| status | active / disabled（**消さない**） |
| created_at | |

**`admin_operator_logins`（App の DB）**
| 列 | 中身 |
|---|---|
| operator_id | 上の ID |
| auth_user_id | App の Supabase Auth のユーザー |
| bound_at・unbound_at | 付けた日・外した日（**有効なログインは 1 つの運営者に 1 つ**） |

- **管理者かどうかの正本は `admin_operators.status = active` ＋ 有効なログインの紐付け**。v1.0 の「app_metadata」は、**この表から作る値**にする（手で別に設定しない = 二重の正本にしない）。ログインのたびに、この表から JWT に「管理者」の印を入れる仕組み（Supabase の Custom Access Token Hook）を使う案。⚠️ 要確認: この仕組みの対応と書き方
- 管理アプリのサーバー側の操作は、JWT の印に加えて**毎回この表を読んで確かめる**（印は入口の速い判定・表は正本）。印と表が食い違ったら「管理者ではない」とみなす（厳しい側に倒す）
- 2 段階認証: 管理アプリは「2 段階認証を済ませたセッション」だけを通す。⚠️ 要確認: Supabase Auth の 2 段階認証（TOTP）と、その確認の段階を判定する方法

### A.3 管理者のログインは、ふだんの利用者アカウントと分ける（Claude 案）
- イタヤが MyRIG の利用者としてガレージを持つアカウントと、**管理アプリに入るアカウントを別にする**
- 理由:
  - 利用者アカウントは退会・停止・同意・通報の対象になる。管理者の資格をそこに載せると、利用者としての操作が管理の資格に響く（v1.0「運営者は通常の退会・停止の対象外」をいちばん単純に守れる）
  - 利用者アカウントが乗っ取られても、管理の資格は奪われない
  - 運営としての発信（お知らせ・返信）と、個人としての投稿が混ざらない
- 管理者のアカウントには profiles を作らない（利用者の画面には出ない）。管理アプリは利用者のサイトと別に置くので、登録状態のガード（profiles が無ければはじめの設定へ）とはぶつからない

### A.4 今ある列との関係
- `comment_reports.resolved_by` などは今 `profiles.id` を指している → r12 で **`operator_id`（論理参照）**に合わせる（G16）
- Research 側の記録の「誰が」も `operator_id` を書く（FK は張れない・論理参照）

## B. Master の同期（Research → App）

### B.1 正典で決まっていること（変えない）
- Research の Master を、**PK を変えず・列名を変えず**、App の DB へ複製する。App はその複製を参照する（schema :438-440）
- **方式は App 側の決定事項**（:442）
- Research 側の条件は 3 つ: PK を振り直さない・列名を変えない・App 側で物理 DELETE しない（:443-446）
- **公開してよいかは同期の条件にしない**（109 §9・v1.2 M2）。公開面は `master_publication_effective`、Picker は `db_register` で判定
- 同期した Master は**再同期で上書きされる前提**（CACHE 可）
- PARTS は cross_ref が無いので、同期できても接続できない（H-1）

### B.2 比べた方式

| 方式 | 中身 | 判定 |
|---|---|---|
| **① App から取りに行く（差分）** | App 側の定期の処理が、Research から「前回より後に変わった行」を読み、App の複製に入れる | **推奨** |
| ② DB どうしの常時の複製（logical replication） | Postgres の機能で、Research の変更をそのまま App に流す | 採らない。列を足すなど Research の形が変わると止まりやすい・失敗が見えにくい・2 つの管理された DB の間で設定できるかも要確認 |
| ③ 表示のたびに Research を読む（FDW） | 複製を持たない | 採らない。**正典の「複製を参照する」に反する**。Research が止まると App も止まる |
| ④ Research から App に押し込む | Research で直したら App に書く | 採らない。Research が App の DB の書き込みの鍵を持つことになる（109 の境界と逆向き） |

### B.3 推奨の中身（①）

**読む側の権限**: Research の DB に、**同期専用の「読むだけ」の役割**を作る（Master の表を読むことしかできない）。鍵は管理アプリと同期の処理の環境だけに置く（利用者のサイトには置かない・v1.0 Q-K1）

**差分の取り方**: 各 Master の表の `updated_at` を見て、前回の同期より後に変わった行を読む
- ⚠️ **Research 側への新しい条件（4 つ目）**: すべての Master の表に `updated_at` があり、**行を変えたら必ず更新される**（DB のトリガーで）。これが守られないと差分で拾えない → Research レーンに確認・依頼（**要確認**）
- それでも漏れることがあるので、**1 日 1 回、全件の照合**（件数と、行ごとの更新日時の照合）をする

**書き方**:
- App の複製の表は、**同期の処理だけが書ける**（ほかの誰も書けない・管理アプリの画面からも書けない = A-3）
- 入れ方は「あれば上書き・無ければ足す」。**Research に無くなった行を App で消さない**（物理 DELETE しない）。無くなっていたら「Research 側で消えた」と Operations に出す（Research も物理 DELETE しない決まりなので、起きたら異常）
- **1 回の同期は 1 つのまとまり（トランザクション）で入れる**。途中で失敗したら全部やめて、前の状態のまま。⚠️ 件数が大きくなって 1 回で入らなくなったら、表ごとに分けて順番（メーカー → カテゴリ → RIG → バリアント → パーツ …）で入れる（**今の件数は要確認**）
- 同期のあと、App 側の**表示用の写し**（`manufacturer_name_cache` など CACHE 可の列）を作り直し、検索の索引と公開ページのキャッシュを更新する（同じ Job の後ろの段）

**いつ動くか**:
- 定期（例: 1 時間ごと）＋ **Catalog 区画で直したあとに「今すぐ同期」**（管理アプリの同じ画面から）
- 記録は `admin_jobs`（v1.0）: 始めた・終わった・読んだ件数・入れた件数・失敗。止まったら非常ベル（v1.0 §6 の「処理の停止」）

**App 所有の値を複製の表に混ぜない**: App が Master について持つ値（例: 将来の注目・購入先）は**別の表**に置く（購入先は `commerce_offers`・v1.1）。複製の表は 100% Research の値だけ。こうすれば上書きで App の値が消える事故が起きない

### B.4 MVP
- 同期は **MVP の必須**（v1.1）。最初は「定期 ＋ 今すぐ同期 ＋ 1 日 1 回の照合」まで
- 公開前の確認: ①全件を入れてから差分で回せるか ②Research で 1 行直して、次の同期で App に届くか ③同期の途中で止めて、前の状態のままか ④Research に無い行が出たとき Operations に出るか

## D. レビューの反映（141・GPT と Gemini）

### D.1 運営者 ID
| # | 指摘 | 反映 |
|---|---|---|
| GPT M1 | 「有効なログインは 1 つ」を運用でなく DB で守る | **DB の制約にする**: ① 1 つの operator_id に有効な auth_user_id は最大 1 つ ② 1 つの auth_user_id が有効に結びつく operator は最大 1 つ（どちらも `unbound_at IS NULL` の行だけの一意制約）③ 過去の紐付けは消さず `unbound_at` で残す |
| GPT M2 ／ Gemini M2 | 締め出されたとき、誰がどの経路で付け替えるかが無い | **非常用の付け替えの関数と手順を、公開前に用意する（Release Blocker）**: 関数 `admin_rebind_operator(operator_id, new_auth_user_id, reason)` を migration に入れる。**Supabase の管理画面（SQL）からだけ実行できる**（管理アプリ・利用者のサイトの役割では実行できない）。中身は ① 新しいログインを紐付け ② 古い紐付けを外す ③ 古いログインのセッションをすべて切る ④ Audit に記録、を 1 つのまとまりで。手順書 = 新しい Auth ユーザーを作る → 関数を実行 → 2 段階認証を登録し直す → 入れることを確かめる。**管理アプリの中に裏口は作らない** |
| GPT M3 ／ Gemini S1 | JWT の管理者の印を権限の正本にしない | **固定**: JWT の印は入口の速い判定だけ。**最終の判定は、操作のたびに「今の Auth ユーザー ↔ 有効な紐付け ↔ 有効な運営者」をサーバーで読む**。キャッシュしない（無効にしたらすぐ効くように。1 行を主キーで読むだけなので軽い）。食い違えば管理者ではない |
| GPT M4 | 2 段階認証を済ませた（AAL2）ことと、危ない操作の直前の再確認は別 | **分ける**: 管理アプリに入る = AAL2 ／ **危ない操作（停止・解除・保全の解除・削除・書き出し・購入先の一斉変更）= AAL2 ＋ 直前の再確認**（2 段階認証のコードをもう一度入れる）。再確認の有効時間は短く（案: 5 分）、サーバー側でその時刻を持って判定する |

### D.2 同期
| # | 指摘 | 反映 |
|---|---|---|
| GPT M5 ／ Gemini M1 | `updated_at > 前回` だけでは取りこぼす（同じ時刻の行・コミットの遅れ・時計のずれ） | **2 つとも入れる**: ① 取りこぼしの位置は **（updated_at, 主キー）の組**で持つ（同じ時刻の行を途中で切っても続きから読める・GPT）② さらに毎回 **前回の位置より少し前（案: 10 分）から読み直す**（コミットが遅れた行を拾う・Gemini）。入れ方は主キーで「あれば上書き」なので、重なって読んでも壊れない。**① だけではコミットの遅れを拾えず、② だけでは同じ時刻の大量の行で効率が落ちるので、両方** |
| GPT S1 ／ Gemini S2 | 大きくなったとき表ごとに入れると、新旧が混ざって見える・索引の作り直しまで同じまとまりに入れると重い | **MVP**: Master の取り込みを 1 つのまとまりで確定 → **索引と表示用の写しとキャッシュの作り直しは、確定のあとの別の Job**。**大きくなったら**: 一時の置き場に全部取り込む → 全部の表を検証 → **世代をまとめて切り替える**（表ごとに本番の表へ入れない） |
| GPT S2 | 全件照合が件数と更新日時だけでは弱い（入れ替わり・トリガーの故障を見落とす） | **全件照合 = 主キーの集合 ＋ 行の中身のハッシュ**。差分の同期（updated_at）とは**別の物差し**で確かめる |
| GPT S3 | 一時的な読み取りの失敗を「Research から消えた」と誤認しない | **「消えた」と判定するのは、全件をきちんと読み切れた照合の回だけ**。差分の同期で見つからないことは「消えた」にしない |
| GPT S4 | 同期する表を r12 の前に並べる | **候補（Research と確定する）**: manufacturers ・ rig_categories ・ part_categories ・ rig_masters ・ rig_master_variants ・ part_masters ・ part_master_variants ・ bodies ・ master_aliases ・ master_images ・ master_external_links ・ **公開の判定**。⚠️ 公開の判定は 109 §9 で「VIEW `master_publication_effective` が唯一の判定源・App で再計算しない」→ **元の表を写して App で VIEW を作り直すのではなく、Research の VIEW の結果の行をそのまま写す**（Claude 案・Research と確認） |
| GPT S5 | 「同期だけが書ける」を DB の権限で閉じる | **DB の権限で閉じる**: 複製の表に書き込めるのは同期専用の役割だけ。App のふだんのサーバーの役割・管理アプリの役割も書けない |

### D.3 公開の条件（Release Blocker）に足すもの
- 非常用の付け替えの関数と手順書（D.1 GPT M2）
- 同期の公開前の確認に 2 つ足す: ⑤ 同じ時刻の行を大量に入れても取りこぼさないか ⑥ 全件照合で、わざと入れ替えた行を見つけられるか
