## 1. 設計の原則（v0.1 から 3 つ足した）

1. 管理画面 = 運営の仕事を流す仕組み。
2. Admin Home は「今日やること」。何も無い日がいちばん良い（Zero-inbox）。
3. 呼ぶのは管理画面の外から（非常ベル §6）。
4. Signal / Case / Job / Audit を分ける（§2）。受付の正本は今ある表のまま。
5. **書き込みはサーバー側で、操作ごとに狭い関数にする。** 何でも通る service role の窓口は作らない（GPT G4）。物理 DELETE はしない（例外はストレージの実ファイル）。
6. 「したこと」を送るのは、実行が終わったと確かめてから。
7. AI は判断しない。下調べと下書きだけ。
8. App と Research を混ぜない。
9. 取り消せない操作は 2 段階。**解除は設定より危ない**ので、理由・再確認・Audit を必須にする（GPT G13）。
10. 🆕 **管理画面を「唯一の非常口」にしない。** Vercel ごと落ちたら /admin も使えない。緊急の切り替えは管理画面の外（Upstash・DNS・各サービスの管理画面）でもできる手順を残す（GPT M7・infra 裁定 09-06）。
11. 🆕 **制裁と保存の根拠を混ぜない。** 停止（Suspended）は制裁。保全（Legal Hold）は保存の根拠。停止したことを理由に消去を止めない（GPT M2）。
12. 🆕 **運営のデータも個人情報を最小にする。** Case・Job・Audit に本文やメールの全文を写さない。元の行を指すだけにし、運営のデータにも保存期間を持たせる（GPT G17）。

## 2. 4 つの概念とデータの形（GPT M1・M3〜M5・SPARK MUST1〜2 で作り直した）

| 概念 | 意味 | 正本の置き場（Claude 案） |
|---|---|---|
| **Signal** | システムが見つけた事実 | **汎用の Signal 表は作らない**。今ある表への問い合わせ（VIEW）で出す。ただし **非常ベルを鳴らしたもの・セキュリティの異常・外部の状態の変化** は、あとで確かめられるよう保存する（`admin_alerts`・下） |
| **Case** | 人の判断が要る案件 | `admin_cases` と、1 対多の子表（下） |
| **Job** | 決まったあとに機械が**あとで・失敗しうる形で**実行する仕事 | `admin_jobs`。**対象は非同期・失敗・やり直しがあるものだけ**（退会の確定・保存期間・書き出し・メール・再送）。非表示のような即時の UPDATE は Job にしない（その場で実行し Audit に残す）（GPT M4） |
| **Audit** | 起きたことの記録 | `admin_audit_log`。追記だけ。**中身は「誰が・いつ・何を・どの行に・理由の区分・結果」だけ**。本文は写さない |

**表の形（案。schema には未反映・r12 で設計）**

| 表 | 中身 | 決まり |
|---|---|---|
| `admin_cases` | kind・priority・status・対象（target_type・target_id）・決定・内部メモ | 状態の正本は Case。Audit と二重に持たない（GPT G5） |
| `admin_case_sources` | Case ↔ 元の受付（source_type・source_id） | **(source_type, source_id) を一意にする**。ここに無い受付 = まだ誰も触っていない受付（SPARK MUST1）。**外部キーで縛らない論理参照**にし、元の行が消えても Case 画面は「元のデータは消去済み」と出して落ちない（SPARK MUST2） |
| `admin_case_deadlines` | 期限ごとに 1 行: 制度・数え始めの事実と日時・暦日か営業日か・期限・届いたか | 1 つの Case に期限は複数ありうる（7 日の照会＋法令の期限など）（GPT M1）。**期限の日数を schema に焼かない**（運営が根拠を見て入れる）（GPT G20） |
| `admin_case_events` | 送った文・受けた返事・状態の変化 | 送った文は「そのまま」残す（対応集の決まり）。保存期間は Case と同じ |
| `admin_jobs` | 種類・対象・状態・試行回数・最後のエラー・**冪等キー** | **同じ仕事を 2 回走らせても結果が同じ**作り。途中から再開できる。退会の確定は二重実行を許さない（GPT M4） |
| `admin_alerts` | 非常ベル: 種類・対象（Case / Job / 異常）・送った時刻・届いたか・確認した時刻 | 同じものを何度も鳴らさない・鳴らしたかが分かる（GPT M5） |
| `admin_audit_log` | 追記だけ | 保存期間を持つ（下の G17） |
| `legal_holds` | 範囲（どの表のどの行・どの列）・理由・かけた人と日・見直しの日・外した人と日・外した理由 | **Case の「保全あり / なし」の印にしない**。保全は独立した寿命を持つ。アカウントまるごとではなく必要なデータ単位でかける（GPT M3）。Case 側には「有効な保全あり」を派生で出すだけ |

> 「新しい表は 3 つだけ」は制約にしない（GPT M1）。中核は Case / Job / Audit。

## 4. 手渡し型 AI（Task Package）

v0.1 の形（Goal・Inputs・**Untrusted**・Evidence・Rules・Allowed / Forbidden・Output・Return）と、守り 4 つ（利用者の文はデータとして隔離・個人情報の最小化・緊急は渡さない・貼り戻しも信用しない）はそのまま。

**変更: MVP 区分を A → B**（GPT。公開の安全には直結せず、Case の運用が固まってから足せる）。
MVP では Case の詳細画面の文を手でコピーすれば回る。テンプレートの形は本書で決めておく（B で画面に載せるときにぶれないように）。

## 6. 非常ベル（GPT と SPARK の食い違いを裁定）

**鳴らすもの**: R2 緊急の申し立て ／ D1・D2 の処理が止まった ／ X3 管理者まわりの異常（最小）／ R7 漏えいの疑い ／ X7 費用が 100% に達した

**載せるもの（Claude 裁定案）**

| 載せる | 載せない |
|---|---|
| 種類（決まった語彙の **理由の区分**: 脅迫・危害 ／ 同意のない性的な画像 ／ 子ども ／ 管理者のログイン異常 ／ 処理の停止 ／ 費用） | 本文・申し立てた人や投稿者の名前・メールアドレス |
| 対象の種類（投稿 / コメント / アカウント / 処理） | 対象の投稿の URL・画像 |
| #ID | 利用者が書いた文（理由の自由記述を含む） |
| **`/admin/m` への入口**（Case の番号だけを含む。開くにはログインと 2 段階認証が要る） | |

- GPT は「種類と #ID だけ」、SPARK は「理由の区分・対象の種類・直リンクを足す」。**SPARK の 3 つを採る**。どれも**決まった語彙か運営の画面の場所**で、利用者の情報を含まないので、GPT の「本文・名前・画像・生の URL を送らない」も守れる。出先で「今すぐ動くべきか」を決めるには、区分が要る。
- MVP の届け先は**件名に「緊急」のメール**。ただし **R7 で実際に届くか・遅れ・失敗を試す**。メールの仕組みが落ちたときにベルも鳴らない問題があるので、**2 つ目の経路**（プッシュの専用サービスなど）は R7 で比べる（GPT Q2）。
- `admin_alerts` に鳴らした事実を残し、同じものを何度も鳴らさない。確認したら止める。

## 7. Mobile（`/admin/m`）

- 緊急の一覧（R2・X3）だけ。理由の区分・対象の種類・受けた時刻。

## 11. 採らない別案

- 汎用の Signal 表（派生できるものは VIEW。ただしベルの対象は `admin_alerts` に残す）
- 停止を保全の代わりにする（制裁と保存の根拠が混ざる）
- Case に「受付の一覧・送った文・期限・保全」を全部詰める（1 対多がすぐ起きる）
- すべての運営の処置を Job にする（即時の UPDATE まで待ち行列に入れると故障点が増える）
- 何でも通る service role の窓口
- 非常ベルに本文・名前・画像・対象の URL を載せる／逆に #ID だけにする（出先で判断できない）
- 管理画面を唯一の非常口にする
- 管理画面を全部レスポンシブにする
- **個人サイトのリンクを最初は自動で公開する（SPARK SHOULD 1）** → 採らない。下の §14
