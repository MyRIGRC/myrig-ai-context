## 0. 前提の置き直し

イタヤ指摘（2026-08-21）:

> 検索結果として、他の検索の結果からどう人が動くのかっていうのをもう少し考えて。
> どう誘導するかとか、例えばマネタイズとかも含めて、あと他のページとかその辺も含めて。

いまの検索結果は **「クエリに一致した行を5種類ぶん並べたもの」** でしかない。
一致した行を並べるのは検索の**前半**であって、後半は「その人が次に何をするか」の設計。
MyRIG の検索結果ページには後半がまだ無い。

そして MyRIG の場合、**後半のほうが差別化になる。**
「TRX-4」に一致する行を返すだけなら Google でもできる。
MyRIG にしかできないのは **「TRX-4 を実際に持っている164人が、何を付けて、どう走らせているか」** を返すこと。

## 1. 結論（先に出す）

| # | 決定 | 根拠 |
|---|---|---|
| 1 | **「すべて」の先頭に製品マスタの「答えカード」を1枚出す** | 検索の主目的が製品理解のとき、行の羅列では答えにならない。Discogs / Rebrickable / Ravelry が同型 |
| 2 | **セクション見出しを「型の名前」から「問いの言い換え」に変える** | 実装コストほぼゼロで、結果が「答え」に見える |
| 3 | **モバイルの型別セクションが正。PC版のブレンドを直す** | 異種エンティティのスコアは比較不能（Lalmas）。ブレンドは順位が恣意的になる |
| 4 | **結果内キーワード絞り込みボックスは作らない** | 推奨する一次資料が無く、クエリの所在が2箇所に割れる |
| 5 | **絞り込みは軸マトリクス駆動＋複数選択＋件数＋適用中チップ＋URL反映** | Baymard の失敗類型に真正面から当たっている |
| 6 | **既定ソートは「関連順（多様性ベース）」。人気順を既定にしない** | Baymard: 人気順既定は上位が同型に偏りカテゴリの幅が伝わらない |
| 7 | **「この検索を保存」→ 新着通知。再訪の理由を作る** | ヤフオク・メルカリ・eBay が持つ。MyRIG では「新しい作例が出たら教えて」 |
| 8 | **「すべて」タブにはソートを出さない。ソートは種別タブに入ってから** | GPT指摘。「すべて」はダイジェストなので、RIGとLOGと人を横断して「新着順」に並べる基準が存在しない |
| 9 | **結果面に広告・アフィリエイトを置くかは要裁定**（主査推奨は撤去、GPTは維持） | §7・§1-2 |

## 1-2. GPTレビューとの一致点・割れた点

同じ問いを GPT にも投げた結果（2026-08-21）。**独立に到達した結論が一致した項目は、確度が高いとみなす。**

### 一致（採用）

| 項目 | Claude | GPT |
|---|---|---|
| 結果の先頭に「その製品が何か」を出す | §3-1 答えカード | 「検索理解」領域 |
| 完全一致するマスタが無いときは出さない | §3-1 出す条件 | 「曖昧なら候補チップだけ出す」 |
| 絞り込みを種別タブごとに変える | §4-1 軸マトリクス駆動 | 「タブによって絞り込み項目を変える」 |
| 適用中条件を常時可視化＋件数バッジ | §4-2 | 「絞り込み ③」＋条件チップ |
| 結果同士を横につなぐ導線 | §6 製品⇄RIG⇄LOG | 「TRX-4をもっと見る 対応パーツ186件…」 |
| PC/モバイルは**表示形式**が違ってよい | §5（NN/g・Slack実例） | 「揃えるべきは見た目ではなく検索の意味」 |
| 広告を増やすより検索意図に乗せる | §7 | 「検索→製品特定→実例→購入先」 |

### 割れた（3件）

**① 結果内キーワード絞り込みボックス**
GPT: 入れるべき（「TRX-4」の中から `Bronco` `Sport` `K10` で絞る）。
主査: **専用ボックスは作らない**（§4-4）。推奨する一次資料が無く、クエリの所在が2箇所に割れる。
**→ 統合案を採る（§3-5）。** GPTが挙げた具体例（Bronco/Sport/K10）は、専用ボックスでなく**絞り込み候補チップ**で満たせる。チップを押すと検索窓のクエリが `TRX-4 Bronco` に書き換わる。クエリの所在は1つのまま、GPTの狙う体験が得られる。

**② `search-results.html` の AD枠**
GPT: P22-B6b裁定（1ページ1枠・PR明示）に従い**維持**してよい。
主査: **撤去を推奨**（§7）。ただし既存裁定と衝突するので**イタヤ裁定が要る**。
論点は、P22-B6b（1ページ1枠）と、`page_blocks.block_type='adsense'` の対象が index / category_top / subcategory_top のみで**検索面が対象外**であること、この2つのどちらが新しいか。

**③ PC版のブレンド結果を直すか**
GPT: PCは広い画面なので混在でよい。
主査: **直すべき**（§5）。理由は画面幅ではなく**スコアの比較可能性**。Lalmas / Arguello は「異質な情報アイテムは特徴量が異なるため同一アルゴリズムでランク付けできない」とし、1,296セッションの実験で「関連度を横断的に測定できない場合は non-blended の方が適切」と結論している。画面が広いことは、順位の根拠が無いという問題を解決しない。
**→ PC版バッチでの裁定事項として残す。**モバイル側の作業はこの結論に依存しない。

### GPTから新規に採用したもの

- **「すべて」タブからソートを外す**（§4-3）— 見落としていた。ダイジェストを横断ソートする基準は存在しない。390px の縦も稼げる
- **基準RIGを結果ページに持ち越す**（§6-2）— D案の「自分のRIGから探す」が結果面まで生きる

## 2. いまの実装の問題（実測）

`search-results.html` の絞り込みシートの中身:

```html
カテゴリ  [すべて] [ロッククローラー] [バギー] [ドリフト]
メーカー  [すべて] [Traxxas] [Axial] [RC4WD]
スケール  [すべて] [1/10] [1/18] [Mini-Z]
          [この条件で絞り込む]
```

| 問題 | 内容 | 一次資料 |
|---|---|---|
| **単一選択になっている** | `data-chipgroup` で1つだけ `is-active`。「Traxxas と Axial の両方」が組めない | Baymard 2025ベンチ: 同一ファセット内で複数値を結合できないサイトが **14%**。失敗類型 |
| **件数が無い** | どれを押すと何件になるか分からない。0件の組み合わせを選べてしまう | Baymard: ファセット値に件数を出す。Adobe Commerce も同様 |
| **適用中フィルタが見えない** | 何が効いているか結果側から読めない | Baymard: 適用中フィルタ一覧が無いサイトが **20〜28%**。「3件適用中」という数だけの表示も不可 |
| **軸が3つで固定** | 種別タブを切り替えても中身が変わらない。人・ガレージのタブでも「スケール」が出る | v3.1 §4 の軸マトリクス未適用 |
| **URLに乗らない** | 絞り込んだ状態を共有できない・戻れない | Baymard: フィルタ/ソートで戻る期待に反するサイトが **27%**、オーバーレイで **37%** |
| **値が各4つしかない** | モックだからだが、実データでは車種24・メーカー数百になる。いまの形では破綻する | — |

## 3. 「すべて」ページの再設計

### 3-1. 答えカード（新規・最重要）

クエリが**製品マスタと強く一致したとき**、結果の先頭に製品カードを1枚だけ出す。
これは検索結果の1行ではなく、**そのクエリへの答え**として扱う。

```
┌────────────────────────────────┐
│ [製品画像]  Traxxas TRX-4                        │
│             Scale and Trail Crawler / 1/10       │
│                                                  │
│  MyRIGに 164台 登録 ・ 整備LOG 402件             │
│                                                  │
│  よく使われているパーツ                          │
│   Duratrax Deep Woods CR 1.9      28台が使用 ›   │
│   SAMIX アルミアクスルシャフト     41台が使用 ›   │
│   1.9 ビードロックホイール         63台が使用 ›   │
│                                                  │
│  [ 164台の作例を見る ]  [ 製品情報を開く ]        │
└────────────────────────────────┘
```

**なぜこれが効くか**
- 「TRX-4」というクエリの実際の意図は「TRX-4 の行を18件見たい」ではなく「TRX-4 について知りたい」。行の羅列は答えの形をしていない。
- **「よく使われているパーツ」は MyRIG にしか出せない。** これがカタログ+UGCハイブリッドの核心で、Ravelry（パターン→プロジェクト）、Rebrickable（パーツ→収録セット）、Discogs（リリース→Have/Want統計）が同じ構造を持つ。
- 件数を必ず添える。Baymard の 5,170人調査で「5★ / 4件」より「4.5★ / 57件」が約2倍選ばれた。**件数はそれ自体が判断材料**。

**出す条件**（誤爆を防ぐ）
- クエリが `rig_masters` / `parts_masters` の名前・型番・別名と**強一致**したときのみ
- 複数の製品に等しく一致したときは**出さない**（Baymard: 曖昧クエリで自動遷移するな。候補リンクを出せ）
- 一致しないクエリでは普通のダイジェストのまま

### 3-2. セクション見出しを「問い」に変える

実装コストはほぼゼロで、結果の読み味が変わる。

| 現状 | 変更後 |
|---|---|
| 製品情報 18件 | **「TRX-4」という製品** 18件 |
| RIG 18件 | **TRX-4 を持っている人の車体** 18台 |
| パーツ 18件 | **TRX-4 に付けられているパーツ** 18点 |
| LOG 18件 | **TRX-4 の整備・走行記録** 18件 |
| ユーザー 12件 | **TRX-4 に詳しい人** 12人 |

※種別タブのラベル（RIG/パーツ/LOG/製品情報/人）は短いままにする。見出しだけ問いにする。
※クエリがカテゴリ名だったとき（例:「ロッククローラー」）は「ロッククローラーの車体」等に差し替わる。

### 3-3. 種別セクションの順序をクエリで変える

いまは RIG → パーツ → 製品 → LOG → 人 で固定。
**型番クエリなら「製品情報」が先頭**、一般語なら RIG が先頭、が自然。

- 型番・製品名に一致 → 製品情報 → RIG → パーツ → LOG → 人
- カテゴリ名に一致 → RIG → 製品情報 → パーツ → LOG → 人
- 人名・@handle に一致 → 人 → RIG → …
- それ以外 → 現状順

**根拠の扱い**: これは観察ではなく設計判断（推論）。ただし「0件の種別セクションは出さない」（v3.1 §6）と同じ発想で、**ユーザーの問いに近い順に置く**という一貫した原則で説明できる。

### 3-5. 絞り込み候補チップ（結果内キーワードの代替）★GPT指摘の統合案

答えカードの直下、または結果の先頭に、**そのクエリをさらに絞る候補**をチップで出す。

```
TRX-4 の中から絞り込む
[ Bronco 24 ] [ Sport 18 ] [ K10 11 ] [ Blazer 9 ] [ 4M 7 ]
```

- チップを押すと **検索窓のクエリが `TRX-4 Bronco` に書き換わる**。フィルタではなくクエリの拡張として扱う
- 候補は**その検索結果の中から実際に頻出する語**（マスタ名の差分・派生モデル名）。架空の候補を出さない
- **件数を必ず添える。0件の候補は出さない**
- 押した後は元のクエリに戻れるよう、検索窓の内容が正本（`←`で1語ぶん戻る）

**なぜ専用の第二キーワード欄にしないか**
- ユーザーは平均2.2回クエリを直す（Baymard）。直す先が検索窓と絞り込み欄の2つに割れると、どちらを直せばいいか分からなくなる
- 主要日本ECでも観察されない。楽天(SP)の絞り込みは価格/ブランド/カラー/サイズのみ。モノタロウ・ミスミにも無い。Yahoo!ショッピングが持つのは第二キーワード欄ではなく「キーワード範囲」トグル（商品名＋説明 / 商品名のみ）
- Baymard の Search Scope 研究が挙げる5機能に「結果内での第二クエリ」は入っていない

**つまり、GPTの狙い（結果の中からさらに絞りたい）は正しく、実現手段だけを変える。**
自由入力でなく候補提示にすることで、0件になる語を打つ余地も消える。

### 3-4. 0件・低件数からの回復

v3.1 §6 の内容を維持しつつ、**低件数（1〜3件）でも回復導線を出す**ように広げる。

- 0件: 条件解除候補 / 表記候補（Hilux→ハイラックス）/ 関連マスター / 装着例 / クエリを残す
- 1〜3件: 結果の下に「条件をゆるめる」— 効いているフィルタのどれを外すと何件になるかを提示
- **クエリを消さない**（Baymard: PC 33% / モバイル 42% が消す。ユーザーは平均2.2回クエリを直す）
- **ユーモアで茶化さない**（NN/g が明示的に否定）

## 4. 種別タブページの再設計

### 4-1. 絞り込み

```
種別タブ = パーツ のとき

┌ 絞り込み ────────────────── × ┐
│                                          │
│ パーツカテゴリ                            │
│  ☑ タイヤ・ホイール            412        │
│  ☐ サスペンション              218        │
│  ☐ 駆動系・ギア                150        │
│  ＋ もっと見る（11）                      │
│                                          │
│ 適合シャーシ                              │
│  ☐ 公式適合のみ                 88        │
│  ☑ 装着例あり                  204        │
│  ☐ 未確認を含める              412        │
│                                          │
│ メーカー                    [ 検索 🔍 ]   │
│  ☑ Traxxas                     96        │
│  ☐ RC4WD                       61        │
│  ＋ もっと見る（148）                     │
│                                          │
│ スケール                                  │
│  ☐ 1/10   ☐ 1/18   ☐ Mini-Z              │
│                                          │
├──────────────────────┤
│  条件をクリア      [ 204件を表示 ]         │
└──────────────────────┘
```

決定事項:

| 項目 | 決定 | 根拠 |
|---|---|---|
| 出る軸 | **v3.1 §4 の軸マトリクスで駆動**。種別を切り替えると軸も入れ替わる | 1箇所定義。別々に持つと必ずズレる |
| 軸の順序 | **適合 → カテゴリ → メーカー → スペック → 補助** | NN/g: 選択への影響が大きい属性を上へ。モノタロウ自動車補修部品も「適合メーカー」がブランドより上 |
| 選択 | **同一軸内は複数選択（OR）。軸をまたぐと AND** | Baymard: 単一選択は失敗類型（14%） |
| 件数 | **全値に件数。0件の値は無効化（消さない）** | 消すと「何が消えたか」が分からず選択を再現できない |
| 値が多い軸 | 初期8件＋もっと見る。**50件超（メーカー）はファセット内検索窓** | Algolia が `searchForFacetValues` を一級APIとして提供 |
| 適用方式 | **ドラフト → 適用**。ただし件数はドラフト状態でリアルタイム更新 | NN/g: モバイルは Apply ボタン。Adobe Commerce: 件数併記 |
| 提示 | **全画面オーバーレイ**（項目数が多いため） | v3.1 §7 の既決を維持 |
| スペック軸 | **カテゴリ確定後にのみ出す**（タイヤを選んで初めて 1.9/2.2/2.6 が出る） | 全部出すと RIG タブにタイヤ径が出る等の破綻 |
| 数値 | **離散バケットのチェックボックス。スライダー単独は不採用** | NN/g: 精密なドラッグはタッチで困難 |

### 4-2. 適用中条件チップ

結果リストの直上に常設。**「3件適用中」という数だけの表示は不可**（Baymard が明示）。

```
[ タイヤ・ホイール × ] [ Traxxas × ] [ 装着例あり × ]   すべて解除
```

- 軸名を含める（スペック中心の軸では「タイヤ径: 1.9"」の形）
- 個別解除 ＋ すべて解除
- 横スクロールではなく折り返し（横スクロールだと2つ目以降が隠れる）

### 4-3. 並べ替え

**「すべて」タブにはソートを出さない。** ★GPT指摘・採用

現状は種別タブ列の下に `関連度 / 新着 / 人気` の3ピルが常時出ている。
だが「すべて」は RIG → パーツ → 製品情報 → LOG → 人 の**ダイジェスト**なので、
**RIGとLOGと人を横断して「新着順」に並べる基準が存在しない。**
押しても意味が定義できないコントロールを置いていることになる。

→ **「すべて」ではソート行ごと出さない。**種別タブへ入ると `関連順 ▾` が現れる。
390px で3ピルぶんの縦が浮くという副次効果もある。

**既定は「関連順」。人気順を既定にしない。**
Baymard: 人気順を既定にすると上位が同一タイプに偏り、そのカテゴリの幅が伝わらない。

種別ごとに選択肢を変える（Baymard「カテゴリ固有ソート」）:

| 種別 | 選択肢 |
|---|---|
| RIG | 関連順 / 新着順 / いいね順 |
| パーツ | 関連順 / 装着例が多い順 / 新着順 |
| LOG | 関連順 / 新着順 / いいね順 |
| 製品情報 | 関連順 / 登録台数が多い順 / 新着順 |
| 人 | 関連順 / RIG登録数順 |

※「人気順」という語は使わない（既裁定「ランキング表現を使わない」）。**何で並んでいるかを名指しする**（「装着例が多い順」「登録台数が多い順」）。

### 4-4. 結果内キーワード絞り込みは作らない

イタヤ案「キーワードで絞り込みとかもできたほうがいい」に対する回答:

**作らない。** 理由:

1. **推奨する一次資料が見つからない。** Baymard の Search Scope 研究が挙げる5機能に、「結果内での第二クエリ」は入っていない。NN/g にも該当ガイドラインが無い。
2. **主要日本ECでも観察されない。** 楽天(SP)の絞り込みは価格/ブランド/カラー/サイズのみ。モノタロウ・ミスミにも無い。Yahoo!ショッピングが持つのは第二キーワード欄ではなく**「キーワード範囲」トグル**（商品名＋説明 / 商品名のみ）。
3. **クエリの所在が2箇所に割れる。** ユーザーは平均2.2回クエリを直す（Baymard）。直す先が2つあると、どちらを直せばいいか分からなくなる。

**代わりに置くもの:**
- 検索窓のクエリを**必ず残し、その場で編集できる**ようにする（現状すでに実装済み）
- **ファセット内検索窓**（メーカーなど値が多い軸のみ）— これは別問題で、実装は妥当
- 必要なら Yahoo! 型の**検索対象範囲トグル**（「本文も含める / タイトルのみ」）

### 4-5. 位置復元と履歴

- カード → 詳細 → 戻る で**元のスクロール位置へ復帰**（Baymard: 13%が失敗）
- 無限スクロールのバッチ読み込みごとに `history.pushState()` で URL 更新
- **絞り込みシートを開く＝履歴1エントリ。戻るで閉じる**（Baymard: 37%が違反）
- **フィルタ適用＝履歴1エントリ。戻るで直前の条件に戻る**（同 27%が違反）

## 5. PC版との整合 — どちらが正か

イタヤ指摘:

> PC版だとサーチリゾルトって関連度順でRIGもパーツも全部ごちゃ混ぜで表示されるけど、
> モバイル版だとトップが全てで、関連度でRIGとパーツとLOGとかが全部分かれたセクションになってる。

### 結論: **モバイル版が正しい。PC版を直す。**

根拠（一次資料）:

Lalmas / Arguello *Aggregated Search*（Foundations and Trends in IR）は、複数の異種ソースをまとめる検索の提示形式を blended（1本のリストに混ぜる）と non-blended（種別ごとに分ける）に整理し、blended の中核的困難として **「異質な情報アイテムは特徴量が異なるため同一アルゴリズムでランク付けできない」** と明記している。
さらに1,296セッションの実験で、**blended ではクリックが位置効果を強く受けるが、non-blended では受けなかった**とし、**「関連度を横断的に測定できない場合は non-blended の方が適切」** と結論している。

MyRIG に当てはめると:
- 製品マスタは正規化された短いレコード、LOG は自由文の長文。BM25 系のスコアは尺度が根本的に違う。
- 1本に混ぜると、**どちらかに機械的に偏る**。そして偏った側が上を占めた瞬間、もう一方は位置効果で事実上不可視になる。
- 実害の具体例: PC版で「新着順」にした瞬間、LOG が全画面を占拠する（LOGが最も高頻度で増えるため）。

### ブレークポイントで違ってよいのか

**提示形式の分岐は許容される。ただし「何が見つかるか」が違ってはいけない。**

- NN/g（Budiu & Pernice, 2016）: 「デバイス間で content と feature の parity は目標だが、UI要素とデザインが完全に同一である必要はない」
- 実例: **Slack は公式ヘルプ上、デスクトップとモバイルで検索対象の型の並びが違う**（PC: Messages/Files/People/Channels/Canvases、モバイル: Messages/Canvases/Files/Channels/People/Workflows）

したがって「PCは3カラムで種別を横に並べ、モバイルは縦にセクションを積む」のような**レイアウトの違いは問題ない**。
問題なのは「PCでは人・ガレージが検索できるがモバイルではできない」のような**発見可能性の差**。

### PC版の直し方（別バッチ）

1. PC の検索結果を種別セクション制へ寄せる（モバイルの29件ダイジェストと同じ構造）
2. PC は横幅があるので、セクション内は横スクロールの棚ではなく**2〜3列グリッド**
3. 左サイドバーは D案の「探し方」＋軸マトリクスのフィルタ
4. クエリなしのときだけ、左サイドバーが「探し方」の姿になる（7月末裁定②「同一ページ内の最小検索開始状態」と整合）

## 6. 検索結果からの誘導 — どこへ送るか

MyRIG の検索結果から人が行くべき先は、**4つしかない。**

```
検索結果
 ├─① 製品マスタ    「この製品は何か」    → ここに購買導線がある
 ├─② 誰かのRIG     「実物はどうなるか」  → 作例。MyRIGの本体
 ├─③ LOG           「どう扱うのか」      → 整備・走行の知見
 └─④ 人・ガレージ  「誰に聞けばいいか」  → フォローへ
```

そして **①⇄② の双方向リンクが最も価値が高い。**

| 方向 | 導線 | 先行例 |
|---|---|---|
| 製品 → RIG | 「この製品を使っている164台」 | Ravelry: パターン→プロジェクト / Rebrickable: パーツ→収録セット |
| RIG → 製品 | RIG詳細のパーツ表から製品マスタへ | PCPartPicker のビルド構成 |
| 製品 → LOG | 「この製品が出てくる整備記録」 | — |
| RIG → 人 | 車体からオーナーのガレージへ（実装済み） | — |

**Baymard の失敗率データが、この設計の必要性を裏づける**（クエリ種別ごとの検索失敗率）:
互換性検索 **44%** / 用途検索 **43%** / 略語・記号検索 **54%** / 非商品検索 **66%**。

RC の検索はこの4つに集中する。「TRX-4 対応」「1.9 タイヤ」「13T モーター」「岩場 セッティング」——
**カタログ側だけでは全部失敗する。** UGC側の実装例（誰が実際に付けているか）が事実上の互換性証拠になる。

### 6-2. 基準RIGを結果ページに持ち越す ★GPT指摘・採用

D案の「自分のRIGから探す」で選んだRIGを、**結果ページの上部に残し続ける。**

```
基準RIG: My TRX-4  ×
```

- パーツ結果では、**公式根拠があるものにだけ**「適合情報あり」を出す
- 根拠が無いものは**推測で「適合」と書かず、普通の結果として出す**（v3.1 §12 の3レイヤー：公式適合 / 装着例あり / 要確認）
- 基準RIGは URL に `rig_scope=` として乗せ、`×` で解除できる

**これが育つと**「タイヤ」と検索しただけで、自分の TRX-4 に関係のあるタイヤから見られるようになる。
検索機能というより、MyRIG がユーザーの所有情報を持っていることの価値そのものになる。

**ただし過信しない。** 適合データが薄い段階でこれを強く効かせると、
「自分のRIGに合うタイヤは3件しかない」という誤った印象を与える。
**MVPでは絞り込みではなく並び替え（関連あるものを上に寄せる）として実装し、件数を減らさない。**

### 再訪の理由を作る: 保存検索

```
[ この検索を保存 ]  → 「TRX-4 の新しい作例が出たら通知」
```

- ヤフオク・メルカリ・eBay が持つ機能。**MyRIG 版は「新着商品」ではなく「新しい作例・新しいLOG」**
- v3.1 §13-4 で既に起票済み。ここで優先度を上げる
- **通知に広告を入れない**（v3.1 §9-3 の既決を維持）
- 効果を示す公開データは見つからなかった（＝観察された実装であり、実証された施策ではない）

## 7. マネタイズ — 結果面には置かない

### 決定: **検索結果ページにアフィリエイトも広告枠も置かない。購買導線は製品マスタ詳細に一本化する。**

これは ledger #34（イタヤ言明「MyRIGはショップではない。控えめ・邪魔しないを常に優先し、迷ったら出さない側に倒す」）と整合するが、
**収益的にも結果面に置くより有利**だと考える。理由:

1. **結果面の広告はバナーブラインドネスで読まれない。** NN/g の研究は、広告的要素が注意をそらし視覚探索を阻害することを示している。結果行に混ぜれば、広告が読まれないうえに検索結果の信号対雑音比だけが下がる。
2. **製品マスタは検索の終着点であり、そこに到達した人の購買意図が最も高い。** 「TRX-4 に付くタイヤを探している」→ 結果一覧 → 製品マスタ、と絞り込んだ末に着地した人にリンクを出すほうが、通りすがりに出すより成立する。
3. **結果面を広告面にすると、順位が疑われる。** MyRIG の検索順位はオーガニックであるべきで、報酬と順位を分離しておくこと自体が資産になる。

なお現状の `search-results.html` には `.ad-slot`（PR枠）が1枚入っている。**これは撤去を提案する**（要裁定）。
既存アーキテクチャ上も `page_blocks.block_type='adsense'` の対象は index / category_top / subcategory_top のみで、**検索面はそもそも広告対象外**。実装と設計はこちらで整合している。

### ステマ規制（2023-10-01施行・景表法5条3号）の実務

一次資料（消費者庁 運用基準・Q&A）から確認できたこと:

- 規制対象は **商品・サービスを供給する事業者**。依頼を受けた第三者（インフルエンサー等）は対象外
- 「事業者の表示」該当性は **表示内容の決定への関与** で判断。アフィリエイトは、事業者が内容を指示したり対価で特定の訴求を誘導した場合に該当する
- 表記は「広告」「PR」等。**周囲の文字より小さい / 気づけない位置 / ハッシュタグ群への埋没は不可**
- Q13: 「本サイトはアフィリエイト広告を利用しています」をページ冒頭に1行置くだけでは**不十分な場合がある**と明記
- Q7/Q21: 対価も取引関係もない一般ユーザーの投稿・レビューは事業者の表示に当たらず、表記不要
- Q6: 高評価を条件に割引等を与えると事業者の表示になる

MyRIG の運用に落とすと:

1. 製品マスタのリンク**直近**に「PR」を本文と同等以上のサイズで表示（v3.1 §9-5 の既決）
2. UGC（RIG/LOG）にユーザー個人のアフィリエイトリンクを許すなら、**投稿時にPR表記を強制するモジュール**を入れる。無償UGC自体は非該当だが、運営が対価や優遇を与えた瞬間に該当化するため、線引きを規約に書く
3. 「レビューを書いたらポイント」のような施策は**やらない**（Q6に直撃する）

## 8. やらないこと（アンチパターン）

| # | やらないこと | 根拠 |
|---|---|---|
| 1 | 結果行への広告・スポンサー枠の混入 | バナーブラインドネス。信号対雑音比の低下 |
| 2 | 純粋な無限スクロール単独 | 戻るで先頭に戻る。比較・再発見を阻害。Load more＋pushState を併用 |

| 11 | 結果行に出している情報にフィルタが無い | Baymard: 38%が欠落。逆にフィルタで絞れない属性を行に足しても操作不能な情報が増えるだけ |
